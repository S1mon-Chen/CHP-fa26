class TransactionalToolRunner:
    def execute_with_undo(self, tool_call, context):
        # 1. 优先执行 dry_run 预演分析 (无物理副作用) ★
        if tool_call.args.get("dry_run", True):
            preview = self.simulate_dry_run(tool_call)
            if not preview.is_safe:
                raise DryRunValidationError(preview.reason)
            return preview.diff_summary  # 仅向 LLM 展示修改影响范围
            
        # 2. 物理写入前捕获 undo 快照 (如 git stash / DB BEGIN) ★
        undo_snapshot = self.capture_undo_state(tool_call)
        try:
            return self.sandbox.execute(tool_call)
        except Exception as err:
            # 3. 产生物理异常时瞬间自动触发 Rollback 回滚 ★
            self.rollback_transaction(undo_snapshot)
            return f"Observation: Execution failed and auto-rolled back: {err}"
  • 预演与事务锁双保证：让模型在真实写入前看清改动 Diff；一旦物理报错则自动抹除污染状态。
核心：将带有修改副作用的 Skill 包装为具备“原位原子恢复”能力的事务管道

读写分离与事务回滚的三大防线

Transactional Defense Pillars

Safety Pillars
1. dry_run 预飞分析 (Preflight Dry-Run) Preview Before Apply

在数据库调用 `EXPLAIN` 或在 Git 执行 `git diff --check`。仅打印即将修改的影响范围，供模型与 HITL 确认无误后再进行写操作。

2. 事务快照与自动 Undo (Auto Rollback) Atomic Restore

依赖数据库 `BEGIN...ROLLBACK` 或 Git `git checkout/stash` 暂存区。物理改动若触发单测失败，宿主环境瞬间撤销该 Turn 的全量变更。

3. 读写物理管道分离 (Read/Write Separation) Replica vs Master Gate

将只读查询导向只读副本与轻量沙箱；将状态修改导向带有事务锁、Undo 日志与 HITL 审批卡扣的只写隔离宿主。

实践参考：Cursor / Roo Code 的 Git Diff 预演与按需 Revert 回滚卡扣

Architectural Core Thesis / 架构师视角

允许 Agent 修改代码或数据库的前提是系统随时能够“一键撤销（Undo）”；通过构建 dry_run 预演与事务原子回滚管道，是将概率大模型引入生产环境运维与编程的关键技术防线。

🎯 剖析 dry_run 预演与事务 Undo 的工程价值： “向学员深入剖析：在使用 IDE 编程插件或数据库 Agent 时，当 AI 准备修改 5 个文件或者做 UPDATE SQL 操作，系统不应该直接覆盖硬盘文件。而是先开启 `dry_run` 生成物理 Diff，让开发者或沙箱单测检查。如果物理运行中报错，自动执行 `git checkout .` 撤销本次修改。”
💡 强调读写分离架构： “向学员强调：只读工具（SELECT、git diff、cat）可以毫无顾忌地高并发运行在副本环境；而修改类工具（UPDATE、patch_apply）必须包裹在带有撤销快照和卡扣的事务容器中，保证系统可随时‘悔棋’。”
