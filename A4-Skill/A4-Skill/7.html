4-Turn 消息队列状态流

Message Queue State Machine

Protocol Trace
[
{"role": "system", "content": "You are an assistant with SQL tools."},
{"role": "user", "content": "Find top 3 VIP users."},
{"role": "assistant", "content": null, "tool_calls": [
{"id": "call_call998", "type": "function", "function": {"name": "query_db", "arguments": "{\"limit\":3}"}}
]},
{"role": "tool", "tool_call_id": "call_call998", "content": "[{\"id\":1,\"name\":\"Alice\"}]"}
]
  • `assistant` 节点持有 `tool_calls`：模型不再直接返回字符串回答，而是产出挂载了全局唯一 `id` 的工具调用意图。
  • `tool` 节点强引用 `tool_call_id`：宿主执行完成后追加 `role: "tool"` 消息，显式以 `tool_call_id` 回写执行 Observation。
规则：缺失中间 `assistant (tool_calls)` 消息直接补 `tool` 结果会导致 API 报错

4 角色协议职责与句柄防错

Role Responsibilities & State Sync

Role Contracts
system & user 上下文边界与目标输入

`system` 注入全局角色指令与安全边界；`user` 提出业务诉求，激活多轮对话决策链。

assistant & tool `tool_call_id` 是并发对齐的物理钥匙

在并发工具调用（Parallel Tool Calls）中，模型可一次性发出多个 `call_01`, `call_02`。宿主在并发执行完后，必须通过 `tool_call_id` 按顺序精准对齐回上下文，防止模型在后续 Turn 中产生“认知混淆”。

物理事实：tool_call_id 保证了长对话上下文里异步工具结果的零交错防死锁

Architectural Core Thesis / 架构师视角

Function Calling 的 4 角色消息队列是维护“无状态 LLM”与“有状态物理沙箱”状态同步的状态机契约（Message State Machine Contract）；只有严格保障 tool_call_id 句柄的完整传递，才能构建不崩溃的长对话 Agent 控制流。

Speaker Notes / 讲师讲稿
🎯 剖析 4 角色消息队列的核心规则： “向学员深入剖析：在引入 Function Calling 后，消息数组不再只是简单的 user 和 assistant 交替。当模型决定调用工具时，会输出一个带 `tool_calls` 的 `assistant` 消息；随后应用层执行工具，并必须追加一个 `role: 'tool'` 消息，其中 `tool_call_id` 必须与上一条 `assistant` 消息中的 `id` 绝对对齐。”
💡 解决常见的 API 400 报错： “很多工程师在开发 Agent 时经常遭遇 API 报错 `An assistant message with 'tool_calls' must be followed by tool messages`。这就是因为在对话历史剪枝（Pruning）或重试时漏掉了中间带有 `tool_calls` 的 assistant 消息，或者 `tool_call_id` 不匹配导致状态机崩溃。”
