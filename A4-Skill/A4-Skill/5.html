Tool Definition Schema：JSON Schema 规范与字段语义设计

解构 OpenAPI / JSON Schema 契约语法：为什么 description 不是给程序员看的注释，而是直接压入 Prompt 指导采样的 注意力语义锚点

标准 Tool Declaration Schema

OpenAPI 3.0 / JSON Schema Spec

Schema Contract
{
"name": "git_create_pull_request",
"description": "Submits a new PR to target branch. Trigger ONLY after all local unit tests pass.",
"parameters": {
"type": "object",
"properties": {
"title": {"type": "string", "description": "Conventional Commit title format (e.g. feat: add auth)"},
"base_branch": {"type": "string", "enum": ["main", "develop"]}
},
"required": ["title", "base_branch"]
}
}
  • `required` 必填强约束：防止 LLM 漏传核心参数，未定义的可选参数会自动置为 Null。
  • `enum` 离散枚举收敛：将自由文本强行限制在预设的合法枚举值集合内。
原则：参数定义越严苛， Sampling 阶段的随机性越小

Schema 语义设计的两大金律

Attention Anchors & Constraints

Design Golden Rules
1 `description` 即微型 Prompt (Attention Anchor)

大模型并没有执行特定代码的前置概念。`description` 字段会被全量注入 System Instructions 区域，直接决定了模型在什么场景下被唤醒召回以及参数该写成什么格式。

2 收紧参数边界，消杀“模糊匹配”

避免使用未受限的 `string` 类型（如“格式为任何文本”）。能用 `enum` / `Literal` 限制的必须定义离散选项，能添加正则 `pattern` 的必须添加校验边界。

效果：优质 Schema 可将工具误召回与参数类型报错降低 90%+

Architectural Core Thesis / 架构师视角

写 Tool Schema 不是给文档工具做字段标注，而是在向 LLM 的注意力矩阵（Attention Matrix）植入语义锚点。 Schema 编写的严密程度直接决定了 Agent 系统的吞吐稳定性与召回召回率。

Speaker Notes / 讲师讲稿
🎯 引导学员理解 description 的真实角色： “向学员强调：很多程序员在写 JSON Schema 时，把 `description` 当成一般的可写可不写的代码注释，随便写一句 `param a`。这在大模型工具调用里是致命的错误！因为 LLM 是靠 `description` 里的自然语言语义来判断这个参数该填什么的。”
💡 强调 required 与 enum 的收敛力量： “指出：如果不设置 `required` 列表，大模型在采样时会倾向于漏填可选参数；如果不设置 `enum`，模型可能会填出类似 `main_branch`、`master` 等不同变体，导致下游 API 解析崩溃。”
