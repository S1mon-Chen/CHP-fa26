Skill 的副作用（Side Effects）分类：ReadOnly (只读) vs State-Changing (写操作)

建立安全与可恢复性的物理屏障：按 只读查询 (ReadOnly) 与 状态修改 (State-Changing) 显式标注 Skill 副作用，为幂等重试、事务回滚与 HITL 人工审批卡扣提供工程凭据

Skill 副作用元数据显式标注

Side-Effect Metadata Declaration

Metadata Contract 
from enum import Enum

class SideEffectType(str, Enum):
    READ_ONLY = "READ_ONLY"          # 无副作用：纯查询/无状态变更
    STATE_CHANGING = "STATE_CHANGING"  # 有副作用：写数据库/修改文件/调外部API

@tool(
    side_effect=SideEffectType.READ_ONLY,
    idempotent=True
)
def query_user_orders(user_id: int) -> list:
    """Pure read-only query. Safe for auto-retry."""
    return db.select_orders(user_id)

@tool(
    side_effect=SideEffectType.STATE_CHANGING,
    requires_approval=True,  # 触发 HITL 卡扣 ★
    supports_undo=True        # 附带撤销动作 ★
)
def delete_user_account(user_id: int) -> str:
    """Deletes account. State-changing & high risk."""
    return db.delete_user(user_id)
  • 代码即契约：在修饰器元数据中显式暴露 `side_effect` 属性，为上游控制器提供管控抓手。
核心：将工具按“只读”与“修改”区分是实现生产级安全卡扣的关键

副作用治理的三大工程基石

Side-Effect Engineering Governance

Safety Control
1. 幂等重试机制 (Idempotent Retries) ReadOnly Auto-Retry

对于 `ReadOnly` Skill，网络超时或偶发错误可放心进行自动重试 (Auto-Retry)；对于 `State-Changing` 工具则严禁盲目重试，防止产生二次写污染。

2. HITL 人工审批卡扣 (Human-in-the-Loop) Approval Gate

标注 `STATE_CHANGING` 且具备高风险（如删除、提权、出站写）的 Skill，控制器自动挂起并唤醒 HITL 审批弹窗，待人类确认后方可释放执行。

3. 审计日志与撤销策略 (Undo & Audit) Dry-Run & Transaction Memo

修改类 Skill 必须强行记录结构化审计日志（Audit Log），并优先支持 `dry_run` 模式预演或提供对应的 `undo` 撤销回调逻辑。

最佳实践：只读工具自动放行，修改类工具强加审批与审计

Architectural Core Thesis / 架构师视角

Skill 的副作用分类并非简单的元数据打标，而是构建系统级容错、权限分级与人工治理卡扣（HITL Gate）的硬性凭据；显式隔离并管控写操作，是打造生产级 Agent 防崩防越权防线的关键一步。

🎯 剖析为什么必须显式标注 Side Effects： “向学员深入剖析：大模型并不清楚调用 `query_user` 和 `delete_user` 在物理世界有什么本质区别，对它而言都只是吐出一个函数名。如果系统不显式打上 `side_effect` 标签，控制器就无法判断遇到网络失败时能否自动重试，也无法阻断越权的删除操作。”
💡 衔接后面的 HITL 与沙箱安全： “提示学员：显式打标 `STATE_CHANGING` 是后续模块三引入 **Human-in-the-Loop 人工审批卡扣** 和 **沙箱隔离级别分配** 的基础依据。只读工具可以直接放行运行，写操作工具则触发强卡扣，这是企业级 AI 安全治理的基本功。”
