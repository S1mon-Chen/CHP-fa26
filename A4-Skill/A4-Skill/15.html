收紧复杂参数的概率空间：利用 Literal / Enum 枚举限制、多层 Pydantic 嵌套模型 与 强类型 List[T] 容器，消杀任意文本带来的类型坍缩

复杂强类型 Pydantic 工具契约

Nested Pydantic Model Code

Complex Schema
from pydantic import BaseModel, Field
from typing import Literal, List, Optional

# 1. 嵌套对象 (Nested Object) 契约
class
FilterCondition(BaseModel):
field: str = Field(description="Target column name")
operator: Literal["eq", "gt", "in"] = Field(description="Operator")
value: str = Field(description="Comparison value string")

# 2. 顶级复杂查询入参
class
DataExportInput(BaseModel):
export_format: Literal["JSON", "CSV", "PARQUET"] # Enum 约束 ★
filters: List[FilterCondition] = Field(description="Filter items list") # List[T] ★
limit: Optional[int] = Field(default=100, ge=1, le=5000) # 数值范围 ★
  • 嵌套 Schema 自动展开：Pydantic 导出的 JSON Schema 自动将 `FilterCondition` 提炼为 `$defs` 引用的子对象结构。
原则：拒绝在入参里使用无约束的纯 Dict/Any，必须将字段展开为强类型模型

复杂入参收紧的三大工程法则

Complex Type Boundary Control

Type Safeguards
1. 枚举离散收敛 (Literal / Enum) Free Text $\to$ Discrete Enum

用 `Literal["JSON", "CSV"]` 强行将大模型的自由文本吐字收敛为固定的合法字符串集，在 JSON Schema 层注入 `enum` 字段阻断未知变体。

2. 显式嵌套模型 (Nested BaseModel) Avoid Raw Dict/Any

严禁使用未声明结构的自由 `dict` 参数。将复杂的结构化字典拆解为独立的子 `BaseModel` 类，为每一个子字段赋予精准的 `description`。

3. 容器类型元素绑定 (Typed List[T]) Item Type Constraints

声明数组时必须指定泛型元素类型 `List[T]`（如 `List[FilterCondition]`），防止大模型向列表里混入标量与非结构化杂质。

工程收益：使复杂的嵌套 SQL 条件与批量任务调用的反序列化成功率达到 99.5%+

Architectural Core Thesis / 架构师视角

面对复杂的数据查询与多条件过滤，绝对不要把类型判断扔给运行时代码去写正则补偿！通过将输入约束升级为多层嵌套 Pydantic Model 与 Literal 枚举，在 Logit Masking 层即可完成绝对合规的参数生成。

Speaker Notes / 讲师讲稿
🎯 剖析复杂入参类型的防崩溃设计： “向学员强调：很多工程师在写工具参数时，对于复合选项喜欢写 `format: str` 并在注释里说‘填 JSON 或 CSV’。这给大模型留下了很大的自由度，容易吐出 `json_string` 或 `csv_format` 等变体。使用 `Literal['JSON', 'CSV', 'PARQUET']` 在 Schema 层直接转译为 `enum` 数组，能 100% 消除这个问题。”
💡 避免自由 Dict/Any 参数： “提醒学员：在 Pydantic 中千万不要图省事写 `filters: dict`！因为 `dict` 导出的 Schema 只有 `type: object`，里面没有任何字段描述，大模型根本不知道该传什么 key。必须将其封装为子 `BaseModel` 类（如 `FilterCondition`）。”
