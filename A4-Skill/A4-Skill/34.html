Log Pruner 
import re

class LogPrunerEngine:
    def prune_build_logs(self, raw_logs: str, max_lines: int = 80) -> str:
        lines = raw_logs.splitlines()
        total_lines = len(lines)
        if total_lines <= max_lines:
            return raw_logs  # 未超行数阀门则原样放行

        # 1. 正则提取关键的 Pytest / Build 失败堆栈 (FAILURES/ERROR) ★
        error_blocks = re.findall(
            r"(?:FAILURES|ERRORS|FAILED|Traceback).*?(?=\n\n|\Z)", 
            raw_logs, re.DOTALL | re.IGNORECASE
        )
        
        # 2. 首尾双视窗截断：保留头 20 行、尾 50 行，中间压平 ★
        head = "\n".join(lines[:20])
        tail = "\n".join(lines[-50:])
        truncated = total_lines - 70
        
        extracted_summary = "\n".join(error_blocks[:2])
        return (
            f"{head}\n"
            f"/* ... [{truncated} lines truncated by LogPruner Engine] ... */\n"
            f"/* Key Stacktrace Extracted: */\n{extracted_summary}\n"
            f"/* Tail Logs: */\n{tail}"
        )

大日志剪枝的三大工程防线

Log Pruning Architecture Pillars

Token Budget
1. 堆栈正则提纯 (Stacktrace Extraction) Targeted Extraction

通过正则或 AST 检索算法抓取 `FAILURES`, `ERROR`, `Traceback` 等核心块，剔除无价值的库安装进度条与编译 Log。

2. 首尾双视窗截断 (Head/Tail Dual-Window) Dual-Window Retain

保留初始前 20 行命令参数与末尾 50 行退栈信息，确保命令行语义完整，折叠中间重复膨胀的漫长刷屏日志。

3. Token 预算感知中间件 (Token-Budget Middleware) Observation Guard

设定 Observation 的硬 Token 预算（如 $<1500$ Tokens），一旦超标即刻触发剪枝管道，杜绝“Lost in the Middle”注意力稀释。

实践选型：Cursor / Roo Code 在执行 pytest 与 npm test 时的日志压缩策略

Architectural Core Thesis / 架构师视角

海量杂乱日志是挤爆 Context Window 与稀释模型注意力的毒药！通过 首尾双视窗截断与 Stacktrace 正则提纯，将 Observations 压缩至 Token 预算边界内，是构建高吞吐 Agent 的硬指标。

Speaker Notes / 讲师讲稿
🎯 讲授为什么日志剪枝是必备防线： “向学员深入剖析：在自动化测试或代码编译场景下，一个 `pytest` 或 `mvn test` 往往会吐出上万行的冗余标准输出。如果毫不处理就直接作为 `role: 'tool'` 写入 Context，一方面会瞬间吃掉几万个 Token，造成数倍的费用爆表；另一方面会引发注意力稀释（Lost in the Middle），导致大模型反而找不到真正报错的代码行号。”
💡 介绍首尾双视窗与 Stacktrace 提纯： “提示学员：最佳解法分为两步——首先通过正则精准提取 `FAILURES` 和 `Traceback` 等报错块；其次采用‘首尾双视窗’，保留前 20 行命令 Header 与最后 50 行报错结尾，将中间上万行毫无价值的进度条压平。”
