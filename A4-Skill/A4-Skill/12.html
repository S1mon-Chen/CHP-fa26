解构代码契约的注意力植入机制：为什么 Python 函数的 Docstring 注释 与 Pydantic Field 字段描述 不是程序员文档，而是引导 LLM 注意力与采样的 微型 Prompt (Micro-Prompt)

“含糊签名” vs “语义锚定签名”

Docstring & Field Description Impact

Signature Audit
// ❌ 反例：缺失语义描述 (错唤率高、参数乱填)
def get_user(u_id: str, flag: bool = False):
"""Gets user."""
// 结果: LLM 无法判断是 UUID 还是 Email、flag 作用未知 ❌
// ✅ 正例：完整动作目标与 Field 边界 (100% 精准召回)
def get_active_user_by_email(
email: str = Field(description="Exact user email address (e.g. alice@company.com)"),
include_roles: bool = Field(default=False, description="Set True ONLY if user RBAC permissions are needed")
) -> UserDTO:
"""Fetches an active user's profile from DB by exact email match. Read-only."""
// 结果: 极度清晰的触发条件、入参例样与权限说明 ★
  • 从 Docstring 提取微型 Prompt：导出工具 Schema 时，Docstring 自动转译为 API `description` 压入 System Instructions。
实测数据：清晰的 Field 描述可将参数格式错误率降低 85% 以上

函数签名 Prompting 的三大金律

Micro-Prompting Principles

Golden Rules
1. 明确“动作 + 目标 + 边界” Action + Target + Boundary

Docstring 开头第一句必须包含明确谓词（如 `Fetches`, `Submits`, `Deletes`）和前置触发条件（如 `Trigger ONLY after unit test passes`）。

2. 示例格式内嵌 (Concrete Exemplars) Field Examples

在 `Field(description=...)` 里显式内嵌合法的正则表达式或格式示例（如 `e.g. 'v1.2.0' or '2026-08-01'`），避免 LLM 填入任意字符串。

3. 显式标注“不可用情况” Negative Guidance

在工具描述中加入否定提示（如 `Do NOT use this tool for batch queries; use query_users_batch instead`），彻底杜绝近义工具的混淆。
