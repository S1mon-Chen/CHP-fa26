from enum import Enum

class IsolationLevel(str, Enum):
    PROCESS = "PROCESS"      # < 1ms | 共享内核 | 适合纯只读 API
    CONTAINER = "CONTAINER"  # ~100ms | Cgroups/gVisor | 适合标准 Shell
    MICROVM = "MICROVM"      # ~5ms | 硬件虚拟化 | 适合任意 Python 代码 ★

def allocate_sandbox(tool_meta: dict) -> Sandbox:
    if tool_meta["side_effect"] == "READ_ONLY":
        return SubprocessSandbox(timeout_s=3)
    elif tool_meta["requires_arbitrary_code"]:
        return FirecrackerMicroVM(memory_mb=512, network=False)
    else:
        return DockerSandbox(image="python:3.11-slim", read_only=True)
  • 按需分配算力与安全预算：只读轻量工具无需付出高额 VM 启动代价，高危代码执行强加物理硬件隔离。
核心：依据 Skill 风险等级在启动延迟、资源消耗与安全逃逸风险间取得最佳平衡

沙箱三层隔离对比与选择法则

3-Tier Isolation Trade-offs

Trade-offs
1. 进程级 (subprocess) Zero Overheads < 1ms Boot

共享宿主 OS 内核与文件系统，仅靠 OS 进程参数约束；适合完全受信的内部只读查询工具，禁止执行模型生成的裸代码。

2. 容器级 (Docker / gVisor) Namespace & Cgroups 50~100ms Boot

通过 Namespaces、Cgroups 或 gVisor 拦截 Syscalls；实现根文件系统只读、限制 CPU/RAM 内存配额，切断网络出站。

3. 微虚拟机级 (Firecracker / e2b) Hardware Virtualization ~5ms Boot ★

基于 KVM 虚拟化独立 Linux 内核，秒级拉起微虚拟机；彻底消杀内核漏洞逃逸（Kernel Escape）威胁，是任意代码解释器的黄金选型。

应用选型：e2b / Modal (MicroVM) vs AWS Fargate / Docker (Container)

Architectural Core Thesis / 架构师视角

绝对不要在同一个环境中混用不同安全等级的工具！根据 Skill 的副作用与代码自由度构建“动态分级沙箱分配器 (Dynamic Sandbox Allocator)”，是将生成式代码安全接入生产环境的核心技术基石。

🎯 讲授三层沙箱架构的 Trade-offs： “向学员深入剖析：在构建 Code Interpreter 或工具宿主时，很多工程师陷入两极分化——要么直接用原生的 `subprocess` 跑任意代码（导致宿主服务器随时面临 `rm -rf` 风险），要么所有请求都拉起庞大的 Docker 容器（导致冷启动延迟拉长到秒级）。了解进程级、容器级与微虚拟机（Firecracker）三层的 Trade-offs，是架构师做选型的基本功。”
💡 强调 Firecracker / MicroVM 的兴起： “提示学员：在现代云原生 Agent 框架（如 e2b 或 Modal）中，基于 KVM 的 Firecracker MicroVM 已经成为趋势。它拥有与 Docker 相当的轻量（启动仅 5ms），同时具备独立 Linux 内核的硬件级隔离，能彻底拦截内核漏洞逃逸攻击。”
