OpenAI / Anthropic / DeepSeek 的 Function Calling Protocol 协议解构

剖析主流大模型 API 原生产载荷（Payload）规范：解构 OpenAI / DeepSeek 标准化 Schema 与 Anthropic Claude input_schema / tool_use 块，打通多模型统一适配层

OpenAI & DeepSeek 协议流

tools[].type = "function"

Standard Spec
// Request Payload
"tools": [{"type": "function", "function": {"name": "query_db", "parameters": {...}}}]
// Response Payload (finish_reason: "tool_calls")
"message": {
"tool_calls": [{"id": "call_call998", "type": "function", "function": {"name": "query_db", "arguments": "{\"sql\":\"...\"}"}}]
}
// Feedback Role
{"role": "tool", "tool_call_id": "call_call998", "content": "..."}
  • DeepSeek 完全兼容：DeepSeek-V3/R1 原生支持 OpenAI API 格式，参数即为字符串转义 JSON。
  • `tool_call_id` 句柄：明确依赖 `role: "tool"` 与 `tool_call_id` 在消息队列中对齐物理结果。
适用场景：OpenAI, DeepSeek, Qwen, Llama 统一生态接口

Anthropic Claude 协议流

tools[].input_schema & tool_use

Claude Spec
// Request Payload
"tools": [{"name": "query_db", "input_schema": {...}}]
// Response Content Block (stop_reason: "tool_use")
"content": [{
"type": "tool_use", "id": "toolu_998", "name": "query_db", "input": {"sql": "..."}
}]
// Feedback Block
{"role": "user", "content": [{"type": "tool_result", "tool_use_id": "toolu_998", "content": "..."}]}
  • 结构化类型参数：输入模式名为 `input_schema`，响应中 `input` 直接为已解析结构化 Dict。
  • `tool_result` 用户块：工具执行结果作为 `role: "user"` 消息中的 `type: "tool_result"` 数组返回。
突破：基于 Content Blocks 的多模态与 Tool Call 统一表达

Architectural Core Thesis / 架构师视角

掌握底层 HTTP / JSON Payload 载荷原语差异是屏蔽供应商锁定的关键；通过设计统一的 API Adapter 适配层（支持 OpenAI tool_calls 与 Claude tool_use 的无缝转换），构建真正跨厂商兼容的企业级 Agent 基础设施。

Speaker Notes / 讲师讲稿
🎯 剖析 OpenAI/DeepSeek 与 Claude 的协议差异： “引导学员关注：OpenAI 格式把函数入参压成了字符串化的 JSON (`"arguments": "{\"sql\":\"...\"}"`)，且使用专属 `role: "tool"` 消息回复；而 Claude Messages API 把参数直接当作 JSON 对象 (`"input": {...}`)，且回复是通过 `role: "user"` 中的 `type: "tool_result"` 块承载。”
💡 强调 Adapter 模式（适配器模式）： “在构建企业级 Agent 系统时，不应在业务逻辑里写死某一家厂商的 API 字段。理解这两套 API Payload 原语，有助于我们编写轻量级的统一适配器（Adapter Pattern），在 OpenAI、Claude 与 DeepSeek 之间无缝切换。”
