模块二导论：Skill 的本质——无状态原子能力契约 (Atomic Capability)

解构 AI 原子能力（Skill）的微服务设计哲学：为什么 Skill 必须具备 高内聚、低耦合、单一职责 (SRP)，并作为无状态 RPC 接口被 LLM 确定性调度

“多头肥大工具” vs “原子能力契约”

SRP vs Monolithic Tool Design

Design Audit
// ❌ 反模式：“全能巨型工具” (Fat Monolithic Tool)
def do_everything_in_db(action, sql, notify_email, drop_table=False):
"""查表、删表、发邮件通知、清日志混合在一起..."""
// 风险: 语义模糊导致模型误唤醒、产生不可逆写污染 ❌
// ✅ 正例：“原子单一职责契约” (Atomic RPC Skill)
def execute_read_only_query(sql_query: str) -> List[dict]:
"""Executes a Read-Only SQL SELECT statement. Pure query, zero side effects."""
// 优势: 高度确定、只读收敛、注意力精准聚焦 ★
  • 避免语义重叠与歧义：工具功能越纯粹，LLM 在向量与注意力召回阶段的错唤率越低。
法则：一个 Skill 应该像微服务中的 RPC 接口，保持高内聚与低耦合

Skill 契约设计的开篇三大支柱

The 3 Pillars of Skill Contracts

Module 2 Pillars
1. 无状态 (Statelessness) 输入决定输出

不在全局变量或隐式内存中维护隐藏状态。相同的入参在相同环境下执行，必须产出幂等或明确的结果。

2. 强类型边界 (Type Bounds) Pydantic & Hints 驱动

依赖 Python 类型注解与 Pydantic 校验模型，自动导出无歧义的 JSON Schema，在物理执行前完成参数截断。

3. 显式副作用标记 (Side-Effects) ReadOnly vs Write

显式标注工具是只读查询还是物理修改；修改类工具需配合事务回滚或 Human-in-the-Loop 人工审批。

下一步：探索如何通过 docstring 与 Field 描述植入注意力语义锚点

Architectural Core Thesis / 架构师视角

Skill 应当被当作软件工程中的无状态原子能力契约（Atomic Capability Contract）；只有严格控制工具的职责边界与副作用，才能保障 Agent 控制流不因误召回而陷于混乱。
