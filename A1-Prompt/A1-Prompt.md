# A1-Prompt：指令工程与结构化上下文构建

> 课程：SE3353（CHP-fa26）。本笔记依据 `A1-Prompt/1.html`～`40.html` 整理，按知识主题归纳，并补充理解边界。课件中的成功率、压缩率和性能提升数字缺少完整实验设置，本笔记不将其作为通用结论；模型、SDK 与工具名称仅用于理解课件示例。

## 1. 本讲主线与知识地图

本讲讨论：**如何把大模型的概率生成能力接入可验证、可控制的软件工程流程？**

课件将 LLM 比喻为“非确定性虚拟 CPU”，将 Prompt 比喻为指令接口。这个比喻强调工程责任：输入要明确，输出要校验，实际操作要由程序控制，结果要通过外部证据验证。

| 模块 | 页码 | 核心问题 | 主要方法 |
| --- | --- | --- | --- |
| 结构化 Prompt 与防御性设计 | 1～7 | 如何减少歧义与错误积累？ | Role、Instruction、Constraints；前置检查、后置校验、降级 |
| 上下文与结构化输出 | 8～15 | 如何组织材料并对接程序？ | XML 分区、Schema、Pydantic、AST 剪枝、注入防护 |
| 推理范式 | 16～25 | 如何组织复杂任务的求解过程？ | Few-Shot、CoT、自洽采样、任务分解、ToT、自我修正 |
| 工具与状态交互 | 26～38 | 如何让模型基于真实环境行动？ | ReAct、Function Calling、Controller、沙箱、规则与评测 |

可沿着以下关系理解全课：

**任务契约 → 上下文构建 → 模型生成 → 结构与权限校验 → 工具执行 → 真实反馈 → 修正与评测。**

## 2. 为什么需要结构化指令

### 2.1 自回归生成与错误级联

LLM 逐个生成 Token，下一步生成依赖已经给出的上下文和已生成内容：

$$
P(w_t \mid w_1, w_2, \ldots, w_{t-1})
$$

如果输入中出现错误接口名，或模型早期生成了不存在的方法，后续内容可能继续沿用错误前提，形成 **Error Cascading（错误级联）**。

需要区分两个层次：单次生成序列通常逐步追加；外部程序仍可让模型重新生成、编辑文件或回到先前状态。因此，错误并非不可修复，但修复需要明确的反馈和控制流程。

### 2.2 注意力与长上下文

课件用缩放点积注意力解释模型如何关联上下文：

$$
\operatorname{Attention}(Q,K,V)
= \operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

其中，Q、K、V 分别表示查询、键和值，$d_k$ 是键向量维度。理解重点是：模型需要从大量输入中定位与当前生成有关的信息。

**上下文能装得下，不等于所有信息都能被同样可靠地利用。** 课件通过 Lost in the Middle（中间迷失）说明：关键信息藏在长材料中间时，可能更容易被忽略。其示意百分比不是固定的“物理内存分区”。

工程应对：

- 将任务、核心约束与材料分区，减少无关内容。
- 在稳定的指令区声明规则，并在当前任务末尾简要重申最重要的约束，即 Tail Pinning（尾部锚定）。
- 按任务检索源码、接口与示例，避免直接灌入整个仓库。
- 通过实际任务评测判断上下文布局是否有效。

### 2.3 上下文污染与幻觉

**上下文污染**指错误代码、错误假设或过期结论留在历史中，持续影响后续生成。**幻觉**则表现为内容合理、流畅，但缺少事实依据，例如虚构私有 SDK 的方法。

处理思路是删除或标记已经证伪的假设，保留已确认事实和失败原因，必要时重建会话上下文；涉及环境状态、接口定义和代码行为时，通过文件、文档、编译器与测试获取证据。

低 Temperature 可减少采样随机性，但不能消除幻觉，也不等于绝对可复现。课件后续的多路径采样反而需要一定多样性，因此温度应服务于具体求解策略。

## 3. Prompt 三要素与防御性设计

### 3.1 三要素

| 要素 | 需要说明什么 | 示例 |
| --- | --- | --- |
| Role：角色域 | 专业视角、职责、作用范围 | 审查 Java 服务中的安全与性能问题 |
| Instruction：目标指令 | 要完成的动作与交付物 | 定位问题，引用相关代码，给出最小修改建议 |
| Constraints：约束 | 不能做什么、输出形式、异常处理方式 | 不修改公共方法签名；缺少依赖定义时列出缺项 |

角色描述提供方向，任务和约束提供具体判定条件。“写得优雅、高性能”缺少验收标准；更明确的表达是“保留现有行为”“不增加第三方依赖”“通过指定测试”。定量目标也必须符合实际任务，不能随意要求不可能达到的复杂度。

### 3.2 防御性设计的三层

1. **前置检查（Pre-conditions）**：确认代码、版本、接口或数据定义是否足够；缺少关键输入时明确返回缺项。
2. **后置校验（Post-conditions）**：检查 JSON、字段、类型、范围以及业务条件；不能只依赖模型承诺。
3. **降级处理（Fallback）**：无法确定时返回约定状态，例如 `MISSING_CONTEXT`、`UNSURE`，由程序决定补充检索、停止或转交人工。

模型给出的置信度可以作为辅助信息，但不能直接当成经过校准的正确概率，更不能代替验证。

### 3.3 练习：缺少上下文的慢 SQL 诊断

课件输入：

```sql
SELECT * FROM orders o
JOIN users u ON o.user_id = u.id
WHERE DATE(o.created_at) = '2026-08-01'
  AND o.status = 'PAID';
```

防御性分析应先检查数据库引擎及版本、表结构、现有索引、数据规模和执行计划。没有这些信息，不能断言某个索引已经存在，也不能保证新索引一定有效。

仍可指出待验证的风险：对列应用 `DATE()` 可能妨碍普通索引的范围访问。课件给出的候选改写是：

```sql
o.created_at >= '2026-08-01 00:00:00'
AND o.created_at < '2026-08-02 00:00:00'
```

这属于待验证建议：需要确认字段类型、时区与原查询语义，并用执行计划检查效果。不要把函数表达式一概等同于“索引必然失效”。

## 4. 结构化上下文与输出契约

### 4.1 输入组织与输出验证是两个问题

- **结构化上下文**：告诉模型哪些是指令、哪些是待分析材料，以及材料的路径和语言等元数据。
- **结构化输出**：规定返回字段与类型，让程序能够解析、校验并分派后续操作。

| 格式 | 主要用途 | 使用时的注意点 |
| --- | --- | --- |
| Markdown | 文档、人工阅读、简单代码说明 | 嵌套代码围栏需要正确处理 |
| XML 风格标签 | 多文件上下文、任务与材料分区 | 内容可能包含同名标签；严格 XML 需正确转义 |
| JSON / YAML | 元数据、配置与规则列表 | 长代码的转义、换行或缩进较繁琐 |
| JSON Schema | 声明输出或工具参数的结构 | Schema 合法不等于业务语义正确 |

XML 风格的上下文示例：

```xml
<system_instructions>
  <role>Java 代码重构助手</role>
  <instruction>简化 OrderService 的条件分支，保持现有行为。</instruction>
  <constraints>不修改公共方法签名，不引入新的第三方依赖。</constraints>
</system_instructions>

<codebase_context>
  <file path="src/main/OrderService.java" language="java">
    <!-- 放入实际待修改代码；这里是位置示意 -->
  </file>
  <file path="src/main/DiscountStrategy.java" language="java">
    <!-- 放入依赖接口的实际定义 -->
  </file>
</codebase_context>
```

这些标签帮助表达语义边界，本身不是权限边界。应用仍需区分可信指令与外部材料，并处理标签冲突和转义。

### 4.2 三种输出控制方式

| 方式 | 作用 | 局限 |
| --- | --- | --- |
| 提示“只返回 JSON” | 表达格式期望 | 仍可能夹带解释或代码围栏 |
| 给出 Schema 与示例 | 说明字段、枚举、必填项 | 仅放进 Prompt 仍是软约束 |
| 受约束解码 + 程序校验 | 在生成端限制结构，并在接收端验证 | 支持范围取决于实现；仍需处理失败和语义错误 |

务必区分：**Pydantic 定义与校验数据；受约束解码限制生成过程。** 定义一个 Pydantic 类，并不会自动改变模型的采样机制。

课件的代码审查 DTO 包含以下字段：

| 字段 | 用途 | 应校验的内容 |
| --- | --- | --- |
| `file_path` | 问题所在文件 | 文件真实存在，且属于允许范围 |
| `line_number` | 问题所在行 | 正整数，并能定位到实际代码 |
| `severity` | 严重程度 | 必须属于约定枚举 |
| `rule_id` | 违反的规则 | 规则编号存在且适用 |
| `suggestion` | 修复建议 | 与实际问题相关且可执行 |
| `diff_patch` | 可选补丁 | 能应用，并通过相关验证 |

`Field(description=...)` 用于解释字段语义，不会自动完成这些业务检查。类型校验是否允许转换也需要明确配置，不能笼统认为字符串 `"42"` 一定会被整数类型拒绝。

### 4.3 校验与重试闭环

```text
模型输出
  → 解析 JSON
  → 校验字段、类型与取值
  → 校验文件、行号、补丁等业务条件
  → 合格：交给下游处理
  → 不合格：返回精简错误，有限次数重试
  → 仍失败：按约定降级或停止
```

**结构正确 ≠ 事实正确 ≠ 行为正确。** 即使审查报告符合 Schema，它指向的代码行仍可能不存在；即使补丁成功应用，也仍可能改变业务行为。

## 5. 上下文管理与提示注入防护

### 5.1 三类上下文管理策略

| 策略 | 做法 | 适用场景与代价 |
| --- | --- | --- |
| AST 骨架剪枝 | 保留类、接口、字段、函数签名和目标函数体 | 节省源码体积，但可能丢失理解行为所需的实现细节 |
| 分层语义摘要 | 将非核心模块压缩为职责、导出符号、依赖摘要 | 便于全局理解，但摘要可能失真或过期 |
| 滑动窗口 | 保留目标、关键状态与近期交互，淘汰无效历史 | 适合多轮任务，需避免遗漏已确认约束 |

稳定的 Prompt 前缀还可能有利于服务端缓存复用，但具体收益由服务实现和请求情况决定。压缩的目标是保留对当前任务有用的信息，而不是单纯追求最少 Token。

### 5.2 直接注入与间接注入

- **直接注入**：输入直接要求模型忽略规则、泄露信息或越权执行。
- **间接注入**：恶意指令藏在源码注释、PR 描述、Issue 或检索文档中，模型读取材料时受到干扰。

防护应分层实现：明确标记外部内容为数据；工具执行前校验参数与权限；限制可访问路径、网络和凭据；通过沙箱隔离实际执行；对超出授权范围的操作设置控制门槛。

XML 标签能帮助模型识别边界，但不能使系统“免疫注入”。真正的权限限制必须在模型之外执行。

### 5.3 综合案例：PR 总结生成器

课件将本模块组合为：

**读取 Diff 与 PR 信息 → 剪枝无关代码 → 标记不可信材料 → 生成结构化总结 → 校验 → 渲染报告。**

示例输出包含 `change_type`、`summary`、`impacted_modules` 和 `changelog_entry`。其中影响范围需要依赖分析或其他证据支持，不能仅凭函数名猜测；生成报告与实际发布报告也是两个不同操作。

## 6. 推理范式：怎样组织求解过程

### 6.1 总体比较

| 范式 | 核心机制 | 适合的问题 | 主要局限 |
| --- | --- | --- | --- |
| Direct / Zero-Shot | 不给示例，直接描述任务 | 简单、定义清楚的任务 | 私有知识不足时容易猜测 |
| Few-Shot | 提供输入—输出示例 | 私有 SDK、DSL、团队格式 | 示例占用上下文，错误示例会误导 |
| CoT | 将问题分解为中间步骤 | 算法、逻辑分析与复杂重构 | 中间步骤也可能出错 |
| Self-Consistency | 生成多条路径并聚合结果 | 可比较最终答案的任务 | 多路径成本更高，错误可能相关 |
| Least-to-Most | 先拆分，再按依赖由简入繁求解 | 多模块生成、复杂迁移 | 子任务接口和集成仍需验证 |
| ToT | 多分支生成、评估、剪枝与回溯 | 存在多种候选方案的任务 | 搜索成本和评分质量限制效果 |
| Self-Refine / Reflexion | 利用反馈修正，必要时保留经验 | 多轮代码修复 | 缺少有效反馈时可能反复犯错 |

这些方法可以组合，并非严格的版本替代关系。

### 6.2 Few-Shot 与 CoT

Few-Shot 的价值是通过示例表达难以简短描述的约定。示例选择应关注：与任务相关、覆盖边界、有代表性，并在使用反例时清楚标注错误原因。

课件中的 Few-Shot CoT 重构示例按以下步骤展开：

**识别代码问题 → 选择改造方案 → 检查边界情况 → 生成修改结果。**

实际交付可要求简洁的方案说明、关键依据与验证结果，无需把完整内部推理过程当成工具协议。说明与机器消费的代码、JSON 或工具参数应分离。

CoT 可理解为把部分计算分摊到更多生成步骤，属于 Test-Time Compute（推理时计算）的使用方式。但更多 Token 不必然提高正确率，复杂推理仍应与外部验证结合。

### 6.3 Self-Consistency：多路径采样

基本流程：对同一任务采样多条求解路径，比较或聚合最终答案。课件用以下目标表达对推理路径的边缘化：

$$
y^* = \arg\max_y \sum_r P(y,r\mid x)
$$

其中 $x$ 是输入，$r$ 是推理路径，$y$ 是答案。

代码有多种等价写法，不适合仅按字符串投票。课件进一步引入测试 Harness 来筛选候选：先编译和执行测试，再比较正确性、复杂度和维护成本。应区分“多数答案一致”与“候选通过测试”这两种选择依据。

### 6.4 Least-to-Most：按依赖递进

以带 TTL 的 LRU Cache 为例，可拆成数据结构、淘汰逻辑、过期策略、并发保护和集成验证等子任务。前序结果成为后续输入，每一步只携带必要的接口、约束和实现片段。

拆分后仍要检查整体不变量。例如，LRU 的读取可能更新访问顺序，不能仅因方法名为 `get` 就认为它不修改状态。

### 6.5 ToT：在方案树中搜索

ToT 包含四个要素：

1. **状态表示**：当前方案、已完成步骤和未解决约束。
2. **候选生成器**：产生可能的后续方案。
3. **评估器**：依据约束、测试或其他指标评价候选。
4. **搜索策略**：决定保留、剪枝、继续展开或回溯。

它引入了探索不同路线的能力，但有限搜索与启发式评分不能保证全局最优。架构方案的评分也必须建立在具体负载、约束和测量依据上。

### 6.6 Self-Refine 与 Reflexion

共同主线是 **生成 → 反馈 → 修正**。课件将其用于代码修复，并强调保存失败原因，避免重走相同错误路径；Reflexion 还特别强调跨尝试保留反思经验。

有效反馈包括编译错误、测试失败、静态分析发现及运行日志。反馈应保留足够定位问题的信息，并设置最大轮数、时间和成本预算。测试通过是重要证据，但不是所有输入下正确的证明。

课件第 25 页通过算法题展示不同方法的收益与成本。其具体通过率只能视为课件展示数据，不能脱离模型、题集、采样预算和测试条件进行泛化比较。

## 7. ReAct：将推理接入真实环境

### 7.1 Thought—Action—Observation

纯文本推理不能直接知道当前仓库、已安装依赖或实际测试结果。ReAct 将决策和工具交互交织：

- **Thought**：确定当前目标与下一步行动。
- **Action**：提出结构化工具调用。
- **Observation**：执行器返回真实结果，供下一步决策使用。

例如：定位报错文件 → 阅读相关实现 → 运行复现测试 → 修改最小补丁 → 再次验证。

**模型提出动作，执行器完成动作。** Observation 必须来自实际执行，不能由模型编造；工具输出也可能包含错误或不可信文本，应保留来源和执行状态。

### 7.2 四方执行关系

| 参与者 | 责任 |
| --- | --- |
| 用户 | 提供目标、输入与授权范围 |
| Controller | 保存任务状态，组装上下文，校验并调度工具，判断停止条件 |
| LLM | 基于当前信息提出方案、工具调用或最终答复 |
| Tool Executor | 在受控环境执行，返回结果、错误与退出状态 |

完整时序为：

```text
用户提交任务
  → Controller 组装任务、规则与工具定义
  → LLM 返回工具调用
  → Controller 校验工具名、参数、权限与预算
  → Executor 执行并返回结果
  → Controller 精简结果、更新状态并再次请求 LLM
  → 达到完成条件或预算上限后结束
```

任务历史和执行状态由 Controller 或外部状态系统维护，不能依赖模型自行“记住”。完成条件也应由可验证结果支持。

### 7.3 ReAct 与 Function Calling 的关系

| ReAct 概念 | 结构化工具调用中的对应项 |
| --- | --- |
| 可用动作说明 | 工具名称、描述和参数 Schema |
| Action | 工具调用请求与参数 |
| Observation | 与该调用标识关联的工具结果 |
| 循环控制 | 宿主程序更新消息和状态后继续请求 |

**ReAct 是组织决策与反馈的模式；Function Calling 是表达工具调用的接口机制。** 具备工具调用接口不等于已经实现完整 Agent，也不等于自动获得沙箱、权限或严格参数约束。

课件的文本协议采用“每轮一个动作”以简化流程。独立的读取任务可以并行；有依赖关系或共享状态副作用的动作，需要由调度器正确排序。

## 8. Agent 运行时的可靠性

### 8.1 四类常见失效

| 问题 | 表现 | 恢复与限制 |
| --- | --- | --- |
| 重复动作死循环 | 相同输入、相同结果反复出现 | 检查动作与环境状态，提示改变策略，限制总步数 |
| 参数或结构错误 | JSON 错误、缺少字段、未知工具 | 返回精简校验错误，有限次数重试 |
| 工具输出过长 | 日志挤占任务与规则上下文 | 保留错误上下文、退出码及关键尾部，原始日志另存 |
| 环境状态不一致 | 后台进程、锁、端口或文件状态残留 | 跟踪本任务资源，定向清理或恢复隔离环境 |

不能仅因动作参数相同就一律阻止重试：如果代码或环境已变化，再次运行同一测试是合理的。

课件中的广泛杀进程和恢复文件命令不应照搬到共享工作区。清理应只针对本任务创建的资源，并保护用户已有修改。

### 8.2 自动修复与重构案例

自动 Bug 修复的理想闭环是：

**报错证据 → 定位上下文 → 失败测试复现 → 最小补丁 → 修复测试通过 → 相关回归验证 → 提交可审查结果。**

重构与修 Bug 的测试基线不同：修 Bug 时，复现测试应在修改前失败；保持行为的重构，应先建立或确认通过的行为测试，再检查修改后仍然通过。

课件还强调公共 API 兼容性、依赖范围、单次改动大小和 Draft PR 审查。这些规则应由项目要求与实际授权决定，并落实到程序检查和开发流程。

### 8.3 Mini-Coding-Assistant 的核心与缺口

第 38 页示例展示了 Agent 的最小骨架：保存历史、调用模型、解析动作、分派工具、追加观察结果、达到上限后停止。

它适合学习控制流程，但示例仍省略了模型客户端、部分工具实现和多项运行时约束。工程实现至少需要补足：

- 对不同工具分别定义参数类型，限制允许的工具名与路径。
- 保持工具声明和实际参数一致；课件示例中 `test_path` 与 `path` 的命名并不一致。
- 设置执行超时，记录 `stdout`、`stderr` 和退出码。
- 使用真实的执行隔离；普通 `subprocess.run` 本身不是沙箱。
- 根据验证证据判断完成，不能仅检测到 `final_answer` 标签就认定成功。

## 9. 项目规则、Prompt Eval 与持续改进

### 9.1 规则分层与按需加载

课件提出公司级规则、仓库级规则和模块级规则的分层思路，并用路径匹配控制装载范围。这样能减少无关规范占据上下文，也有利于定位冲突。

好的规则应明确适用范围、具体动作或禁止事项、必要示例和验证方式，并纳入版本管理。`.cursorrules`、`CLAUDE.md` 等是课件中的规则载体示例，实际加载和优先级由对应工具决定；文件名本身不会赋予规则最高权限。

第 33 页还用三个侧重点理解编程助手：FIM 利用光标前后代码进行补全；仓库检索为多文件任务构建上下文；工具循环使系统能够读写、测试并修正。应将这些视为架构模式，而非对特定产品当前实现的完整描述。

### 9.2 评测要同时看正确性与成本

| 指标 | 回答的问题 |
| --- | --- |
| 格式与参数校验通过率 | 能否可靠接入程序？ |
| 编译、测试与任务成功率 | 是否完成了预期行为？ |
| 无关修改、权限与规则违规情况 | 是否在约定范围内行动？ |
| Token、耗时、工具调用与重试次数 | 成本是否可接受？ |
| 人工或模型辅助评审 | 可读性、可维护性等软指标如何？ |

**Pass@1** 关注一次候选生成通过测试的表现；**Pass@k** 关注多个候选中至少一个通过的表现。后者不等于系统能够自动选出正确候选，也不能在忽略额外预算的情况下与 Pass@1 直接比较。

LLM-as-a-Judge 可辅助评价可读性和改动合理性，但不能代替测试，也不应被视为无偏裁判。文本相似度同样不足以判断代码是否正确。

### 9.3 Prompt 迭代闭环

1. 从历史缺陷、PR 和典型需求中建立脱敏评测集，覆盖正常、边界和异常情况。
2. 固定模型配置、环境、工具权限和预算，比较不同 Prompt。
3. 将 Prompt 变更纳入版本管理，执行回归评测，检查是否解决一个问题却引入其他退化。
4. 记录线上失败的调用、状态和结果，把新发现补入后续评测。

课件给出的通过率阈值、评测集规模和循环次数都属于示例参数，应根据任务风险与成本确定。

## 10. 复习要点与自测

### 10.1 常见误区

| 误区 | 更准确的理解 |
| --- | --- |
| Prompt 越长越好 | 相关性、信息位置与清晰边界更重要 |
| 加 XML 就能防住注入 | XML 辅助分区，权限与执行隔离需要程序保障 |
| JSON 合法就说明答案正确 | 格式、事实和业务行为要分别验证 |
| Pydantic 自动强制模型输出合法内容 | 它负责定义与校验；生成约束需要额外机制 |
| 低温度可以杜绝幻觉 | 它减少随机性，不能弥补事实缺失 |
| 让模型反思就会修好 | 外部反馈、状态管理和退出条件同样关键 |
| 测试通过就没有任何 Bug | 测试提供有限覆盖下的证据 |
| Function Calling 就是完整 Agent | 还需要状态、调度、权限、执行与评测 |

### 10.2 自测问题

1. Role、Instruction 和 Constraints 分别解决什么问题？
2. 上下文污染如何形成？哪些历史应删除，哪些事实应保留？
3. JSON Schema、Pydantic 和受约束解码分别位于哪个环节？
4. AST 剪枝节省了什么，又可能损失什么？
5. Self-Consistency、Least-to-Most 和 ToT 分别怎样使用额外计算？
6. ReAct 中谁产生调用意图、谁执行动作、谁保存状态？
7. 为什么不能让模型自行生成 Observation，或自行宣布测试通过？
8. 如何判断 Prompt 改动确实改善了任务成功率，而不只是增加了成本？

## 11. 与后续 MCP 课程的联系

本讲重点是任务、上下文、输出和工具反馈如何组成可控循环。后续 MCP 课程进一步讨论外部能力怎样标准化接入。

课件预告的三个概念是 **Resources（上下文资源）**、**Tools（可调用工具）** 和 **Prompts（可复用提示模板）**。学习时应区分：指令工程关注任务表达，ReAct 关注决策与行动循环，MCP 关注接入协议；它们分别承担不同职责。
