防御性架构思维

Prompt 设计中的“防御性编程”思维

把传统软件工程的 前置断言、后置校验 与 降级机制 映射入 Prompt 契约，彻底遏制非确定性系统崩溃

Principle 01

前置条件校验 (Pre-conditions)

要求模型在推理前显式断言上下文完整度。当输入缺乏关键代码、环境变量或类型定义时，拒绝盲目推演。

// Prompt 前置逻辑
IF context.code_snippet IS EMPTY:
RETURN "ERROR_MISSING_INPUT"
拦截垃圾输入与提示词注入
Principle 02

后置条件与强 Schema 契约

通过语法与结构约束（JSON Schema / Pydantic）强制验证模型输出。违规输出直接被 Guardrail 拦截重试。

// 输出强类型契约
Must match: CodeReviewSchema
Strict mode: JSON syntax validate
防止返回客套话与非法格式
Principle 03

降级容错机制 (Fallback Rules)

为概率模型定义“安全出口”。当置信度低或无法确定答案时，返回统一规范的标准 Error Code 而非凭空“瞎编”。

// 安全降级逻辑
IF confidence < 0.8:
RETURN {"status": "UNSURE", ...}
消除幻觉给下游系统带来的毒化
Industrial Defensive Prompt Pattern / 工业级防御提示词范例 System Contract Block

<defensive_rules>

1. [Pre-condition] 检查 <input_code> 是否包含完整函数定义。若不完整，直接抛出 ERR_INCOMPLETE_CODE。

2. [Constraint] 严禁擅自修改类名或新增第三方未引用的 package。

3. [Fallback] 如果涉及你不确定的 API（如私有 SDK），设置 confidence_score < 0.7 并列出疑似依赖。

</defensive_rules>

Architectural Takeaway / 架构小结

永远不要假设 LLM 会“默契地理解”极端情况。防御性 Prompt 的核心要求是：显式声明边界、明确拦截异常、规范降级输出。
