Least-to-Most Prompting：由简入繁的任务分解

剖析 Zhou et al. (2022) 范式：解决传统 CoT 在超长算法链条中的 注意力漂移 (Attention Drift)，通过 解构（Decompose） 与 拓扑求解（Sequential Solving） 实现大块代码无痛生成

Least-to-Most Execution Pipeline (Zhou et al.) 2-Stage Subproblem Loop
STAGE 1: Task Decomposition Prompt Prompt 1
// Task: 实现带 TTL 过期与读写锁的高并发 LRU Cache
Decomposed Subtasks:
1. 设计 Node 双向链表与 Expiry Timestamp 属性
2. 实现并发安全读写锁 (ReentrantReadWriteLock)
3. 实现清理惰性淘汰 (Lazy Eviction) 与后台定时线程
STAGE 2: Sequential Solving Loop Prompt 2..N
[Subtask 1 Output] -> Node & DoublyLinkedList Impl
[Subtask 2 Output] -> Append Lock Protection to Subtask 1
[Subtask 3 Final] -> Integrate TTL Thread + Pass Unit Tests
前序子问题 Output 成为后续推理输入 完美攻克 Context 漂移
克服传统 CoT 的注意力遗忘 Core Value

当代码生成任务超过 200 行时，传统 CoT 一吐到底会导致中间逻辑丢失。Least-to-Most 将巨型 Task 拆解为多个独立 API 调用的上下文小块，消除概率漂移。

拓扑依赖按需串联 (Topological Sorting) Mechanism

解构阶段（Decomposition）强行要求模型输出子任务的依赖顺序（如：先建 DTO 类，再建 DAO 接口，最后写 Service 校验），符合人类软件工程师的真实编码习惯。

与 Unit Test Harness 无缝闭环 Engineering

每个子问题求解后，可交由沙箱跑一次单测，若 Subtask 2 失败则立即重试，防止错误积累至最终全量代码。

01

解构 Prompt 强契约

Stage 1 必须要求 LLM 输出格式化子任务清单，以便 Python/Node.js 调度器通过正则或 JSON 提取子任务列表。

02

上下文滑动控制

随着求解推进，前序子任务只保留“精简签名与关键代码”，避免 Context Window 爆炸。

03

面向大型架构迁移

最适合将大型旧系统（如 Monolith 到 Microservice）按模块依次平滑重构。

Architectural Design Rule / 架构分治法则

Least-to-Most Prompting 是软件工程“分而治之 (Divide and Conquer)”在 Prompt 领域的经典映射；把复杂系统降解为依赖递进的子问题图谱，是保障长代码可运行率的关键。
