物理闭环: Trace $\to$ TDD Reproduce $\to$ Patch $\to$ Pass 零人工干预修复
TDD 驱动复现 (Red-to-Green Loop) TDD Principle

生产级 Bug 修复 Agent 决不能直接修改主干代码。必须要求 Agent 先写一段能够触发崩溃的复现单测（Red Test），修正代码后再验证单测变绿（Green Pass）。

最小化改动范围 (Minimal Patch Constraint) Patch Scope

限制 Agent 只能修改引起 Bug 的特定函数或文件（Line Range Limit），严禁其对不相关的周边代码进行顺手“大重构”，防止引发次生故障（Regression）。

Human-in-the-Loop (HITL) 人工卡扣 Safety Gate

Agent 修复完成后只能发起 Draft PR，绝对禁止直推 `main` 分支。由人类高级工程师结合 CI 跑全量回归测试后再批准 Merge。

01

只信任真实测试反馈

LLM 嘴上说“我已经修复好了”不可信，只有物理沙箱抛出的 `BUILD SUCCESS` 才能作为终止 Token。

02

防范无限修改死循环

修了 A 引发 B，修了 B 引发 A。必须在 Controller 中设置 `Max Patch Retries = 3` 熔断阀门。

03

自动补全回归测试套件

每一次自动修复不仅解决了当前的 Bug，其产生的复现单测还为代码库沉淀了永久的回归测试资产。

Architectural Auto-Fix Rule / 工业级修复法则

基于 ReAct 的自动 Bug 修复系统的灵魂在于“TDD 复现断言 + 隔离沙箱实测 + 最小 Patch 限制”；将物理环境测试结果作为绝对事实（Observation），才能构建可信的代码修补流水线。

🎯 剖析工业级 Bug 修复 Agent 的核心（SWE-bench 范式）： “向学员强调：很多企业做 Agent Bug 修复，直接把崩溃堆栈传给 LLM 让它吐一段修改好的代码，这种做法在生产环境极度危险！工业级的 SWE-Agent 必须引入 **TDD（测试驱动开发）闭环**：先让 Agent 写一个能稳定引发这个 Bug 的测试用例（Red Test），接着改代码，最后在沙箱里跑 Maven/Pytest 确保测试变绿（Green Pass）。”
💡 讲授边界控制与防越权卡扣： “向学员提醒：一定要严格限制 Agent 修改代码的行数和文件范围（Minimal Patch）。如果不加限制，模型可能会修改配置、甚至删掉报错的方法，导致生产严重的二次次生故障。”
