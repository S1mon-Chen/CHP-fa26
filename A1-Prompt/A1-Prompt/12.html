实战：使用 Pydantic 定义代码审查结构化契约

从 Pydantic 契约模型 到 ValidationError 自动重试闭环，实现直接注入 GitHub PR / GitLab CI/CD 的生产级代码审查器

Production-Grade Pydantic DTO Schema Field Validation Active
from enum import Enum
from pydantic import BaseModel, Field, field_validator
from typing import List, Optional

class SeverityLevel(str, Enum):
CRITICAL = "CRITICAL" # 严重问题，卡死 Build
WARNING = "WARNING" # 性能或规范警告
INFO = "INFO" # 建议优化项

class CodeIssue(BaseModel):
file_path: str = Field(description="相对项目根目录的文件路径")
line_number: int = Field(description="产生 Bug 或不规范的代码精确行号")
severity: SeverityLevel
rule_id: str = Field(description="违背的规则编号, 如 SEC-001")
suggestion: str = Field(description="具体且可落地的修复指导")
diff_patch: Optional[str] = Field(default=None, description="建议修改的 Unified Diff 片段")
Field description 作为语义锚点给 LLM 提示 原生支持 Json Schema 导出
ValidationError 自动容错重试机制 Instructor / Retry

当 LLM 返回非预期格式（例如 `line_number` 填了字符串 `"42"`），Pydantic 校验抛出异常，捕获堆栈并自动发起 2nd-turn 修复：

// Exception Caught -> Auto Prompt Injection
"Validation Error in `line_number`: value is not a valid integer. Please fix this field and return JSON again."
GitHub / GitLab Inline Comment 直连 Zero Parser Logic

反序列化后的 `CodeReviewReport` 实例拥有 100% 类型保护，可直接映射为 GitHub REST API 属性，零正则表达式解析：

gh_api.create_review_comment(
path=issue.file_path, line=issue.line_number,
body=f"[{issue.severity}] {issue.suggestion}"
)

Architectural Takeaway / 架构师原则

Pydantic 模型不仅是 Python 的验证类，更是将大模型转变为标准强类型 RPC 微服务的核心契约文件。所有输入与输出字段都必须拥有显式的 `Field(description=...)` 描述以引导 Sampling。

Speaker Notes / 讲师讲稿
🎯 强调 `Field(description=...)` 的双重作用： “向学员说明：Pydantic 的 `description` 属性不仅是代码注释，在生成 JSON Schema 传递给 LLM 时，它会作为 API Schema 的文档直接注入 Prompt，是引导 LLM 正确理解数据语义的最佳位置。”
💡 讲解自动重试闭环（Retry Loop）： “在生产工程中，即使偶发格式报错也不要紧。使用 Instructor 或 Pydantic 校验捕获 `ValidationError`，把报错的 Traceback 拼接入第 2 轮对话重新请求，模型 100% 能够在第 2 轮修正过来。”
