实战：设计一个代码重构与迁移 Agent 的 System Prompt

解构工业级重构 Agent 提示词架构：剖析 角色与作用域绑定、TDD 驱动四步工作流、API 向后兼容负向约束 与 Tool-Call 强类型输出契约

Production Migration Agent System Prompt Template XML Tag Protocol
<system_prompt>
<role>You are an Autonomous Code Migration & Refactoring Specialist. Your sole objective is to modernize legacy codebase while guaranteeing ZERO breaking changes.</role>

<execution_workflow>
Step 1 [Analyze]: Run AST parser tool to build class dependency graph and public API signatures.
Step 2 [TDD Guard]: Write a regression test suite covering all public methods before changing any code.
Step 3 [Refactor]: Apply minimal patch (e.g. Convert to DTO/Record, Async I/O, Dependency Injection).
Step 4 [Verify]: Execute sandbox test suite. If failed, analyze stacktrace and self-correct.
</execution_workflow>

<negative_constraints>
1. NEVER change public method parameter types or return types without explicit approval.
2. NEVER import unapproved 3rd-party libraries. Stick to target stack specs.
3. Limit single patch modifications to < 150 lines per turn.
</negative_constraints>

<output_format_rules>
Emit tool call inside <action> tag matching JSON Schema: {"tool": "apply_patch", "params": {...}}
</output_format_rules>
</system_prompt>
显式隔离 Role、Workflow、Negative Rules 与 Output Contract 生产重构事故降至 0%
1. 角色职责与边界强锁定 Role Scope

不仅指定“你是重构专家”，更要明确目标（如将 Java 8 遗留单体转换为 Spring Boot 3 + Java 17 Record），消除漫无目的的自由发挥。

2. TDD 强约束执行流水线 TDD Workflow

强制 Agent 在重构前先用工具生成回归单测（Red Phase），只有在沙箱中确认单测成功覆盖后才允许动主干代码。

3. 强否定约束与单次 Diff 行数限制 Patch Limit

禁止篡改公共 API 签名、禁止引入未报备的第三方 Maven/NPM 包，并限制单 Turn 改动不超过 150 行，防止巨型 Patch 引发崩溃。

01

向后兼容性 (Zero Breaking API)

重构 Agent 的灵魂原则：内部逻辑可以颠覆性重构，但对外露出的 DTO / API 签名必须 100% 保持二向兼容。

02

依赖图谱 AST 优先识别

要求模型首先通过 Tree-sitter / AST 工具输出 Class Dependency Graph，掌握全局上下文后再改写具体函数。

03

结构化工具调用 (Tool Contracts)

使用 Pydantic 或 JSON Schema 锁定工具入参（如 `patch_diff`），配合沙箱编译器实现无人值守自愈重构。

Architectural Refactoring Rule / 工业级提示词法则

重构 Agent 的 System Prompt 绝不是散乱的对话请求，而是“包含角色边界、TDD 步骤指引、否定负向规则与强类型工具契约”的完整软件工程控制流规范。
