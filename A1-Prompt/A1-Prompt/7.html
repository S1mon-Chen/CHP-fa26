综合运用 防御性编程、前置条件断言 与 降级机制，解决真实场景中的慢 SQL 诊断与上下文缺失问题

演练题目 / Task

实战场景：缺失上下文的慢 SQL 诊断请求

用户仅提交了一段 SQL 请求优化，但未提供数据库类型、索引信息和数据规模：

// 用户原始提问
"帮忙优化这条 SQL：
SELECT * FROM orders o
JOIN users u ON o.user_id = u.id
WHERE DATE(o.created_at) = '2026-08-01'
AND o.status = 'PAID';"
传统 Prompt 隐患：

若无防御性约束，模型会凭空虚构索引（如建议建 idx_created_at），忽略 DATE() 函数会导致索引失效的死穴。

目标：编写防御性 Prompt 避免幻觉，强制拦截无效参数。
参考答案与防御 Prompt / Solution
// 架构师设计：防御性 SQL 审查 Prompt 模板

<system_instructions>

1. [Pre-condition] 检查是否包含 db_engine, table_schema, existing_indexes。

2. [Fallback Rule] 若缺失上述任意项，拒绝假设索引，返回 status="MISSING_CONTEXT" 并列出所需补全项。

3. [Static Analysis] 检查是否存在表达式导致索引失效（如 DATE(col)）。若存在，优先指出隐式转换风险。

</system_instructions>

预期防御性模型输出 (Structured JSON) Guardrail Passed

{

"status": "MISSING_CONTEXT",

"critical_anti_pattern_detected": "WHERE DATE(o.created_at) 函数计算导致索引失效",

"required_inputs": ["db_engine (e.g. MySQL 8.0/PG)", "existing_indexes on orders table"],

"range_query_refactor_recommendation": "o.created_at >= '2026-08-01 00:00:00' AND o.created_at < '2026-08-02 00:00:00'"

}

总结：通过防御性 Prompt，成功将“胡乱编造”拦截为“精确诊断与范围改写建议”。

Module 1 Recap / 模块一核心要义

提示词不是文字游戏，而是控制概率 CPU 行为的强契约。永远记住：前置断言拦截垃圾输入，尾部重申锁定注意力，结构化 Schema 接入自动化系统。
