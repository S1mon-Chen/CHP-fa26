Saga Pattern for Distributed Microservices, Choreography vs. Orchestration, Forward Actions ($T_i$) & Compensating Actions ($C_i$)

Saga 事务链路：正向动作 ($T_i$) 与逆向补偿 ($C_i$) 故障回滚流 ($T_1 \to T_2 \to \text{Fail}(T_3) \to C_2 \to C_1$) BASE Eventual Consistency via Kafka Event Topics
1. Order Service ($T_1$) Success
正向: $T_1$: CreatePendingOrder
补偿: $C_1$: CancelOrder
2. Payment Service ($T_2$) Success
正向: $T_2$: DeductUserBalance
补偿: $C_2$: RefundUserBalance
3. Inventory Service ($T_3$) Failed!
正向: $T_3$: LockStock (Out of Stock!)
结果: 抛出 InventoryFailedEvent
4. 逆向补偿链路 Rollback
依次广播执行 $C_2 \to C_1$
完成分布式系统最终一致性状态恢复
1. Saga 模式原理与两大拓扑架构 (Choreography vs. Orchestration) Saga Core

弃用 2PC/XA：将大事务拆解为有序本地子事务序列 No Locking 2PC

微服务架构中，2PC 跨服务强锁严重损害可用性。Saga 将长事务拆分为多个本地子事务 $T_1, T_2, \dots, T_n$。每个子事务独立提交 ACID 事务并向 Kafka 抛出事件。

舞蹈模式 (Choreography) vs. 编排模式 (Orchestration) Topologies

• **Choreography (舞蹈模式)**：无中心点！服务通过监听 Kafka 领域事件自发触发下一步或补偿。
• **Orchestration (编排模式)**：由中央 Saga Orchestrator 状态机驱动命令 Topic，统一指挥调度。

正向动作 $T_i$ 与逆向补偿 $C_i$ 的幂等性要求 Idempotent $C_i$

每一个正向动作 $T_i$ 必须配备对应的撤销/回滚补偿动作 $C_i$（如 $T_i$: 扣款 $\to C_i$: 退款）。**补偿动作 $C_i$ 必须保证 100% 幂等且绝不失败**。

Saga 黄金法则：放弃 ACID 中的隔离性 (Isolation)，获得极限吞吐与 BASE 最终一致性
2. 基于 Kafka 的 Saga 编排器逻辑 (`OrderSagaOrchestrator.java`) Spring Boot & Kafka
// Saga 编排器状态机处理 (`OrderSagaOrchestrator.java`)
@Component
public class OrderSagaOrchestrator {
@Autowired private KafkaTemplate<String, Object> kafkaTemplate;
// A. 步骤 2 扣款成功，向 Kafka 发送库存扣减指令
@KafkaListener(topics = "payment-events", groupId = "saga-group")
public void onPaymentEvent(PaymentEvent event) {
if ("SUCCESS".equals(event.getStatus())) {
kafkaTemplate.send("inventory-commands", new LockStockCommand(event.getSagaId()));
} else {
// 扣款失败，触发 C1 补偿撤销订单
kafkaTemplate.send("order-commands", new CancelOrderCommand(event.getSagaId()));
}
}
// B. 步骤 3 库存扣减失败，触发 C2 逆向退款补偿与 C1 撤单
@KafkaListener(topics = "inventory-events", groupId = "saga-group")
public void onInventoryEvent(InventoryEvent event) {
if ("FAILED".equals(event.getStatus())) {
// 触发 C2 补偿: 异步发退款指令
kafkaTemplate.send("payment-commands", new RefundPaymentCommand(event.getSagaId()));
// 触发 C1 补偿: 异步发撤单指令
kafkaTemplate.send("order-commands", new CancelOrderCommand(event.getSagaId()));
}
}
}

核心架构启发 (Saga Distributed Transaction Insight)

Saga 模式代表了微服务长事务的工业解法。通过将**全局大事务降维拆解为单服务本地 ACID 事务链**，并配合 Kafka 事件驱动的**正向驱动 ($T_i$) 与逆向幂等补偿 ($C_i$)**，成功打破了 2PC 的性能枷锁，实现了兼具高吞吐与最终一致性的柔性事务机制。

🎯 引导学生透视 Saga 模式对 2PC 枷锁的解耦： “向学员强调：在微服务环境下，跨服务的两阶段提交 (2PC) 或 XA 全局锁会导致服务吞吐暴跌甚至引发死锁。Saga 模式将跨服务长事务拆分为多个本地子事务 $T_1, T_2, T_3$，各自在本地数据库提交。一旦某个子事务失败（如库存不足），则通过 Kafka 事件驱动按逆向顺序依次触发补偿操作 $C_2, C_1$ 来实现最终一致性。”
