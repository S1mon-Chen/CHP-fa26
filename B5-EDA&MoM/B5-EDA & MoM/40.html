思考与研讨题 (Thought-Provoking Discussion Topics) 4 Q&A Topics
Q1: 为何 2PC 强锁无法应对微服务扩展？Saga 与 Outbox+CDC 如何破局？ Consistency

**提示**：对比 2PC 跨服务持锁导致的死锁风险与吞吐雪崩；剖析 Transactional Outbox + CDC 如何把双写转化为本地 ACID 事务，以及 Saga 如何通过正向 $T_i$ 与逆向 $C_i$ 幂等补偿实现 BASE 最终一致性。

Q2: Kafka 追加日志与零拷贝能达百万 QPS，为何不适合微秒级高频交易？ Batch vs. Latency

**提示**：分析 Kafka 榨干物理网卡的核心来源于 `batch.size` 与 `linger.ms` 的微批打包，这必然拉长毫秒级等待延时。高频交易（HFT）追求 <1ms 单条推流，必须选型 RabbitMQ 式的逐条即时推送。

Q3: 发生 Rebalance 或网络抖动时，为何消费端强制幂等是防丢防重唯一解？ At-Least-Once

**提示**：物理网络的不确定性决定了 Broker 只能做到“至少一次 (At-Least-Once)”传递。剖析为何端到端“精确一次”必须依赖消费端使用 Redis `SETNX` 状态锁与数据库唯一约束去重表。

Q4: CQRS 与 Event Sourcing 如何配合？如何应对读视图最终一致性延迟？ CQRS & ES

**提示**：剖析 Event Sourcing 为 CQRS 写入侧提供不可变事件源，通过投影引擎更新 ES 读视图；分析前端通过客户端预渲染或乐观 UI 更新解决“刚提交写操作却查不到”的延时体验。

研讨要领：结合物理硬件限制、分布式理论 (CAP/BASE) 与实际业务场景做架构权衡
