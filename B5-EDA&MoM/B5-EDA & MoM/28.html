1. “至少一次”下的幂等必要性与 3 大去重模式 Idempotency Patterns

为什么消费端必须做幂等防重？ At-Least-Once Delivery

Kafka 的默认保证是“至少一次 (At-Least-Once)”。Producer 重试、网络超时、Consumer 宕机或集群 Rebalance 均会导致完全相同的消息被重复投递。若没有幂等设计，会导致重复扣款、重复发货等严重资损事故。

模式 A：数据库唯一主键 / 唯一索引 (Unique Index) DB Constraint

将业务唯一标识（如 order_id 或 tx_id）设为数据库表的唯一主键。重复消息触发插入时会抛出 DuplicateKeyException，捕获该异常直接 Ack 即可。

模式 B：Redis `SETNX` 状态锁与高并发过滤 Redis SETNX

在处理前执行 redis.setIfAbsent(key, "PROCESSING", expire)。若返回 false 说明已被处理；处理成功后更新状态为 "DONE"，能抗住数万 QPS 的高并发重复冲击。

模式 C：本地事务去重表 (De-duplication Table) Local Transaction

在同一数据库本地事务中，同时执行“业务数据更新”与“向去重表插入流水记录”。由于属于同一个本地 ACID 事务，去重表写入成功即保障了业务落盘的原子性。

黄金法则：将“至少一次”消息传递与“消费端幂等”结合，等价于端到端“精确一次”
2. 生产级 Redis + 本地事务幂等消费者 (`IdempotentConsumerService.java`) Spring Boot 3
// 幂等防重消费者实现 (`IdempotentConsumerService.java`)
@Component
@Slf4log
public class IdempotentConsumerService {
@Autowired private StringRedisTemplate redisTemplate;
@Autowired private OrderService orderService;
@KafkaListener(topics = "order-payment-events", groupId = "payment-group")
public void onPaymentEvent(PaymentEvent event, Acknowledgment ack) {
String lockKey = "lock:tx:" + event.getTxId();
// 1. Redis SETNX 原子争抢状态锁（有效期 10 分钟防止死锁）
Boolean isNew = redisTemplate.opsForValue()
.setIfAbsent(lockKey, "PROCESSING", 10, TimeUnit.MINUTES);
if (Boolean.FALSE.equals(isNew)) {
log.info("Duplicate event [{}] detected, skipping.", event.getTxId());
ack.acknowledge(); // 已处理或正在处理，直接提交 Offset
return;
}
try {
// 2. 执行本地事务：更新业务表 + 插入去重记录
orderService.processPaymentInTransaction(event);
// 3. 处理成功更新 Redis 标记为 DONE，并显示提交 Offset
redisTemplate.opsForValue().set(lockKey, "DONE", 24, TimeUnit.HOURS);
ack.acknowledge();
} catch (Exception ex) {
redisTemplate.delete(lockKey); // 发生可重试异常解锁
throw ex; // 抛出异常触发 DefaultErrorHandler 重试
}
}
}
