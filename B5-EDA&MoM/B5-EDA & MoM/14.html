1. Kafka Record 物理 4 大核心组成要素 Record Fields

Headers（标头元数据）：应用级键值对 Lightweight Metadata

允许在不反序列化整个大 Payload（Value）的情况下，直接读取轻量元数据（如分布式链路追踪 `trace_id`、Schema 格式版本 `schema_version`、消息类型路由标记）。

Key 与 Value（键值对）：纯二进制 byte[] byte[] Payloads

Kafka 本身不感知数据 Schema，Key 与 Value 在网络传输与磁盘持久化时均表现为原始 **`byte[]` 字节数组**。配合 Serializer/Deserializer（如 String, JSON, Avro, Protobuf）完成反序列化。

Timestamp（时间戳）：CreateTime vs LogAppendTime Time Semantics

每个 Record 均带有毫秒级时间戳。可配置为客户端生成时间 CreateTime（默认，用于流计算窗口对齐），或 Broker 追加写盘时间 LogAppendTime。

模式灵活：支持非结构化 JSON 到强类型 Avro/Protobuf 契约演进
2. Partitioner 哈希路由算法与 Key 锁定性 Partitioner Mechanics

指定 Key 时的 MurmurHash2 哈希路由 Key Hash Router

当 ProducerRecord 包含 Key 时，默认分片器使用 MurmurHash2 算法计算 Key 哈希：

$$\text{Partition} = \text{Utils.toPositive}(\text{MurmurHash2}(key)) \pmod{\text{NumPartitions}}$$

$\implies$ **保证同一实体（如 `order_1001`）的所有事件必定发往同一个 Partition**。

Key 为 Null 时的粘性分区 (Sticky Partitioning) High-Throughput Batching

当 Key 为 `null` 时，现代 Kafka Partitioner 采用**粘性分区策略**：将连续多条消息尽可能打包发送到同一个 Partition 批次中，直至达到 `batch.size` 或 `linger.ms` 限制，大幅提升网络打包吞吐量，随后再平滑轮询下一个 Partition。

自定义 Partitioner 插件化扩展 Partitioner Interface

业务可以实现 org.apache.kafka.clients.producer.Partitioner 接口，自定义特定的路由倾斜逻辑（例如将 VIP 客户优先发往性能更高的独立 Partition）。

核心架构启发 (Key-Value Design Insight)

Kafka Record 的 Key 绝不仅仅是一个主键文本——它是**决定事件数据在集群物理磁盘上分布与消费顺序**的绝对核心。合理设计 Message Key，是构建分布式高并发、强顺序保证系统的第一步。
