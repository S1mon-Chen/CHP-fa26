1. 实时流计算原理与流表对偶性 (Stream-Table Duality) Stream vs. Table

批处理 (Batch) vs. 实时流处理 (Stream Processing) Low Latency

传统批处理（如 Spark/Hadoop）按定时天/小时调度有界数据集，延迟极高。流计算针对**无界连续事件流**（Unbounded Stream），实现毫秒级的逐条增量计算与 ETL 转换。

流表对偶性 (Stream-Table Duality: $KStream \leftrightarrow KTable$) Duality

• **KStream (日志/流)**：包含完整历史的变更记录流（Insert/Update 事件）。
• **KTable (数据库表/快照)**：KStream 的最新状态聚合快照（按 Key 只保留最新的最新表述）。两者可自由互相转换！

Event Time 时间语义与水位线 (Watermarks) 机制 Out-of-Order Handling

区分**事件发生时间 (Event Time)** 与**进入系统处理时间 (Processing Time)**。借助 Watermark 水位线机制处理网络乱序到达与延迟迟到事件。

黄金定律：数据不是静态存盘后才被查询，而是在流动过程中被实时计算
2. Kafka Streams Java 代码实战与 Flink 选型矩阵 Kafka Streams DSL
// Kafka Streams 实时滑动窗口聚合 (`OrderStreamTopology.java`)
StreamsBuilder builder = new StreamsBuilder();
KStream<String, OrderEvent> orders = builder.stream("order-events");
// 按用户 ID 分组，按 5 分钟滚动窗口计算累计消费金额
KTable<Windowed<String>, Double> totalSpend = orders
.selectKey((k, v) -> v.getUserId())
.groupByKey()
.windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
.aggregate(
() -> 0.0, // 初始化累加器
(userId, event, aggregate) -> aggregate + event.getAmount(),
Materialized.<String, Double, WindowStore<Bytes, byte[]>>as("spend-store")
);
totalSpend.toStream().to("aggregated-spend-topic"); // 输出回下游 Topic

核心架构启发 (Stream Processing Insight)

实时流计算代表了从**“被动数据库存储检索”**向**“主动事件流式计算”**的范式飞跃。轻量级的 Kafka Streams 适合直接嵌入 Spring Boot 微服务处理轻量级 ETL，而重型的 Apache Flink 则是海量数据实时数仓与复杂事件处理 (CEP) 的不二之选。

Speaker Notes / 讲师讲稿
🎯 引导学生透视流表对偶性 (KStream vs. KTable)： “向学员强调：理解流计算的关键在于‘流表对偶性’。KStream 是包含所有历史修改的变更事件流，而 KTable 是按 Key 聚合后的最新数据状态表。我们可以用 KStream 记录用户的每一次消费事件，用 KTable 维护用户的当前总余额。”
💡 剖析 Kafka Streams 与 Flink 的选型考量： “请学员关注右侧的选型对比：如果只是在已有的 Spring Boot 微服务里做轻量级的数据清洗（如过滤非法字符、按窗口滑动求和），直接使用嵌入式的 Kafka Streams Jar 包即可，无需部署额外的集群；如果需要面对千万级 TPS 实时数仓或复杂 CEP 规则，则推荐选型 Apache Flink。”
