Bank Transfer Event Pipeline, Exponential Backoff (`@RetryableTopic`), Dead Letter Topic (`@DltHandler`) & Redis `SETNX` Idempotency

银行转账金融管线：幂等校验、指数重试与死信告警 (Bank Transfer Pipeline) @RetryableTopic + Redis Idempotency + DLT
1. Redis 幂等防重校验
SETNX tx_id "PROCESSING"
若已消费或正在处理中，自动判定重复并丢弃，防止重复扣款
2. 账户结算与转账逻辑
processTransfer(event)
原子化更新账户余额并写账单明细，成功后手动提交 Offset
3. 指数退避重试 (Retry Topic)
bank-transfers-retry-1000
遇到网络抖动等瞬时异常，延迟重试（延时 1s, 2s, 4s...）
4. 死信队列 (DLQ) & 人工审计
bank-transfers-dlt
非重试异常或达到重试上限，入库死信表并触发钉钉/邮件告警
1. 金融级消费端防重与死信容错三原则 Banking Robustness

消费端幂等防重 (Consumer Idempotency) Redis SETNX

由于 Kafka 保证的是“At-Least-Once”传输，网络抖动重试或 Rebalance 会导致重复投递。消费端必须在处理前使用 tx_id 进行 Redis 分布式锁/去重表校验，确保多次消费结果一致。

异常精确分类与非阻断重试 (`@RetryableTopic`) Exception Classification

区分**可重试异常**（如 DB 网络抖动、三方 HTTP 超时）与**不可重试异常**（如余额不足、账号不存在）。通过开辟独立的重试 Topic，避免坏消息卡死主 Partition 阻塞其他用户。

死信队列 (`.DLT`) 与人工补偿兜底 @DltHandler

达到最大重试次数后，Spring Kafka 会将消息路由至 Dead Letter Topic。通过标注 @DltHandler，将问题交易打入人工审计数据库并触发实时告警。

金融防线：消息可重试、坏数据不卡死、死信可追溯、消费必幂等
2. 银行转账消费端代码 (`BankTransferConsumer.java`) Spring Boot 3
// 转账消费者与 DLQ 处理器 (`BankTransferConsumer.java`)
@Component
@Slf4j
public class BankTransferConsumer {
// 配置自动重试 3 次，指数退避 (1s, 2s)
@RetryableTopic(attempts = "3",
backoff = @Backoff(delay = 1000, multiplier = 2.0),
exclude = {AccountNotFoundException.class}) // 排除不可重试异常
@KafkaListener(topics = "bank-transfers", groupId = "transfer-settlement-group")
public void processTransfer(TransferEvent event, Acknowledgment ack) {
// 1. Redis SETNX 幂等校验，若已处理直接 Ack 返回
boolean isNew = redisTemplate.opsForValue()
.setIfAbsent("tx:" + event.getTxId(), "DONE", 24, TimeUnit.HOURS);
if (!isNew) { ack.acknowledge(); return; }
// 2. 执行核心转账扣款结算逻辑
transferService.executeSettlement(event);
ack.acknowledge(); // 成功后手动提交 Offset
}
// 达到重试上限或遭遇不可重试异常进入死信句柄
@DltHandler
public void handleDeadLetter(TransferEvent event,
@Header(KafkaHeaders.RECEIVED_TOPIC) String topic) {
log.error("Transfer [{}] sent to DLT [{}]", event.getTxId(), topic);
dltAuditService.recordForManualReview(event); // 存入死信表人工审查
}
}

核心架构启发 (Enterprise Pipeline Insight)

金融级转账管线的核心在于**“将不确定性隔离”**。结合 Spring Kafka 的 @RetryableTopic 指数退避重试与 Redis 幂等校验，不仅主流程高吞吐不卡死，而且死信事件可通过 @DltHandler 完整记录，实现 100% 的可追溯与可补偿。

🎯 引导学生透视金融管线的防重与容错机制： “向学员强调：银行转账等金融交易系统对数据一致性要求极高。因为 Kafka 提供的是‘至少一次’保障，所以在消费方法 `processTransfer()` 内部，第一步必须通过 Redis `SETNX` 或数据库唯一主键进行幂等校验。即使网络重复投递，第二次处理也会被直接拦截并安全 Ack。”
