1. Producer ACKs 等级配置与 ISR 动态列表 ACKs & ISR

`acks = 0`（即发即弃 / Fire-and-Forget） Highest Throughput

Producer 发送后完全不等待任何 Broker 确认。吞吐量极高，但如果 Broker 挂掉或网络异常，消息将直接丢失。适用于日志收集等容忍丢失场景。

`acks = 1`（仅 Leader 副本写盘确认 / 默认） Balanced Standard

Producer 等待 Leader 副本写入本地 Log 后即接收 Ack。兼顾了吞吐与可靠性，但如果 Leader 刚写完即物理宕机且未同步到 Follower，仍可能丢数据。

`acks = all` / `-1`（全 ISR 副本强同步确认） Zero Data Loss

Producer 等待 ISR 列表中的所有健康副本均完成写盘才接收 Ack。配合 min.insync.replicas=2，可提供金融级零数据丢失保证。

In-Sync Replicas (ISR) 动态健康列表 replica.lag.time.max.ms

仅包含与 Leader 落后时间不超过 `replica.lag.time.max.ms` 的健康副本。慢 Follower 会被动态踢出 ISR，防止其卡死 `acks=all` 的响应延迟。

权衡之道：ACKs 越高安全性越强，但网络 Ack 延时和 CPU 开销相应增加
2. 消息传输三大语义与零数据丢失工程配方 Delivery Guarantees

传输保障三大语义 (Delivery Semantics) Guarantees

At-Most-Once: 至多一次（可能丢失，绝不重复）。`acks=0` 或消费前先 commit offset。
At-Least-Once: 至少一次（绝不丢失，可能重复）。`acks=all` + 业务处理完后手动 commit offset，要求 Consumer 具备防重幂等性。
Exactly-Once: 精确一次（端到端不丢不重）。基于幂等 Producer + Kafka 事务消息（EOS）。
生产级零数据丢失 (Zero Data Loss) 配置配方 Golden Config
1. Producer: acks = all
2. Producer: retries = Integer.MAX_VALUE
3. Topic: replication.factor = 3
4. Broker: min.insync.replicas = 2
5. Consumer: enable.auto.commit = false (手动提交)

核心架构启发 (Reliability Recipe Insight)
