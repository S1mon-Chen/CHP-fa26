1. 幂等 Producer 与 Transaction Coordinator 两阶段提交 Idempotency & 2PC

幂等 Producer：`PID` 与递增 `Sequence Number` `enable.idempotence=true`

开启后，Broker 会为 Producer 分配全局唯一 ID（`PID`），并为发往每个分区的消息维护单调递增的 `Sequence Number`。若重试导致重复消息，Broker 根据元组 (PID, Partition, Sequence) **自动丢弃重复帧，无需业务代码干预**。

Transaction Coordinator 与 `__transaction_state` 2PC Coordinator

特定 Broker 担任 **Transaction Coordinator**，利用内部持久化 Topic __transaction_state 记录全局事务日志（Ongoing, PrepareCommit, Committed）。

两阶段提交 (2PC) 控制标记 (Control Markers) Commit/Abort Markers

提交事务时，Coordinator 向受影响的目标 Partition 写入特殊的 **Commit/Abort Control Marker** 消息，告知下游 Consumer 该批次数据已生效或需丢弃。

本质保障：单分区单会话幂等 + 跨分区/跨 Topic 事务原子提交
2. Read-Process-Write 事务套路与 Consumer 隔离级别 Transaction API
// 1. 生产者事务 API 标准流程 (`KafkaPro.java`)
props.put("transactional.id", "tx-order-pipeline-1");
producer.initTransactions();
try {
producer.beginTransaction();
// ① 推送处理后的业务消息
producer.send(new ProducerRecord<>("target-topic", key, val));
// ② 将消费者的源 Offset 一并原子提交至同一事务
producer.sendOffsetsToTransaction(offsets, consumerGroupId);
producer.commitTransaction(); // 2PC 提交
} catch (KafkaException e) {
producer.abortTransaction(); // 发生异常回滚
}

Consumer 端隔离级别配置 (`read_committed`) isolation.level

下游 Consumer 需配置 isolation.level = read_committed。Consumer 内部会缓冲未决消息，自动丢弃已 Abort 的事务，仅向业务层暴露出已成功 Commit 的记录。

核心架构启发 (EOS Architecture Trade-off)

真正的端到端 **Exactly-Once** 绝不仅仅靠简单地将消息幂等去重，而是通过 幂等 Producer (PID) + Transaction Coordinator (2PC) + Consumer read_committed 的联动，将“消息处理”与“Offset 提交”强绑定在一个原子事务中。
