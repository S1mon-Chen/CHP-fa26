Part 04 · 次世代 MQ 与事件驱动架构 (EDA) 模式

事件驱动架构 (EDA) 核心原理解析：拓扑结构与设计原则

Event Producers, Event Routers, Event Consumers, Mediator Topology vs. Broker Topology

事件驱动两大核心拓扑：中介者拓扑 (Mediator) vs. 代理者拓扑 (Broker) Orchestration vs. Choreography
1. 中介者拓扑 (Mediator Topology) Centralized Orchestration
Initial Event → Event Queue → Event Mediator (编排器)
编排器（如 Camunda / Temporal）接收初始事件，按工作流业务规则串行/并行调度 Step 1, Step 2, Step 3 动作队列。
适合复杂的长事务、分布式工作流（Workflow），流程状态清晰可见。
2. 代理者拓扑 (Broker Topology) Decentralized Choreography
Producer → Event Broker → Consumer A (发布新 Event) → Consumer B
无中央控制器！组件通过发布并响应事件串联（Choreography 舞蹈模式），组件仅感知自己感兴趣的事件。
适合高度解耦、去中心化的响应式事件响应链，扩展性极强。
1. 两种 EDA 拓扑范式对比与选择依据 Topologies Trade-off

中介者拓扑 (Orchestration)：强控制力与全局视角 Centralized Control

由中央 Mediator 掌握完整业务编排逻辑。出现异常时可统一触发补偿事务（如 Saga 事务编排）。**缺点**：Mediator 存在集中式耦合与单点演进瓶颈。

代理者拓扑 (Choreography)：极致解耦与自演进 Decentralized Autonomy

事件在各微服务间像接力棒一样流转。新增下游消费服务时完全无需改动上游。**缺点**：缺乏全局视图，复杂链路的追溯与分布式调试较困难。

事件通知 (Event Notification) vs. 事件状态传递 Payload Strategy

• **Event Notification**：仅发送轻量事件通知（如 `OrderCreatedEvent(id)`），下游回查 API。
• **Event-Carried State Transfer**：事件携带完整快照 Payload，下游无需回调上游。

选型法则：长线性复杂业务流程选 Mediator，高度解耦广播选 Broker
2. 事件驱动架构 (EDA) 四大核心架构优势 EDA Core Benefits

极致时空解耦 (Temporal & Spatial Decoupling) Loose Coupling

事件发布者 (Producer) 与消费者 (Consumer) 完全不知道对方的存在。生产者只将事件丢给 Event Router，消除了对特定服务接口与网络的物理依赖。

天然符合开闭原则 (Open-Closed Principle) Extensibility

当业务需要接入新功能（如加积分、发短信、风控审计）时，只需挂载新的事件 Consumer 监听目标 Topic，**核心上游代码完全无需修改或重新发布**。

隔离故障与弹性削峰 (Resiliency & Elasticity) Fault Isolation

即使下游消费服务崩溃宕机，事件依然会在 Broker 中安全积压，不影响上游生产者的正常响应。待下游服务恢复后自动断点续传。

开启下一个核心：Slide 32 · 读写分离架构 CQRS (Command Query Responsibility Segregation)

核心架构启发 (EDA Paradigm Shift Insight)

事件驱动架构 (EDA) 代表了现代分布式系统从**“被动 RPC 调度”**向**“主动事件响应”**的范式转变。理解 Mediator 与 Broker 拓扑，是将系统从紧耦合的微服务泥潭解脱出来的决定性武器。

Speaker Notes / 讲师讲稿
🎯 引导学生透视 EDA 架构范式： “向学员强调：事件驱动架构 (EDA) 的核心哲学是‘发生了某件事（Event）’，而不是‘命令某人做某事（Command）’。生产者只管向中央 Broker 宣告发生了什么，不关心谁来处理以及何时处理。”
💡 剖析 Mediator 与 Broker 拓扑的工程权衡： “请学员特别关注两种拓扑结构：Mediator 拓扑使用中央编排器（Orchestrator）控制严密的步进工作流，适合复杂的长事务；而 Broker 拓扑使用无中心链式反应（Choreography），适合高度自演进的分布式微服务。”
