高性能并发容器与细粒度锁设计

剖析 ConcurrentHashMap 从分段锁 (Segment) 到 CAS + synchronized 节点锁演进，与 CopyOnWrite 写时复制机制

ConcurrentHashMap 架构演进与无锁读机制 JDK 7 Segment vs JDK 8+ CAS Node
JDK 7：Segment 分段锁 (ReentrantLock) 锁粒度：Segment 数组

内部维护 Segment 数组，每个 Segment 继承 ReentrantLock，锁住对应 Hash 桶段。并发度受限为 Segment 数组长度（默认 16）。

JDK 8+：Node 链表首节点锁 + CAS + 树化 锁粒度：Node 槽位首节点

弃用 Segment，直接采用 Node[] + CAS + synchronized。写节点时仅锁定数组首节点，链表长度 $\ge 8$ 且容量 $\ge 64$ 时自动转换为**红黑树 (TreeBin)**。

// ConcurrentHashMap get() 方法完全不加锁的原因
transient volatile Node<K,V>[] table; // 数组修饰为 volatile
volatile V val; // 节点的 val/next 均修饰为 volatile
// 读操作依赖 volatile 内存语义强刷保证可见性，实现高并发无锁读！
警告：绝对禁止在并发场景使用 Collections.synchronizedMap
CopyOnWrite 与并发队列矩阵 Lock-Free Reads & Blocking Queue
CopyOnWriteArrayList (写时复制列表) 适合：读多写极少场景

写操作（add/set）使用 ReentrantLock 加锁，复制一份全新的底层数组进行修改，修改完成后更新指针。读操作零锁控制，彻底避免迭代器抛出 ConcurrentModificationException。

J.U.C 并发队列方案选型矩阵
ConcurrentLinkedQueue
基于 CAS 无锁算法的链表无界非阻塞队列，性能极高。
ArrayBlockingQueue
基于数组的有界阻塞队列，单 ReentrantLock + 两 Condition。
LinkedBlockingQueue
分离锁 (takeLock / putLock)，若未设上限易致 OOM。
SynchronousQueue
不存元素的挂接队列，生产必须等待消费，用于线程池。
核心原则：优先根据读写比例与阻塞需求挑选特定并发容器

并发设计哲学 (Concurrency Collection Philosophy)

高并发容器的设计精髓在于**解耦读写锁粒度**。无论是 ConcurrentHashMap 的“槽位粗细粒度锁”、CopyOnWrite 的“空间换锁时间”，还是 SynchronousQueue 的“零容量直接配对”，都是消除全局锁瓶颈的范式。

Speaker Notes / 讲师讲稿
🎯 引导学生透视 ConcurrentHashMap 的演进逻辑： “向学生说明：JDK 7 的 Segment 分段锁仍然存在并发度上限（默认 16）；JDK 8 摒弃 Segment，直接采用数组首节点锁（Node synchronized + CAS），锁粒度细化到了每个散列槽。配合 volatile 修饰 Node 的 val/next 指针，实现了 get() 读操作完全不加锁的高吞吐架构。”
💡 强调 CopyOnWriteArrayList 的适用边界与内存副作用： “提示学生：`CopyOnWriteArrayList` 虽然解决了读写并发竞争，但每次写入都全量复制原数组，在大对象或高频写场景下会频繁触发垃圾回收 (GC) 甚至 OOM！必须强调它只适用于**黑白名单、路由规则表等写极少、读极频繁**的场景。”
