synchronized 内置锁与 ObjectMonitor 机制

剖析对象头 Mark Word 状态转移、Monitor 监视器锁内部结构以及 JVM 锁升级 (Lock Escalation) 优化

Java 对象头 Mark Word 与锁升级路径 Lock Inflation Pipeline
001 无锁状态 (Unlocked)
对象刚创建，未被任何线程加锁
单线程首次偏向访问
101 偏向锁 (Biased Lock)
Mark Word 记录偏向线程 ID，无 CAS 开销
出现轻度交替竞争
000 轻量级锁 (Lightweight Lock)
栈帧分配 Lock Record，通过 CAS 自旋抢锁
自旋超限或重度锁竞争
010 重量级锁 (Heavyweight Lock)
膨胀指向 ObjectMonitor，依赖 OS Mutex 挂起
JDK 优化本质：锁撤销与不可逆膨胀

锁升级是 JVM 为了降低锁获取开销所作出的无锁-自旋-阻塞性能折衷。锁只能升级膨胀，通常**不可逆**（JDK 15+ 默认禁用偏向锁）。

对象头：Mark Word (8 Bytes) + Class Pointer (4/8 Bytes)
ObjectMonitor 内部数据结构与等待队列 C++ Monitor Core
JVM 重量级锁核心结构：ObjectMonitor.hpp
_EntryList
锁池 (BLOCKED)
等待竞争 Monitor 锁的线程队列
_owner
持有锁线程
`_recursions` 记录重入次数
_WaitSet
等待池 (WAITING)
调用 `wait()` 挂起被等待唤醒的队列
monitorenter 指令尝试获取 Monitor $\rightarrow$ 成功置 _owner，失败入 _EntryList

同步代码块 vs 同步方法字节码

同步代码块通过显式的 monitorenter 与 monitorexit 字节码实现（异常路径也会自动插入 monitorexit）；同步方法则由常量池中的 ACC_SYNCHRONIZED 标志隐式控制。

可重入锁语义 (Reentrancy)

同一线程再次获取由自己持有的锁时，无需挂起，仅将 Monitor 内的 _recursions 计数器加 1，退出时依次递减，为零时彻底释放锁。

底层损耗：重量级锁引发 OS 线程从 User Mode 切换到 Kernel Mode

架构反思 (Architectural Takeaway)

synchronized 是 Java 语言层面最简单的同步原语。虽然 JVM 引入锁升级极大优化了低竞争场景，但在高并发长时间阻塞场景下，重量级锁的内核态上下文切换开销依旧高昂——这驱动了 J.U.C 显示锁（AQS）与 Java 21 虚拟线程的演进！
