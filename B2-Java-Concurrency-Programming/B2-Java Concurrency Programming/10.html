显示锁 ReentrantLock 与 Condition 多条件等待机制

剖析 ReentrantLock 对 Synchronized 的功能增强、非阻塞与中断锁获取，以及 Condition 精准唤醒机制

ReentrantLock vs Synchronized 显式增强 java.util.concurrent.locks
非阻塞锁获取 (tryLock) tryLock(time, unit)

尝试获取锁，若锁已被占用则立即返回 false 或挂起指定超时，**天然避免死锁 (Deadlock Prevention)**。

可中断锁响应 (lockInterruptibly) throws InterruptedException

允许在等待获取锁的过程中响应中断请求。与无法中断阻塞的 synchronized 形成鲜明对比。

公平锁 vs 非公平锁策略 new ReentrantLock(true)

支持选择 FIFO **公平锁**（防止饥饿但牺牲吞吐量）或默认**非公平锁**（高吞吐量插队模式）。

规范要求：必须在 `finally` 块中显式调用 `lock.unlock()`
Condition 精准唤醒机制与有界缓冲区实现 BoundedBuffer Pattern
// 经典并发有界缓冲区：通过独立 Condition 避免全局无差别通知
public class BoundedBuffer<T> {
private final Lock lock = new ReentrantLock();
private final Condition notFull = lock.newCondition(); // 生产者等待队列
private final Condition notEmpty = lock.newCondition(); // 消费者等待队列
public void put(T x) throws InterruptedException {
lock.lock();
try {
while (count == items.length) notFull.await(); // 队满阻塞
items[putptr] = x; if (++putptr == items.length) putptr = 0; ++count;
notEmpty.signal(); // 精准唤醒等待数据的 Consumer！
} finally { lock.unlock(); }
}
}
Object wait() / notify()

对应单条件等待队列，调用 notifyAll() 会无差别唤醒所有生产者和消费者，引发惊群效应与上下文切换开销。

Condition await() / signal()

一个显示锁可创建多个独立的 Condition 对象的等待队列，实现唤醒目标的**精准靶向定位**。

底层实现：基于 AQS (AbstractQueuedSynchronizer) 的单向条件队列

显示锁演进思考 (Explicit Locking Advantage)

ReentrantLock 在 JDK 5 引入时性能远超当时的重量级 synchronized。虽然 JDK 6+ 优化了 synchronized，但显式锁提供的 tryLock、中断响应与精准 Condition 唤醒，依然是构建复杂并发容器（如 BlockingQueue）不可或缺的利器！

Speaker Notes / 讲师讲稿
🎯 引导学生辨析 ReentrantLock 的核心应用场景： “向学生强调：尽管 synchronized 语法极其简洁，但在需要死锁预防（`tryLock` 定时超时退避）、分布式中断撤销（`lockInterruptibly`）或多条件阻塞（`Condition`）时，`ReentrantLock` 是唯一的选择。”
💡 强调 try-finally 手动解锁规范： “提示学生：`ReentrantLock` 不像 synchronized 可以在异常时由 JVM 自动释放监视器，它要求开发者必须在 `try-finally` 的 `finally` 块中显式调用 `unlock()`，否则一旦发生运行时异常，该锁将永远无法释放，引发系统死锁故障。”
