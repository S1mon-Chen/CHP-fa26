Scoped Values：解决 ThreadLocal 在虚拟线程下的内存与安全隐患

剖析 ThreadLocal 堆内存暴雷原理、ScopedValue (JEP 446) 结构化作用域绑定与不可变契约

1. 传统 ThreadLocal 在海量虚拟线程下的 3 大痛点 ThreadLocal Flaws
① 物理内存膨胀暴雷 (RAM Overhead) OOM Vulnerability

每个 `ThreadLocal` 绑定在 `ThreadLocalMap` 数组中。百万级虚拟线程各自持有独立 Map 时，即使变量值很小，极多的 Map 结构也会瞬间吃光堆内存导致 **OOM 宕机**！

② 缺乏可变性约束 (Mutable Danger) Unbounded Mutability

`ThreadLocal` 允许调用链深处的任何代码随意 `set()` 更改变量值，破坏了上下文数据的不可变契约，使得错误排查极度困难。

③ 继承继承与显式清理难题 (Unbound Lifecycle) Inheritable ThreadLocal

`InheritableThreadLocal` 派生子线程时需要**完整深拷贝 Map**；且忘记调用 `remove()` 会导致长生命周期线程的严重内存泄漏。

Java 21 破局之道：ScopedValue (JEP 446 / JEP 481)

`ScopedValue` 是一种**不可变 (Immutable)、生命周期严格受限于闭包代码块 (Scope-Bound)** 的隐式上下文传递机制。它天然支持父子虚拟线程间高效共享，退出代码块后隐式自动销毁，零垃圾残留！

核心变革：用“作用域限定的只读数据”替代“线程绑定的可变数据”
ScopedValue 结构化使用范式 ScopedValue.where().run()
// 1. 声明静态常量 ScopedValue 容器
public static final ScopedValue<UserContext> CONTEXT =
ScopedValue.newInstance();
// 2. 绑定安全上下文并限定运行作用域 (Scope)
var user = new UserContext("usr_9981", "ADMIN");
ScopedValue.where(CONTEXT, user).run(() -> {
// 在此闭包及其调用的深层子方法内部，可通过 CONTEXT.get() 读数据
orderService.processOrder();
}); // 离开 run 闭包后，user 绑定立刻解绑失效，零清理代码！
// 3. 在调用的任意底层方法中无缝读取
public void processOrder() {
UserContext currentUser = CONTEXT.get(); // 只读且安全
}
对比维度 ThreadLocal ScopedValue
数据可变性 可变 (`set()` 任意修改) 只读不可变 (Immutable)
生命周期 绑定线程 (极易泄漏) 绑定闭包作用域 (Scope)
子线程共享 全量 Map 拷贝 (成本高) 零拷贝指针继承 (极其轻量)
百万 VT 适配 不推荐 (易诱发 OOM) 推荐 (专为虚拟线程打造)
生产准则：新写 Java 21+ 虚拟线程代码，请全面使用 ScopedValue

上下文传递范式革化 (Context Propagation Shift)

从 `ThreadLocal` 到 `ScopedValue` 的演进，代表了 Java 从**“基于隐式线程存储”**向**“基于结构化作用域 (Structured Scope)”**的深刻思维转变。它解耦了数据与线程生命周期，解决了海量虚拟线程下的内存泄漏与隐式修改风控痛点！
