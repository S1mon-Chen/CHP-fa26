Part 01 · 并发基础 (Concurrency Fundamentals)

线程控制 API 与优雅中断响应机制

掌握 sleep / yield / join 的底层状态行为，以及生产环境中消除孤儿线程的中断握手协议 (Interrupt Handshake)

核心控制 API 对比 (Thread Control) java.lang.Thread
Thread.sleep(ms) TIMED_WAITING

让出 CPU 执行权，不释放获得的 Monitor 锁/ReentrantLock。暂停指定时间后重新等待 CPU 调度。

Thread.yield() RUNNABLE

提示操作系统调度器“当前线程愿意放弃当前时间片”，但不改变状态。调度器可以完全无视此提示。

t.join() WAITING / TIMED_WAITING

当前线程暂停执行，等待目标线程 t 死亡终止。底层基于 Object.wait() 实现。

中断三剑客方法辨析：
  • t.interrupt() : 设置线程 t 的中断标志位为 true。
  • t.isInterrupted() : 仅查询标志位（不改变状态）。
  • Thread.interrupted() : 查询并清除当前线程标志位！
警告：严禁使用已废弃的 Thread.stop()
优雅中断代码范式 (Safe Worker Pattern) Java Standard Concurrency
// 生产级后台任务：正确响应中断信号与异常清理
public class SafeWorker implements Runnable {
@Override
public void run() {
// 1. 定期检查中断标志位
while (!Thread.currentThread().isInterrupted()) {
try {
// 执行可能引发 InterruptedException 的阻塞操作
Thread.sleep(1000);
} catch (InterruptedException e) {
// ⚠️ 关键点：捕获异常时，JVM 会自动清除中断标志位！
// 必须重新传递中断（恢复中断状态）或清理资源后 break
Thread.currentThread().interrupt();
break; // 退出任务循环
}
}
// 2. 清理临时文件与连接资源
cleanupResources();
}
}
高频踩坑：吃掉 InterruptedException (Swallowing Interrupt)

如果在 catch (InterruptedException e) 块中仅仅打印日志（如 e.printStackTrace()）而既不向上抛出也不重新调用 interrupt()，上层线程池或调用者将完全失去对该线程的控制，导致后台任务沦为无法停止的**孤儿线程 (Orphan Thread)**！

协作契约：Java 中断是“协商机制”而非强行杀线程

服务端健壮性设计原则 (Robustness Takeaway)

Java 中的中断是一种**协作式 (Cooperative)** 机制。良好的服务端代码应当随时准备响应中断，确保在服务优雅下线 (Graceful Shutdown) 或线程池回收时能够及时释放锁与系统资源。

Speaker Notes / 讲师讲稿
🎯 引导学生理解中断的协作本质： “向学生说明，Java 中没有类似于 Linux kill -9 这样能直接杀死任意线程的现代安全方法（废弃的 Thread.stop 会破坏对象内部一致性状态）。中断（Interrupt）本质上是发送一个协商请求，告诉目标线程‘请尽快停止当前工作’。”
💡 强调 InterruptedException 清除标志位的坑： “重点剖析：当调用 sleep/wait/join 的线程收到中断信号时，JVM 会抛出 InterruptedException，**同时自动把中断标志位置回 false**。因此，直接 catch 掉该异常而不做任何处理，上层的 ExecutorService 就会彻底失去该线程的控制。必须通过 Thread.currentThread().interrupt() 重新恢复标志位！”
