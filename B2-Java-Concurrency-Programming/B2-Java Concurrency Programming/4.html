JVM 状态与 OS 内核状态对照表 (State Mapping) Linux / Windows Kernel

JVM 状态 (Thread.State) OS 内核状态 (Kernel) 触发展现场景
RUNNABLE Ready / Running / Waiting I/O 获得 CPU 执行权、就绪等待调度、或正在进行磁盘/Socket I/O 阻塞

TIMED_WAITING Waiting (Timer queue) Sleep 超时、带 TimeOut 参数的 wait/join/parkNanos
核心考点/陷阱：为什么 Socket.read() 在 JVM 里看依然是 RUNNABLE？

在操作系统视角，线程发起阻塞式 Socket I/O 时已被内核置为 Waiting/Blocked 挂起；但在 JVM 维度，Java 认为“操作系统随时可能完成 I/O 并交还控制权”，因此 JVM 依旧将其统一报告为 **RUNNABLE**。排查网络阻塞不能只看线程状态，还需检查线程堆栈中的本地 Socket 方法！

诊断命令：jstack <pid> | ThreadMXBean jcmd / VisualVM

服务端性能诊断洞察 (Performance Diagnostic Takeaway)

JVM 的状态定义服务于 Java 运行时的抽象；区分 JVM 的 RUNNABLE 与 OS 内核真正运行状态，是高并发场景下精准定位 CPU 跑满还是 I/O 阻塞的关键。

Speaker Notes / 讲师讲稿
🎯 引导学生区分 JVM 状态与 OS 状态： “向学生强调，Java 的 Thread.State 是 JVM 级别的抽象。很多初学者在使用 jstack 排查问题时发现线程是 RUNNABLE，就误以为 CPU 正在极速运转，实际上该线程可能正在执行阻塞式的 Socket 网络读写。”
💡 强调 BLOCKED 与 WAITING 的核心区别： “必须点明：在 JVM 中，只有等待进入 synchronized 临界区拿不到 Monitor 锁时，状态才是特殊的 BLOCKED；而在使用 J.U.C 的 ReentrantLock.lock() 时，拿不到锁的线程状态其实是 WAITING (LockSupport.park)。这是面试和日常调优极其常见的混淆点。”
