JMM Happens-Before 契约与指令重排机制

探究编译器/CPU 重排优化对有序性的破坏，剖析 JMM Happens-Before 内存可见性断言与屏障指令

指令重排序 (Instruction Reordering) Pipeline Optimization Pipeline
源代码到最终执行指令的三层重排阶段
1. 编译器优化重排 JIT 编译器在不改变单线程语义前提下重排
2. 指令级并行重排 CPU ILP (Instruction-Level Parallelism) 重排
3. 内存系统重排 Store Buffer 缓存写回延迟引起的重排
as-if-serial 语义： 无论如何重排，单线程内程序的执行结果不能被改变。但对于**多线程并发**，重排将直接破坏线程间的逻辑依赖！
经典乱序隐患：指令重排导致无锁双重检查锁 (DCL) 失效
instance = new Singleton();
// 正常：1. 分配内存 -> 2. 初始化对象 -> 3. 设置指针
// 重排：1. 分配内存 -> 3. 设置指针 -> 2. 初始化对象
// 导致其他线程拿到未初始化的半成品对象！
本质：重排序提升单核效率，却引发多核可见性混乱
Happens-Before 八大核心规则 (JMM Guarantees) Visibility Contract
DEFINITION (Happens-Before 含义)

若操作 A Happens-Before (HB) 操作 B，则 A 操作产生的影响（写变量、方法调用等）**必然对 B 立即可见**，且 A 的执行顺序排在 B 之前。

1. 程序次序规则 (Program Order)

单线程内，按代码控制流顺序，前面的操作 HB 于后面的操作。

2. 管程锁定规则 (Monitor Lock)

对一个锁的 unlock 操作 HB 于后续对同一个锁的 lock 操作。

3. volatile 变量规则

对 volatile 变量的写操作 HB 于后续对该变量的读操作。

4. 线程启动规则 (Thread Start)

Thread 对象的 start() 方法 HB 于该线程的每一个动作。

5. 线程终止规则 (Thread Join)

线程中的所有操作都 HB 于对此线程的 join() 检测返回。

6. 传递性规则 (Transitivity)

若 A HB B 且 B HB C，则操作 A 必然 HB 于操作 C。

底层实现：JVM 通过插入**内存屏障指令 (Memory Barriers)** 禁重排与强刷缓存

契约思维 (Contract Takeaway)

Happens-Before 是 JVM 规范向开发者承诺的“内存可见性保证”。只要你的代码遵循 Happens-Before 规则（如加锁或使用 volatile），JVM 与底层 CPU 保证在任何硬件平台都能正确反映数据更新！

🎯 引导学生理解指令重排与 as-if-serial： “向学生强调：优化（重排）本身是为了榨干 CPU 的并行处理能力。在单线程下，重排绝不会改变执行结果；但在多线程场景下，如 DCL 双重检查锁（Singleton），指令重排会导致另一个线程拿到未初始化的内存对象，直接引发空指针或状态污染！”
💡 解读 Happens-Before 契约的本质： “提示学生：程序员不需要去记底层的 x86 `mfence` 或 ARM `dmb` 内存屏障指令，只需要记住 Happens-Before 规则。只要建立了 Happens-Before 关系（如 volatile 或 synchronized），JVM 就会自动插入相应的内存屏障，保证指令不被乱序且内存修改立即可见。”
