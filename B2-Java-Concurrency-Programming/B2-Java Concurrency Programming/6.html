Part 01 · 并发基础 (Concurrency Fundamentals)

数据竞态 (Data Race) 与指令交叉执行 (Interleaving)

剖析简单的 count++ 在 JVM 字节码维度的非原子性拆解，透视多线程环境下“丢失更新 (Lost Update)”故障根源

非原子操作：Unsafe Counter Java Code & Bytecode
// 多线程并发调用 increment() 会导致数据覆盖
class UnsafeCounter {
private int count = 0;
public void increment() {
count++; // 看似只有 1 行代码！
}
}
javap -c 反编译分析 (3 条 JVM 指令)
  1. 1
    getfield #2

    从主内存/堆读取字段 count 的当前值装载到当前线程的操作数栈顶

  2. 2
    iconst_1 & iadd

    在当前线程私有栈内将栈顶整数加 1

  3. 3
    putfield #2

    将操作数栈顶计算出的新值强行写回对象的 count 属性

本质：高级语言的单条加减法并非 CPU 原子的！
指令交叉执行时序图 (Interleaving Timeline Trace) 初始状态：count = 0
时间点 线程 A (Thread A) 线程 B (Thread B) 主存 count 值
T1 getfield (读出 count=0) -- (等待/挂起) 0
T2 -- (发生线程调度/上下文切换) getfield (读出 count=0) 0
T3 iadd (私有栈计算 0+1=1) iadd (私有栈计算 0+1=1) 0
T4 putfield (写回 count=1) -- (保持内部计算值 1) 1
T5 -- (完成操作) putfield (写回 count=1) 1 (丢失更新!)
后果分析：丢失更新 (Lost Update) 与数据损坏

按预期，线程 A 与线程 B 各执行一次递增后，count 应为 2。但在时间点 T5，线程 B 将基于旧数据计算出的 1 写回，直接覆盖了线程 A 已经更新的结果。若循环执行 1,000,000 次，最终结果往往远小于 2,000,000！

并发三大特性之一：原子性 (Atomicity) 遭受破坏

并发防御思考 (Concurrency Protection)

要消除数据竞态并保证更新不丢失，必须确保临界区操作具备**原子性**与**内存可见性**：方案包括使用 synchronized 内置锁、ReentrantLock 显示锁，或无锁 CAS 原子类 (AtomicInteger)。
