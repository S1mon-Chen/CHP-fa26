ThreadPoolExecutor 7 大核心参数与调度原理

深入剖析线程池任务提交决策状态机、工作线程 (Worker) 生命管理与 CPU / I/O 密集型参数调优

ThreadPoolExecutor 7 大核心构造参数 java.util.concurrent
// 规范：禁止使用 Executors 工具类直接创建线程池！
ThreadPoolExecutor executor = new ThreadPoolExecutor(
8, // 1. corePoolSize (核心线程数)
16, // 2. maximumPoolSize (最大线程数)
60L, TimeUnit.SECONDS, // 3&4. keepAliveTime & Unit (非核心存活)
new ArrayBlockingQueue<>(1000), // 5. workQueue (有界任务队列)
new NamedThreadFactory("biz-pool"),// 6. threadFactory (自定义命名工厂)
new ThreadPoolExecutor.CallerRunsPolicy()// 7. handler (拒绝策略)
);
1. corePoolSize

常驻线程数，任务空闲时不销毁（除非设置 allowCoreThreadTimeOut）。

2. maximumPoolSize

允许容纳的最大并发线程上限（核心数 + 临时非核心数）。

5. workQueue

必须显式选用有界队列，严禁默认无界的 LinkedBlockingQueue。

6. threadFactory

必须自定义线程名称前缀，便于生产环境 Dump 堆栈与日志排查。

规约要求：生产环境必须通过 ThreadPoolExecutor 显式创建线程池
任务提交调度 4 步决策时序 (Task Execution State) execute(Runnable) Workflow
步骤 1：核心数校验 线程数 $< \text{corePoolSize} \rightarrow$ 直接创建核心 Worker 线程
步骤 2：入队暂存 线程数 $\ge \text{corePoolSize} \rightarrow$ 尝试 offer 入 BlockingQueue
步骤 3：扩容最大数 队列已满 $\rightarrow$ 创建临时非核心 Worker (直至 maximumPoolSize)
步骤 4：触发拒绝策略 线程数 $=$ max 且队列已满 $\rightarrow$ 调用 Handler 拒绝机制
容量调优经验公式 (Thread Pool Capacity Sizing) $N_{cpu} = \text{Runtime.availableProcessors()}$
CPU 密集型 (CPU-Bound)
计算繁重，避免上下文切换：
N_threads = N_cpu + 1
I/O 密集型 (I/O-Bound)
包含网络/数据库等待耗时：
N_threads = N_cpu * (1 + W/C)
高阶扩展：推荐结合 Nacos / Apollo 实现分布式动态线程池参数调优

线程池工程哲学 (ThreadPool Best Practices)

线程池本质是**池化技术与生产者-消费者模式**的结合。决不能使用无界队列（如默认 Executors.newFixedThreadPool），否则高并发大流量突发时会导致请求大量积压，最终直接诱发 **OOM 宕机**！

Speaker Notes / 讲师讲稿
🎯 引导学生明晰线程池任务提交的 4 步逻辑： “向学生强调：很多人误以为线程池是‘核心数满了存队列，队列满了直接拒绝’。实际上中间有一步：**队列满了才会去继续扩容非核心线程直至 maximumPoolSize**！这个调度逻辑是面试和日常调优中最容易被踩坑的。”
💡 强调阿里 Java 规约中对 Executors 的禁用原因： “提示学生：阿里 Java 规约明确规定‘严禁使用 Executors.newFixedThreadPool 或 newCachedThreadPool’。因为 `FixedThreadPool` 默认使用未设容量上线的 `LinkedBlockingQueue`（内存积压触发 OOM），而 `CachedThreadPool` 允许 `maximumPoolSize` 为 `Integer.MAX_VALUE`（创建百万级操作系统线程直接卡死 CPU）。必须通过 `ThreadPoolExecutor` 手动显式配置所有 7 大参数！”
