Part 03 · 传统并发架构瓶颈 (Limitations of Platform Threads)

1:1 平台线程物理瓶颈与内核开销剖析

探究 OS 内核线程 1:1 映射机制、预分配 1MB 栈内存膨胀危机与上下文切换 CPU 损耗

1:1 平台线程与 OS 内核线程映射关系 java.lang.Thread (Classic)
JVM Platform Thread 物理绑死 OS Kernel Thread
Java Thread 1 <==== 1 : 1 ====> OS Kernel Thread 1
Java Thread 2 <==== 1 : 1 ====> OS Kernel Thread 2
Java Thread N <==== 1 : 1 ====> OS Kernel Thread N
生命周期绑定： 每一个平台线程的创建、调度和销毁都必须通过 JNI 调用 OS 内核 API（如 POSIX pthread_create），创建成本与系统代价高昂。
内存暴雷公式 (Thread Stack Memory Footprint) -Xss1m (Default)
$$\text{RAM}_{\text{stacks}} = \text{Thread Count} \times \text{Stack Size (-Xss)}$$
10,000 线程 $\times$ 1 MB/Stack $\approx$ 10 GB 纯物理内存！
哪怕线程处于 Blocked 空闲等待，这 1MB 的栈空间也无法释放被白白浪费。
代价：高并发下内存大部分用于存放线程栈，引发 OOM 崩溃
CPU 上下文切换 (Context Switch) 隐形损耗 User Mode vs Kernel Mode
1. 状态保存与保存 PCB (Process Control Block) \~1-2 microseconds

CPU 必须暂停当前指令流，将通用寄存器、程序计数器 (PC)、栈指针等状态写入内核态 PCB 结构体。

2. 用户态与内核态特权级切换 Ring 3 $\longleftrightarrow$ Ring 0

涉及 CPU 保护模式中断响应与特权级转换，导致 CPU 指令流水线 (Pipeline) 彻底清空冲刷。

3. CPU L1/L2 缓存与 TLB 页表失效 (Cache Pollution) 致命隐形开销

新线程调度执行后，原本硬件 CPU L1/L2 高速缓存与 TLB (快表) 中的数据全部失效，引发大量的 **Cache Miss** 重新读主存！

极限吞吐警示：上下文切换占比超限

当活跃平台线程数远超 CPU 逻辑核心数时，系统超过 **20% - 30% 的 CPU 计算资源** 纯粹浪费在上下文切换本身，而非实际业务逻辑！

后果：1:1 平台线程架构无法扩展支撑 C10K / C1000K 海量并发

传统并发模型反思 (1:1 Model Limitations)

1:1 平台线程模型在处理 CPU 密集型任务时表现优异，但在面对**海量并发 I/O 阻塞请求**时，固定物理栈内存消耗与昂贵的内核态上下文切换成为了不可逾越的天花板。这倒逼了高并发后端向 **Java 21 虚拟线程 (M:N 协程)** 演进！

Speaker Notes / 讲师讲稿
🎯 引导学生反思传统平台线程的物理极限： “向学生强调：为什么在 Java 21 之前，我们无法仅靠多线程轻松实现 C1000K（百万连接并发）？因为传统平台线程与 OS 内核线程是 1:1 绑定的。默认每个线程预分配 1MB 物理栈空间，1 万个线程就会吃掉 10GB 内存！而且绝大部分线程只是在阻塞等待网卡/数据库响应。”
💡 解读 CPU 上下文切换的隐藏杀手——TLB 与 L1/L2 缓存失效： “提示学生：上下文切换不单单是保存寄存器那几微秒。真正的性能杀手在于** Cache 污染**——当内核切换到新线程时，原本 CPU 缓存的物理数据和 TLB 页表映射全部变得不适用，引发大量的 Cache Miss 重新穿透读取 DRAM 主存！”
