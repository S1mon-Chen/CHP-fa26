避坑指南：Pinning (线程固定) 瓶颈剖析与重构

探究 synchronized 与 JNI 导致 Carrier Thread 无法卸载卡死机制、-Djdk.tracePinnedThreads 排查与 ReentrantLock 替代方案

1. 什么是 Pinning (线程固定)？ Carrier Thread Stall
Pinning 现象致命危害：卸载失败致 OS 线程被卡死 C1000K Collapse

当虚拟线程进入 **Pinning 状态** 时，其调用栈无法在阻塞时被序列化卸载（Unmount）到 Java 堆。此时底层的载体 platform 线程（Carrier Thread）会被 **同步绑死硬挂起**。若海量虚拟线程同时触发 Pinning，底层 ForkJoinPool 的载体线程将被快速耗尽僵死！

触发原因 ①：在 synchronized 代码块/方法内部发起阻塞 I/O 高频生产坑

Java 内置的 `synchronized` 依赖 C++ 的 `ObjectMonitor`，Monitor 锁结构目前与平台线程栈深度绑定。在 `synchronized` 内部进行网络调用、数据库查询或 `Thread.sleep` 会锁定 Carrier Thread！

触发原因 ②：在 JNI (Native 方法) 执行期间发起阻塞操作 Native Code Barrier

当虚拟线程调用通过 JNI 嵌入的 C/C++ 本地原生方法时，JVM 无法干预 Native 栈帧，同样会导致虚拟线程不可 Unmount。

演进展望：JDK 24+ (JEP 491) 将逐步彻底消除 synchronized 的 Pinning 限制
Pinning 排查诊断标志与 ReentrantLock 重构 -Djdk.tracePinnedThreads
JVM 诊断启动参数 (Print Stack Trace on Pin) JVM Flag
-Djdk.tracePinnedThreads=full

当虚拟线程因 Pinning 导致 Carrier Thread 无法卸载并触发阻塞时，JVM 会在控制台打印详细的包含 `synchronized` 源码行号的 StackTrace！

// ❌ 错误代码：synchronized 包裹同步阻塞 I/O (引发 Pinning)
public synchronized String fetchData() {
return httpClient.get(url); // 阻塞时绑死 Carrier Thread!
}
// ✅ 推荐重构：使用 J.U.C ReentrantLock 替代 synchronized
private final ReentrantLock lock = new ReentrantLock();
public String fetchDataRefactored() {
lock.lock();
try {
return httpClient.get(url); // 虚拟线程可安全 Unmount，零 Pinning!
} finally { lock.unlock(); }
}
生产重构原则：升级 Java 21 虚拟线程前，全量扫描项目中的 synchronized I/O 模块

Pinning 防御思考 (Pinning Mitigation Strategy)

Pinning 是 Java 21 虚拟线程迁移过程中最隐蔽的性能杀手。要避免生产环境高并发吞吐暴跌：**在临界区包含长耗时 I/O 或 RPC 调用时，务必将 `synchronized` 替换为 J.U.C 的 `ReentrantLock`**，并开启 JVM 诊断标志进行严格集成压测！

Speaker Notes / 讲师讲稿
🎯 引导学生理解 Pinning 产生的本质原因： “向学生强调：为什么 `synchronized` 会引起 Pinning？因为 Java 原生的 `synchronized` 对应 HotSpot C++ 的 `ObjectMonitor`，Monitor 锁帧目前直接压在平台线程栈上，使得 JVM 无法把当前的 `Continuation` 栈帧打包拉出来。当虚拟线程此时发起网络 I/O 阻塞时，连带底层的 Carrier Thread 也会被锁死！”
💡 强调从 synchronized 到 ReentrantLock 的简单替换： “提示学生：解决方案非常清晰——用 `ReentrantLock` 替换 `synchronized`。`ReentrantLock` 底层基于 AQS，其 `lock()` 调用已经被 JDK 21 团队用非阻塞写重构，即使在锁内部执行阻塞 I/O，虚拟线程依然可以平滑 Unmount 卸载！”
