Part 03 · 传统并发架构瓶颈 (Limitations of Platform Threads)

请求-线程 (Thread-per-Request) 模型与 Blocking I/O 危机

剖析传统 Web 容器 (Tomcat / Spring MVC) 同步阻塞模型在大规模微服务网关中的物理失效

Thread-per-Request 工作流与 I/O 阻塞耗时比 Tomcat / Spring MVC Typical Lifecycle
单个 HTTP 请求的处理耗时分布 (Latency Breakdown)
CPU 计算时间 (CPU Time) ~ 2 - 5 ms (5%)
I/O 阻塞等待 (I/O Wait Time) ~ 50 - 200 ms (95%)
MySQL 查询 Redis 交互 下游 RPC 调用
核心痛点： 在 95% 的请求处理周期内，**物理线程被彻底锁定挂起**，CPU 物理核心完全闲置，但该 1MB 物理内存与 OS 线程句柄却被死死占用！
容器线程池枯竭 (Tomcat Thread Pool Starvation) max-threads: 200 (Default)

当并发请求数达到 200，且每个请求因为上游 DB 慢查询延迟 1 秒时，Tomcat 线程池将在瞬间被**完全占满僵死**，后续连接只能进队列或被拒绝 (HTTP 503 Service Unavailable)！

后果：1:1 平台线程将并发容量限制在“线程池大小”而非“物理硬件极限”
高并发下“高吞吐”与“物理开销”的不可调化矛盾 The Concurrency Dilemma
目标：实现 C10K / C100K 高并发吞吐 Scale Up Demand

为支撑 100,000 并发长连接或高延迟 HTTP 请求，系统必须创建 100,000 个 `Thread` 实例。

代价：100,000 OS 线程引发系统崩溃 Physical Barrier
  • 内存爆表： $100,000 \times 1\text{MB} = 100\text{GB}$ 纯线程栈 RAM 消耗。
  • CPU 抖动： 几万个线程频繁竞争 CPU，CPU 利用率 100% 但 90% 都在做上下文切换。
  • OS 限制： 触及 Linux `max user processes` (`ulimit -u`) 与 `pid_max` 句柄上限。
历史上退而求其次的解决方案：响应式编程 (Reactive) Netty / WebFlux

响应式编程放弃了“一个请求一个线程”的同步顺序思维，强制使用复杂的**非阻塞异步回调/Mono/Flux 响应式流**。虽然榨干了少量线程的性能，但极度损害了代码可读性与排错调试体验 (Async Call Stack Hell)！

破局：需要一种“像同步代码一样好写，但像异步回调一样轻量”的全新模型

架构危机总结 (The Blocking I/O Dilemma)

在微服务网关与云原生场景下，**I/O 阻塞才是高并发最大的杀手**。基于平台线程的 Thread-per-Request 架构无法兼顾“开易编写的同步代码”与“支持百万高并发”。这直接促成了 **Java 21 虚拟线程 (Project Loom)** 的诞生！

🎯 引导学生反思请求-线程模型的物理瓶颈： “向学生强调：在传统的 Spring MVC + Tomcat 结构中，`max-threads=200` 意味着同时最多只能有 200 个并发请求被处理。当请求涉及数据库或 RPC 等网络耗时（占请求周期的 95% 以上）时，这 200 个物理线程绝大部分时间都在等网络响应，CPU 利用率极低但新请求已经进不来了。”
💡 铺垫响应式 (Reactive) 的痛苦与虚拟线程的优雅： “提示学生：为了解决这个 Blocking 危机，过去的行业做法是用 Spring WebFlux 或 Netty 写异步响应式代码（Mono/Flux）。但响应式代码破坏了传统的控制流和异常栈，极难调试。这便为下一章引入 Java 21 虚拟线程（既保留同步代码编写体验，又拥有异步非阻塞吞吐）奠定了背景！”
