Redis 持久化机制 1：RDB 内存快照与 Copy-on-Write (COW)

RDB Binary Snapshot (`dump.rdb`), `bgsave` Sub-process & Linux OS `fork()` Page Table COW Mechanism

1. RDB 内存快照原理与触发方式

dump.rdb

RDB (Redis Database) 是在指定的时间间隔内，将当前时刻的全部内存数据集生成一份紧凑的**二进制压缩镜像文件 (`dump.rdb`)** 写入磁盘。

`save` vs. `bgsave` 命令对比 Command Trigger
  • • SAVE：主线程阻塞执行快照落盘。**期间禁止接收任何读写命令**，线上生产禁用！
  • • BGSAVE：主线程通过 fork() 创建子进程，后台异步生成 RDB，**主线程无锁继续响应客户端**。
自动快照触发配置 (`redis.conf`) Auto-Save Rules
save 900 1 # 900 秒 (15 分钟) 内至少有 1 个 key 被修改
save 300 10 # 300 秒 (5 分钟) 内至少有 10 个 key 被修改
save 60 10000 # 60 秒内至少有 10000 个 key 被修改
特点：文件极小，重启加载恢复极快，但两次快照间存在数据丢失窗口

2. Linux `fork()` 与 Copy-on-Write (COW) 写时复制

COW Physics
// Linux fork() 写时复制 (Copy-on-Write) 内存映射逻辑
Redis Main Process ──fork()──► Child Process (`bgsave`)
│ │
▼ ▼
[ 虚拟内存页表 (Shared Page Table) ] ◄──┘ (仅复制页表指针，耗时极短)
│
├── Read-Only ──► 物理内存页 Page A, Page B, Page C (只读生成 dump.rdb)
└── Write Cmd ──► 操作系统触发 Page Fault ──► 复制 4KB 物理页 Page B'

主线程修改 Page B 时，OS 将 Page B 复制出一份副本 Page B'，主线程修改 Page B'，而子进程继续读取只读的 Page B，保证快照点数据一致性。

COW 机制的三大工程优势 Zero Locking
  • • **零阻塞快照**：`fork()` 只复制页表指针（几毫秒），无需停机锁死整个物理内存。
  • • **物理内存按需复制**：快照期间若只有 $5\%$ 的 Key 被修改，只额外消耗 $5\%$ 的物理页内存。
  • • **数据时刻一致性**：子进程拿到的永远是 `fork()` 那个时间点的只读内存快照。

核心持久化启发 (RDB COW Insight)

Redis 的 RDB 快照机制巧借了 Linux 操作系统的 **`fork()` 与 Copy-on-Write (写时复制)** 能力，在主线程不锁内存的前提下，完成了点在时间上的二进制镜像落盘，展示了操作系统与上层软件高度协同的极致优雅。
