一致性 Hash 算法与虚拟节点 (Consistent Hashing & Virtual Nodes)

Modulus Hashing Flaw, $2^{32}-1$ Hash Ring, Clockwise Lookup & Virtual Node Load Balancing

1. 传统取模 Hash 缺陷与一致性 Hash 环

Hash Ring Concept
传统取模算法的灾难 ($hash(key) \pmod N$) > (N-1)/N Migration

当缓存节点数从 $N$ 变为 $N \pm 1$（如增加或挂掉 1 台机器），超过 $(N-1)/N$ 的缓存 Key 路由映射全盘失效！引发全集群缓存雪崩与 DB 瘫痪。

一致性 Hash 环（$0 \sim 2^{32}-1$） Clockwise Routing
0 / 2^32
Node 3 (Hash3) ──► Node 1 (Hash1)
▲ │
│ [Key A] ▼
Node 2 (Hash2) ◄── (顺时针寻节点)

节点与 Key 均计算 Hash 映射到闭环。Key **沿顺时针方向寻找遇到的第一个物理节点**。若节点 2 宕机，仅 Hash2 附近的 Key 受影响，其他节点不受波及！

优点：将节点扩缩容对缓存失效的影响限制在局部相邻区间

2. 虚拟节点 (Virtual Nodes) 解决数据倾斜

Data Skew Fix
少节点下的数据倾斜问题 (Hotspot Data Skew) Uneven Distribution

当集群仅有 2\~3 个物理节点时，节点在 Hash 环上的分布容易极度不均，导致大量流量集中倾斜到某一台节点，引发单点热点崩溃。

虚拟节点算法（物理节点 $\to K$ 个虚拟节点） Virtual Replicas
物理节点 Node 1 映射为虚拟节点:
Node1#1 = hash("127.0.0.1:8080#1")
Node1#2 = hash("127.0.0.1:8080#2")
Node1#3 = hash("127.0.0.1:8080#3") ...

将虚拟节点均匀打散切割 $2^{32}-1$ 的 Hash 环。当 Key 命中虚拟节点时，自动通过映射关系路由回实际的物理节点，达成完美的负载均衡。

开启下一个核心：Slide 7 · Memcached 与 Redis 全方位多维度硬核对比

核心架构启示 (Consistent Hashing Insight)

一致性 Hash 算法通过**将哈希空间构造成闭环**并配合**虚拟节点打散技术**，完美兼顾了分布式集群扩缩容时的“最小化数据迁移”与“极致负载均衡”，是 Memcached 客户端路由与分布式数据库路由的核心基石。

Speaker Notes / 讲师讲稿
🎯 引导学员理解取模算法与一致性 Hash 环的本质差异： “向学员做解构说明：很多初学者不明白为什么不能简单用 $hash(key) \pmod N$。请大家看左边：如果集群有 10 台机器，挂掉 1 台后变成除以 9，导致 90% 以上的 Key 路由全部错乱！而一致性 Hash 构造了一个 $0 \sim 2^{32}-1$ 的闭环，机器和数据都在环上，增加或减少节点只会影响局部区间，避免了全网失效。”
💡 强调虚拟节点 (Virtual Nodes) 解决数据倾斜： “请学员重点关注右侧的虚拟节点机制：如果只有 3 台物理节点，它们在环上的位置可能相距很近，导致大部分流量涌入同一台节点（数据倾斜）。通过给每台物理节点分配 100~200 个虚拟节点并打散映射，就能完美实现均摊流量。下一个 Slide 7 将对 Memcached 与 Redis 进行全方位多维度对比。”
