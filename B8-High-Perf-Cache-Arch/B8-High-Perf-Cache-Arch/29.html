1. 原生 `SETNX` 加锁误区、Lua 解锁与看门狗续期

Watchdog Mechanism
加锁指令与 Lua 脚本解锁 (Lua Atomic Unlock) Prevent Mis-deletion

加锁使用 `SET lock_key token NX EX 30`。直接使用 `DEL` 可能会误删其他线程拿到的锁！解锁必须使用 Lua 脚本保证**“校验 token + 删除”**的物理原子性：

// Lua 脚本原子解锁
if redis.call('get', KEYS[1]) == ARGV[1] then
return redis.call('del', KEYS[1])
else return 0 end
Redisson 看门狗 (Watchdog) 自动续期原理 Every 10 Seconds Check

• **痛点**：若业务执行超时（如 GC 卡顿 35 秒），锁在 30 秒过期释放，其他线程就会并发抢到锁导致数据不一致。
• **解法**：获取锁成功后（未显式设定 leaseTime），Redisson 启动一个后台定时任务（Watchdog）。每隔 10 秒（`lockWatchdogTimeout / 3`）检查，若当前线程依然持有锁，**自动将锁过期时间重置续期为 30 秒**，直到线程显式 `unlock()`。

特点：Lua 脚本解决误删，Watchdog 解决长业务超时提前释放

2. 主从故障切换丢锁痛点与 RedLock 红锁算法

RedLock Quorum
主从异步复制引发的锁丢失痛点 (Failover Lock Loss) Race Condition

由于 Redis 主从复制是**异步**的：线程 A 在 Master 节点加锁成功，尚未同步给 Slave 节点，此时 Master 突发物理宕机；Sentinel 哨兵将该 Slave 升级为新主，线程 B 去新主成功加锁，**导致两个线程同时持有同一把分布式锁！**

RedLock (红锁) 算法共识判定规则 N/2 + 1 Majority

部署 $N$ 个（通常 $N=5$）**完全相互独立的 Redis Master 节点**（无主从/集群关系）：
1. 客户端按顺序向 5 个独立 Master 节点依次发送加锁指令（带微秒级超时）；
2. 只有当客户端在**多数节点 ($\ge \frac{N}{2} + 1 = 3$ 个)** 上均成功获取锁，且**总耗时小于锁有效时间**时，才判定红锁获取成功！

RedLock 锁有效性数学判定
$$\text{Valid Time} = \text{Initial TTL} - \text{Elapsed Lock Time} - \text{Clock Drift}$$

核心架构启发 (Distributed Lock Design Insight)

分布式锁选型体现了极强的场景权衡：普通高并发场景使用 **`SETNX` + Lua 脚本 + Redisson 看门狗** 即可兼顾极速性能与自动续期；面对对数据准确性有绝对硬性要求（如金融扣款）且无法容忍主从切主丢锁的场景，则需要部署 **RedLock 多主节点共识算法** 筑牢防线。
