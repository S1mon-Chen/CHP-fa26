Redis 数据结构 2：Hash 对象物理内核 (ziplist/listpack 与 dict 渐进式 Rehash)

Dual Encoding (ziplist/listpack vs. hashtable), Compact Memory Layout & Non-Blocking Progressive Rehash

1. Hash 对象的底层双重编码转换 (ziplist/listpack $\to$ dict)

Dual Encoding

Redis 中的 Hash 对象不是单一数据结构，而是依据字段数量与元素大小在 **ziplist/listpack**（紧凑内存）与 **dict**（哈希表）之间自动平滑切换：

// 1. 小数据量：ziplist / listpack (连续物理内存块)
[zlbytes][zltail][len][ field1 ][ value1 ][ field2 ][ value2 ][zlend]

键与值相邻连续存储。省去了指针开销与内存碎片，CPU L1/L2 缓存命中率极高。

自动编码转换阈值 (`redis.conf`) 512 entries & 64 bytes
  • • hash-max-ziplist-entries 512：Hash 包含字段数小于 512 个。
  • • hash-max-ziplist-value 64：每个字段与值的字符串字节数均不大于 64B。
  • • **Redis 7.0+ 优化**：使用 `listpack` 替换 `ziplist`，彻底解决了 `ziplist` 级联更新（Cascade Update）隐患。
本质：极小数据量用连续内存榨干硬件 Cache 效率，大数据量自动升轨哈希表

2. Dict 字典结构与渐进式 Rehash (Progressive Rehash)

Zero Blocking
// Redis dict 双哈希表物理结构
typedef struct dict {
dictht ht[2]; // 包含 ht[0] (旧表) 和 ht[1] (扩容/缩容新表)
long rehashidx; // -1 表示未在 rehash，>=0 表示当前迁移的 bucket 索引
} dict;
渐进式 Rehash 拆分迁移流管线 Step-by-Step
  • 1. 分配新表：为 ht[1] 分配双倍空间，重置 rehashidx = 0。
  • 2. 分摊迁移：后续每次执行对当前 dict 的增删改查时，**顺带将 ht[0] 索引在 rehashidx 上的所有键值对迁移至 ht[1]**，随后 rehashidx++。
  • 3. 后台协助：定时任务 (serverCron) 空闲时分批抽样帮拉迁移。
  • 4. 切换释放：迁移完毕后，ht[1] 替换 ht[0]，重置 rehashidx = -1，释放旧表。
开启下一个核心：Slide 12 · List 对象与 quicklist / listpack 链表物理结构

核心数据结构启发 (Hash Architecture Insight)

Redis 的 **渐进式 Rehash (Progressive Rehash)** 机制展示了极具智慧的平滑工程哲学：如果将数百万个 Key 一次性 Rehash，会导致 Redis 单线程主线程卡顿数百毫秒；而将其拆分平摊到后续的每一次读写操作与定时 Cron 中，既完成了平滑扩容，又保障了微秒级的极速响应。
