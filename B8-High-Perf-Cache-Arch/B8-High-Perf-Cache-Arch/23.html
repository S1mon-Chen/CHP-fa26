1. 集群在线扩容 (Resharding) 与槽位平滑迁移

Resharding Pipeline

在不停止服务的前提下，通过 redis-cli --cluster reshard 指令，可动态将一部分哈希槽从源节点转移到新加入的 Master 节点：

// 槽位 (Slot S) 迁移四大步骤管线
1. 设置目标节点状态: CLUSTER SETSLOT S IMPORTING <source_node_id>
2. 设置源节点状态: CLUSTER SETSLOT S MIGRATING <target_node_id>
3. 获取并原子迁移 Key: MIGRATE target_ip port "" 0 timeout KEYS key1 key2
4. 广播更新槽位归属: CLUSTER SETSLOT S NODE <target_node_id>
`-ASK` 重定向与 `ASKING` 命令处理时序 -ASK Transit Interception

当请求命中处于 MIGRATING 状态的槽位时：若 Key 仍留在源节点直接处理；若 Key 已迁走，源节点返回 `-ASK S Target_IP:Port`。客户端先向目标节点发送 ASKING 命令开启一次性临时访问权限，再重新发送原读写指令。

区别：-MOVED 更新本地长久缓存，-ASK 不更新本地缓存（仅限迁移中途）

2. Gossip 协议通信与 Cluster 原生自动故障转移

Gossip & Failover
Gossip 协议 4 大核心报文 (Cluster Bus 端口 16379) Decentralized
MEET 握手邀请新节点加入集群
PING / PONG 每秒随机心跳，交换槽与状态
FAIL 确认 Master 宕机，广播强制下线
PUBLISH 集群内部广播 Pub/Sub 消息
// Cluster 无 Sentinel 依赖的原生故障转移流管线
1. PFAIL (疑似下线):

节点超时未收到 `PONG` 响应，单方面在本地将目标标记为 `PFAIL`。

2. FAIL (确认下线):

半数以上健康 Master 节点均报告其为 `PFAIL`，广播 `FAIL` 消息，正式判定下线。

3. Slave 拉票选举与接管:

挂掉 Master 的健康的 Slave 向其他 Master 发起拉票。获得半数以上 Master 选票的 Slave 执行 `SLAVEOF NO ONE`，自动接管旧主的所有 Slot 哈希槽！

核心高可用启发 (Resharding & Gossip Insight)

Redis Cluster 展现了真正去中心化架构的工程之美：通过 **Gossip 协议** 实现全网节点状态的自愈与收敛，通过 **`-ASK` 拦截与 `MIGRATE` 指令** 完成无阻塞的在线热扩容，通过 **Master 纪元投票** 实现了无需外部 Sentinel 裁判的原生故障自愈。
