1. 16384 哈希槽 (Hash Slots) 计算与物理分布

CRC16 % 16384

为了打破单机内存上限与单线程性能瓶颈，Redis Cluster 采用无中心化切片架构。集群将物理数据空间逻辑划分为 **16384 个哈希槽 (Hash Slots)**：

哈希槽映射数学公式 (Slot Mapping Rule)
$$\text{Slot ID} = \text{CRC16}(Key) \pmod{16384}$$
// 3 主 3 从集群哈希槽分布范例
Node A (Master): Slots 0 ~ 5460
Node B (Master): Slots 5461 ~ 10922
Node C (Master): Slots 10923 ~ 16383
Hash Tag 强行槽位固定机制 {user100}:profile

使用大括号 `{}` 括起 Key 的一部分（如 `{user100}:profile` 和 `{user100}:orders`）。Redis 计算哈希槽时仅取 `{}` 内部字符，强行将关联数据路由至**同一个物理 Slot**，从而支持 Multi-key 批量操作与 Pipeline！

为什么是 16384 (16k)？平衡 Gossip 状态心跳包大小 (2KB bitmap) 与节点拓展规模

2. Smart Client 客户端路由与 MOVED / ASK 重定向

MOVED vs. ASK
Smart Client 槽位映射缓存 (JedisCluster / Lettuce) Client Routing

客户端启动时连接任意 Cluster 节点，获取全量 Slot-to-Node 映射关系并本地缓存。发送请求时先在本地计算 Slot，直连目标 Master 节点，实现真正的 **零 Proxy 代理性能**。

`-MOVED` 永久重定向 (Permanent Route Update) Update Cache

当客户端因缓存过期向 Node A 发送 Slot 5461 的请求，而 Slot 5461 实际已归属于 Node B 时，Node A 返回 `-MOVED 5461 127.0.0.1:6380`。客户端自动更新本地缓存并重试。

`-ASK` 临时重定向 (Temporary Resharding Transit) Resharding In Progress

在集群在线扩容槽位迁移 (Resharding) 过程中，目标 Key 正在从 Node A 迁移到 Node D。若 Key 在 Node A 找不到，Node A 返回 `-ASK 5461 NodeD_IP`。客户端先向 Node D 发送 `ASKING` 命令，再发送原读写请求，不更新本地路由表。

开启下一个核心：Slide 23 · Redis Cluster 在线扩容 (Resharding) 与 Gossip 协议

核心高可用启发 (Redis Cluster Slot Insight)

Redis Cluster 通过 **16384 哈希槽** 成功解耦了“物理节点”与“逻辑数据数据项”的硬编码绑定。无论是水平扩容还是故障切主，只需在节点间转移哈希槽，配合 Smart Client 的 **`-MOVED` / `-ASK` 重定向**，即可达成为平滑非阻塞的横向线性扩展。
