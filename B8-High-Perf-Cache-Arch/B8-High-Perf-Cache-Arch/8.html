Part 01 · 缓存架构基础与缓存模式

Caffeine + Redis 多级缓存架构 (Multi-Level Caching Architecture)

L1 Process Cache (Nanoseconds) + L2 Redis Cluster (Microseconds) & Pub/Sub Active Invalidation

1. 多级缓存穿透查询链路（L1 本地 + L2 分布式）

L1/L2 Pipeline
为何需要多级缓存？突破网络 Socket 物理延时 ns vs. ms

Redis 响应虽快，但单次跨网络 Socket I/O 仍需 0.5~2 ms。对于每秒数万 QPS 的超热点 Key（如秒杀商品、首页banner），网络传输会卡死网卡。JVM 进程内本地缓存（~10 ns）是终极加速方案。

三级查询过滤管线 (Query Pipeline) Zero Network Latency on L1 Hit
L1
Caffeine Local Cache (进程内内存)
直接读 JVM 内存，响应时间 ~10 ns，无网络序列化开销
Hit: ~10ns
L2
Redis Distributed Cluster (分布式缓存)
共享分布式缓存，跨节点访问，吸收 99% 的数据库流量
Hit: ~1ms
L3
MySQL Database (关系型数据库)
最终落盘数据库，写操作更新源头
Miss: ~10ms
架构效果：95% 流量被 L1 拦截，4.9% 流量被 L2 拦截，只有 0.1% 穿透至 DB

2. 多节点 L1 本地缓存一致性与主动失效广播

Invalidation Pub/Sub
多 JVM 节点的本地缓存数据漂移困境 (Data Drift) Stale Cache Risk

当某个节点修改了 DB/Redis 中的数据，微服务集群中其他 10 个 JVM 实例的 L1 Caffeine 依然保留旧值，导致不同用户看到不一致的脏数据！

广播主动失效机制（Redis Pub/Sub / Canal 广播） Broadcast Invalidation
1. App Instance 1: 修改 DB 并删除 Redis L2 数据
2. App Instance 1: PUBLISH cache_channel "invalidate:item:1001"
3. App Instance 2~N: 收到消息，自动清除本地 Caffeine L1 的 item:1001
高性能本地缓存之王：Caffeine W-TinyLFU

采用基于 W-TinyLFU (Window TinyLFU) 的淘汰算法，命中率远超传统 LRU，并基于 RingBuffer 实现近乎无锁的极端并发性能，彻底替代旧式 Guava Cache。

开启 Part 02：Slide 9 · Redis 单线程内核与 Redis 6.0+ 多线程 I/O 演进

核心架构启发 (Multi-Level Caching Insight)

**Caffeine (L1) + Redis (L2) 多级缓存** 是应对十万级 QPS 热点流量的终极方案。利用本地内存的极速响应（纳秒级）吸收读热点，再通过 **Redis Pub/Sub 广播事件** 解除各节点间的数据漂移，兼顾了极致性能与一致性安全。

Speaker Notes / 讲师讲稿
🎯 引导学员理解 L1 本地缓存 + L2 分布式缓存的组合优势： “向学员解构说明：即使 Redis 性能再强，请求也要经过 TCP 协议栈和跨网络传输，响应在 1ms 左右。而在 JVM 进程内放一层 Caffeine（L1），直接读取 Java 对象内存，延时只有 ~10ns，并且完全不占用网卡带宽！这是防范热点 Key 冲垮 Redis 集群的必备利器。”
💡 剖析多节点一致性与广播失效模式： “请学员特别注意右侧的数据一致性难题：当节点 1 修改了数据并清除了 Redis，节点 2 的 Caffeine 里还存着旧数据。解决方法是利用 Redis Pub/Sub 或 Canal 监听到 DB 变更后广播发送 `CacheInvalidateEvent`，通知集群内所有微服务实例同步清除各自的 Caffeine 缓存。这标记着 Part 01 结束，下一个 Part 02 (Slide 9) 将开启对 Redis 多线程 I/O 与底层核心数据结构源码的剖析。”
