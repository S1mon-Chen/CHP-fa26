Part 02 · Redis 内部内核与核心数据结构

Redis Key 过期删除策略 (Lazy Eviction & Periodic Scanning)

Why No Timer Deletion, Lazy Eviction, Active Expiration Cycle (`activeExpireCycle`) & Dual Defense Lines

1. 惰性删除 (Lazy Eviction) 与周期抽样 (Periodic Scan) 组合拳

Dual Strategy

为每个 Key 创建硬件定时器（Timer）会在同一秒大量 Key 过期时瞬间拉爆单线程 CPU。Redis 采用**被动惰性 + 主动周期抽样**组合：

1. 惰性删除 (Lazy Eviction - 被动防御) On-Demand Check

客户端访问任何 Key（如 `GET/EXISTS`）时，Redis 会先调用 expireIfNeeded() 校验其 TTL。若已过期，立即从内存删除并返回 `NULL`。**最大化节省 CPU，但长期未被读到的冷 Key 会滞留内存**。

2. 周期抽样删除 (Active Expire - 主动扫描) serverCron (10 Hz)

Redis 后台定时任务（每秒执行 10 次）触发 activeExpireCycle()： • 从过期字典 (`expires`) 中**随机抽取 20 个 Key** 进行检查； • 清理其中已过期的 Key； • 若过期 Key 占比 **超过 $25\%$**，认为集中过期爆发，**立即重复抽样清理**（每次有最高 CPU 时间限额，防卡死主线程）。

本质：极低 CPU 消耗下的概率平衡——用 25% 概率阈值阻断过期 Key 堆积

2. 过期删除 (Expiration) 与主动淘汰 (Eviction) 双重防线

Dual Defense Line
// Redis 内存安全双重防御防线模型
防线 1: 过期 TTL 机制 (Expiration) Lazy + Active 20 Sampling

处理设定了 TTL 的 Key。绝大多数过期 Key 在访问或抽样时被清理。

若大量 Key 已过期，但既未被访问，也未在随机抽样中被抽中（极小概率漏网）...
防线 2: maxmemory-policy 淘汰策略 (Eviction) Volatile-TTL / LRU / LFU

最终保底屏障！当物理内存触发 maxmemory 时，按 Slide 16 的 8 大策略（如 `volatile-ttl`）强制物理剔除！

核心对比：过期删除 vs. 内存淘汰 Expiration vs. Eviction
  • • **过期删除 (Expiration)**：针对**业务设置了 TTL 生存时间**的 Key，时间到期后进行清除。
  • • **内存淘汰 (Eviction)**：针对**物理内存达到 `maxmemory` 上限**时，按配置策略强行剔除 Key。
开启 Part 03：Slide 18 · RDB 快照与 Copy-on-Write (COW) 内存持久化原理

核心架构启发 (Key Expiration Design Insight)

Redis 的 Key 过期策略体现了极高水平的 CPU 与内存平衡艺术：通过**惰性删除**保障零额外 CPU 预开销，通过**25% 概率抽样循环**控制过期 Key 规模，最终依靠 **`maxmemory-policy` 淘汰策略** 作为物理底线，构筑了坚不可摧的内存安全体系。
