Redis 数据结构 3：List 对象物理内核 (quicklist 与 listpack)

Evolution from ziplist/linkedlist to quicklist & listpack, Contiguous Memory Locality & LZF Compression

1. List 底层演进 (ziplist/linkedlist $\to$ quicklist $\to$ listpack)

quicklist Structure

Redis 中的 List 经历了三次重大架构演进。为了兼顾链表的灵活增删与连续内存的高 CPU Cache 命中率，自 Redis 3.2 引入了 **quicklist**：

// Quicklist 物理双向链表 + 紧凑内存块结构
head ──► [ quicklistNode 1 ] <══> [ quicklistNode 2 ] <══> [ quicklistNode 3 ] ──► tail
• Node 1: [listpack: e1, e2, e3, e4] (头节点未压缩，保速)
• Node 2: [LZF Compressed listpack] (中间节点 LZF 压缩，省内存)
• Node 3: [listpack: e9, e10, e11] (尾节点未压缩，保速)

Redis 7.0+ 将 quicklist 节点内部的 `ziplist` 全面替换为 `listpack`，消除了级联更新隐患。

List 数据结构三代演进阶段 Redis 3.2 / 7.0 Milestone
  • • **第一代 (Redis < 3.2)**：小数据用 `ziplist`，大数据升轨为 `linkedlist`（指针开销大，内存碎片严重）。
  • • **第二代 (Redis 3.2+)**：统一使用 `quicklist`（双向链表 + ziplist 结合体）。
  • • **第三代 (Redis 7.0+)**：将 quicklist 节点的内部存储升级为 **`listpack`**。
本质：用双向链表串联中等尺寸的连续字节数组，平衡指针开销与内存重分配

2. Quicklist 内存压缩与参数配置 (`redis.conf`)

LZF & Size Tuning
1. 节点字节上限控制 (`list-max-listpack-size`) Default: -2 (8 KB)

控制每个 quicklistNode 绑定的 listpack 字节大小。负数代表限制最大字节数（-2 对应 **8 KB**），正数代表限制元素个数。太小退化为普通双向链表；太大退化为连续巨块内存。

2. 中间节点 LZF 压缩深度 (`list-compress-depth`) Default: 0 (No compress)

List 的 `LPUSH`/`RPOP` 操作大多集中在两端。设置深度（如设为 1）代表**首尾各 1 个节点不压缩**，中间的节点全部采用 **LZF 压缩算法** 高倍率压缩，极大地提升高并发下的内存利用率。

// quicklistNode 物理结构体
typedef struct quicklistNode {
struct quicklistNode *prev; // 前驱节点
struct quicklistNode *next; // 后继节点
unsigned char *entry; // 指向 listpack / compressed 结构
size_t sz; // listpack 内存字节数
unsigned int encoding:2; // RAW=1 或 LZF=2
} quicklistNode;

核心数据结构启发 (Quicklist Architecture Insight)

Redis 的 **`quicklist`** 是空间与时间权衡的经典工程结晶：通过在“链表”的节点中嵌入“连续字节数组 (listpack)”，既享受了连续内存对 CPU L1/L2 缓存的极高命中率，又规避了单个巨型连续内存块分配与扩容的开销。
