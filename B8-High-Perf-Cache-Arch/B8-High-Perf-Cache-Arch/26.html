缓存雪崩治理与多级防御防线 (Cache Avalanche & Multi-Layer Defense)

Mass Expiration Random Jitter, Redis Node Crash Failover, Sentinel Rate Limiting & Local Degradation

1. 缓存雪崩 (Cache Avalanche) 产生原因与集中过期治理

Mass Expiration
缓存雪崩两大诱因 (Two Core Causes) System Disaster

• **诱因 1 (Key 集中过期)**：大量缓存 Key 设置了相同的过期时间（如零点更新），在同一秒内同步失效；
• **诱因 2 (Redis 节点崩溃)**：Redis 实例或集群宕机（OOM、网络切断），缓存服务全面瘫痪。海量请求如雪崩般直接砸向底层 DB。

治理方案 1：离散随机 TTL 消除集中过期 (Random Jitter) TTL + Random

为原本定时的缓存 TTL 加上一个随机离散波动值（如 1~300 秒），使 Key 的失效时间均匀错开打散，杜绝同一时刻集中过期。

$$\text{TTL} = \text{BaseTTL} + \text{Random}(1, 300\text{ seconds})$$
治理方案 2：热点数据提前预热与逻辑过期 Pre-warming

大促前对秒杀与热搜 Key 进行后台定时任务提前**数据预热**；结合 Slide 25 的**逻辑过期机制**，实现零等待后台异步重构。

核心：打散物理失效点，让流量冲击平滑分散在不同时间轴上

2. Redis 宕机崩溃防护与多级熔断降级体系

Multi-Layer Defense
1 防线一：Redis Cluster / Sentinel 高可用拓扑 Auto Failover

部署 3 主 3 从切片集群（Cluster）或哨兵（Sentinel）集群。单节点挂掉后，自动在微秒级切主升级恢复服务，保障系统不间断。

2 防线二：网关与 API 限流熔断 (Sentinel / Resilience4j) Rate Limiting

针对 DB 的承载上限设置限流关口（如最多允许 2,000 QPS 穿透至 DB）。超出的流量直接触发**熔断关口**并快速拒绝，保护数据库不崩溃。

3 防线三：本地 Caffeine 进程内缓存与静态降级页 Local Fallback

开启 JVM 内的 Caffeine 本地二级缓存（Slide 8）。当 Redis 完全挂掉时，直接返回 JVM 内存旧数据或默认静态托底 JSON 页面。

开启下一个核心：Slide 27 · 缓存与数据库双写一致性 (Dual-Write Consistency) 与 Canal 治理

核心架构启发 (Cache Avalanche Defense Insight)

防范缓存雪崩需要构建纵深防御体系：简单的数据离散使用 **`TTL + Random` 抖动算法** 规避；面对节点宕机物理故障，则靠 **Cluster 高可用 + Sentinel 限流熔断 + Caffeine 本地二级缓存** 层层拦截，确保核心 DB 固若金汤。

🎯 引导学员区分“缓存击穿”与“缓存雪崩”： “向学员做解构说明：缓存击穿是**单个超级热点 Key 过期**；而缓存雪崩是**海量 Key 集中在同一秒集中过期**，或者 **Redis 服务节点整机崩溃**。解决雪崩需要分层治之：针对 Key 集中过期，使用 `TTL + Random(1-300s)` 随机抖动算法打散时间；针对节点崩溃，使用 Redis Cluster 高可用 + Sentinel 限流熔断 + Caffeine 本地二级缓存。”
💡 剖析多级降级与 Sentinel 限流防线： “请学员重点关注右侧防线 2 和防线 3：如果 Redis 完全崩溃，最可怕的是海量并发流量直接压垮 DB。因此必须在网关或应用层加 Sentinel/Resilience4j 限流熔断，多余的流量直接返回托底静态页或 HTTP 429。下一个 Slide 27 将探讨**数据库与缓存的双写一致性 (Dual-Write Consistency)** 治理。”
