Part 01 · 缓存架构基础与缓存模式

四大核心缓存设计模式 (Four Core Cache Patterns)

Cache-Aside, Read-Through, Write-Through & Write-Behind Architecture Patterns

1. Cache-Aside Pattern (旁路缓存模式 - 工业标准)

Most Popular

应用代码同时直接操控 Cache 与 Database，将缓存视为独立于数据库之外的旁路辅助存储。

读请求流程 (Read Pipeline)
Client ──1. Query──► Cache ──[Hit?]──► Return Data
└──[Miss?]──► Read DB ──► Write Cache ──► Return
写请求流程 (Write Pipeline)
Client ──1. Update DB──► Database
└──2. Delete/Invalidate Cache──► Cache (失效而非更新)
为什么淘汰缓存优先于更新缓存？防并发乱序写导致脏数据覆盖

2. Read-Through / Write-Through Pattern (读写穿透模式)

Proxy Layer

应用系统将缓存层当作唯一的主数据源 (Main Data Store)，所有对 DB 的读写均由 Cache Provider 统一代理。

Read-Through (读穿透)

应用查 Cache，未命中时由 Cache 服务组件透明地负责从 DB 加载数据并填入 Cache，再返回给应用。

Write-Through (写穿透)

应用更新 Cache，由 Cache 组件**同步**将新数据写入底层 DB。写操作完成后才返回成功。

特点：应用层代码与 DB 彻底解耦，但需要专门的 Cache Provider 插件支持

3. Write-Behind / Write-Back Pattern (异步写回模式)

Ultra-High Throughput

写请求直接更新内存 Cache 并立刻返回。后台独立线程**异步、批量**将脏页 (Dirty Pages) 刷新写入 DB。

1. Client ──Write──► Cache (Mark Dirty) ──► Return Immediately! (极大低延时)
2. Background Thread ──Async Batch Flush (每 5 秒 / 1000 条)──► DB
权衡与适用场景 (Trade-offs)

优点：写入吞吐量极高，大幅减少 DB 磁盘 I/O。缺点：若内存 Cache 突然宕机，未刷盘的脏数据将永久丢失。适用于点赞数、浏览量统计等允许轻微丢失的场景。

本质：牺牲部分持久性换取极致的写性能，常配合 WAL 日志弥补

4. 4 大缓存模式综合选型矩阵 (Pattern Comparison Matrix)

Decision Guide
模式类型 读延迟 写吞吐 数据丢失风险 典型适用场景
Cache-Aside 低 (Hit 时) 一般 (受限于 DB) 无 (DB 事务保证) 绝大多数读多写少互联网业务
Read-Through 极低 受限于 DB 无 带有专门 Cache 中间件的服务
Write-Through 极低 受限于 DB 同步写 无 要求缓存与 DB 强同步更新
Write-Behind 极低 极致 (内存直接写) 有 (宕机丢未刷脏数据) 高频计数器、点赞数、文章浏览量

核心架构启示 (Caching Pattern Insight)

在分布式服务端开发中，Cache-Aside 旁路缓存模式是应用最为广泛的工业标准。处理写请求时，请务必记住**“先更新数据库，再失效删除缓存”**，这是保障数据一致性的黄金法则。
