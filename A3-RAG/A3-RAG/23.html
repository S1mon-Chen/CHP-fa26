数据流的实时动态更新 (Incremental ETL Pipeline)

Static Demo vs. Dynamic Production

全量重构的昂贵瓶颈：现实业务中数据每时每刻都在增删改查。直接使用 Demo 阶段的“推倒全量重建”方案在千万级规模下会导致持续数小时的 CPU 瘫痪与检索中断，必须引入增量索引机制。

Incremental Pipeline Architecture
  • ● 哈希指纹校验 (MD5 Check)：在进入文本解析前，为每个物理源文件计算唯一的哈希指纹。若指纹未变，则直接智能跳过，避免无效的 Embedding 算力。
  • ● 实体映射解耦 (Mapping Table)：维护一套映射关系：Document_ID ➔ List[Chunk_IDs]。
  • ● 原子级先删后插：检测到哈希变化时，利用 Chunk_IDs 批量在向量数据库执行物理擦除，随后重新切分、向量化并原子的追加新向量。

def sync_document_index(doc_id: str, content: str) -> None:
    new_hash = calculate_md5(content)
    if new_hash == get_stored_hash(doc_id):
        return  # 哈希未发生变动，智能跳过，省下 100% Embedding 算力
    
    # 1. 顺着关系映射表，批量物理擦除数据库中的旧段落向量
    old_chunk_ids = get_mapped_chunk_ids(doc_id)
    db.batch_delete(collection="enterprise_kb", ids=old_chunk_ids)
    
    # 2. 重新对变动文本进行清洗、切块并向量化提取
    chunks = sliding_window_chunker(content, size=512, overlap=100)
    embeddings = [get_embedding(c) for c in chunks]
    
    # 3. 批量追加插入新向量，并原子更新哈希指纹和映射表
    new_ids = db.batch_insert(collection="enterprise_kb", vectors=embeddings)
    update_mapping_table(doc_id, hash_val=new_hash, chunk_ids=new_ids)
高可用生产法则 (Zero-Downtime Pipeline)： 增量更新流水线的本质是维护“关系一致性”。切勿在删除旧向量后留下悬挂指针，批量物理 `delete` 与批量原子 `batch_insert` 必须配合宿主进程形成保护事务。这是在大规模高并发、数据流多变状态下，守护整个企业级 RAG 检索端到端零停机持续可用（Continuous availability）的唯一出路。
