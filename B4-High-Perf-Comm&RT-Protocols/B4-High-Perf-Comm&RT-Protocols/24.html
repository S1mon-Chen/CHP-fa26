传统 HTTP 轮询 vs. WebSocket 全双工实时通信

HTTP Short/Long Polling Bottlenecks, 101 Switching Protocols & Minimal Framing Overhead

1. 传统 HTTP 轮询机制及其架构瓶颈 Polling Limitations

传统 HTTP 协议是**单向请求-响应范式**，服务器无法主动向客户端推送数据。为了获得实时状态更新，早期 Web 架构衍生出“短轮询”与“长轮询”，但带来极其高昂的网络与计算开销。

① 短轮询 (Short Polling) High Overhead

客户端每隔固定的 $T$ 秒（如 1 秒）强行发送一次 HTTP `GET` 请求。即使服务端没有任何新消息，也必须应答 `200 OK` 空数据包，造成大量空刷请求，造成严重带宽与 CPU 浪费。

② 长轮询 (Long Polling / Comet) Server Hold

服务端接收请求后**挂起**（Hold）连接，直到有新数据产生或发生超时（Timeout）才返回响应。虽然降低了无用请求次数，但**每次数据传输仍需携带完整 HTTP Header（约 500B ~ 2KB）**，且频繁重新握手。

③ 报头开销与全双工缺失 (Header Bloat) 800B vs 2B

在每秒高频推拉 1 字节状态时，HTTP 报文高达 800 字节的 Cookie、User-Agent 等 Header 使得有效数据负载率不足 **0.2%**，严重制约高并发拓展。

本质矛盾：HTTP 单向无状态与实时双向交互需求之间的天然错位
2. WebSocket 全双工长连接与 101 协议升轨 WebSocket 101 Handshake
① HTTP 101 Switching Protocols 协议升轨握手 RFC 6455
// 客户端请求 Upgrade
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhl...==
// 服务端响应 101 升轨
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pP...=
② 通信范式时序对比 (Sequence Comparison) Full-Duplex TCP
短轮询 Client --GET (Header 800B)--> Server --Empty 200--> Client (重复触发)
长轮询 Client --GET--> Server (Hold 挂起) --Data--> Client (重新连接)
WebSocket 持久 TCP 管道: Client <=== 2 字节极简帧 (Full-Duplex) ===> Server
开启下一个核心：Java API 原生 WebSocket 注解 (`@ServerEndpoint`) 实现 (Slide 25)

核心架构启发 (WebSocket Full-Duplex Paradigm)

WebSocket 通过标准的 **HTTP 101 Switching Protocols** 将单向短连接协议无缝“升级”为**持久化全双工 TCP 管道**。连接建立后仅需 2–10 字节的极简帧头，彻底摆脱了 HTTP 头部冗余与轮询开销。
