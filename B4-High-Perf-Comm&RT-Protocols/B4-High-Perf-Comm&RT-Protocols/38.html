Q3: 实时推流的方向性？
单向推流 (AI/日志/通知) $\to$ SSE

选型法则：无万能协议，依据通信边界、方向性与载荷特性做出组合拳选型
2. 协议选型核心架构维度权衡 (Architectural Trade-offs) Trade-off Matrix
① 性能吞吐 vs 可读性/可调试性 Performance vs Readability

gRPC (Protobuf) 牺牲了人类直观可读性，换取了 6~10 倍的极速二进制序列化与 HTTP/2 多路复用，是内网微服务 IPC 的不二之选；而 REST / JSON 则保留了极致的可调试性。

② 前端开发敏捷度 vs 服务端复杂度 Agility vs Backend Complexity

GraphQL 给予了前端自由拣选数据树的极大灵活性，但服务端必须引入 DataLoader（如 `@BatchMapping`）治理 N+1 数据库瓶颈与防范恶意复杂 AST 嵌套查询攻击。

③ 状态治理重度 vs 架构轻量化 Stateful vs Stateless

WebSocket 需要在微服务集群中维持分布式 Session 记忆（需 Kafka/Redis Pub/Sub 挂接）；而 SSE 纯 HTTP 语义完美兼容无状态网关与代理，为大模型流式输出节省了巨量治理成本。

核心架构选型启发 (Protocol Decision Golden Rule)

架构师的修养在于拒绝对协议盲目“一刀切”。**“对外暴露采用 REST/GraphQL，内网高性能互调采用 gRPC，双向竞技交互选用 WebSocket，AI 流式输出选用 SSE”** 的混合组合拳，是现代化后端架构的黄金标准。
