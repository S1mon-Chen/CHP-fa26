何时首选 WebSocket？ Full-Duplex

当业务需要**高频、低延迟的客户端与服务端双向数据对等交互**（如在线即时通讯、多人协同画布、高频证券交易双向指令）时，WebSocket 是不可替代的方案。

何时首选 SSE？ Server Push

当业务主要是**服务端单向推流，客户端仅需普通 HTTP 发起触发**（如 AI 大模型 LLM 打字机输出、实时控制台日志、订单状态跟踪）时，SSE 以其极简性与原生的断线重连体验胜出。

何时考虑 Long Polling？ Legacy Fallback

长轮询仅作为**异构网络受限或老旧客户端的兜底方案 (Fallback)**。在现代 Web 架构中，应尽可能通过 SockJS 或 EventSource 自动将其退避至最低优先级。

架构选型金律 (Real-Time Architecture Rule of Thumb)

切忌盲目追求全双工！**“能用单向 HTTP/SSE 解决的场景（如 LLM 输出、日志监控），决不引入复杂的 WebSocket 握手与分布式集群 Session 治理”**，是现代化服务端轻量化演进的核心原则。

Speaker Notes / 讲师讲稿
🎯 引导学员理解选型权衡： “向学员强调：不要盲目崇拜全双工！许多开发者一听到‘实时推送’就无脑选择 WebSocket，结果在集群部署时被分布式 Session、握手心跳和鉴权治理搞得头破血流。如果场景仅仅是服务端向客户端单向推流（如大模型生成回答），SSE 才是性价比极高且对防火墙/HTTP2 极度友好的第一选型。”
💡 剖析自动重连与状态追溯机制： “请学员关注表格中的‘断线自动重连’一栏：SSE 内置了 W3C 标准的自动重连，并且会自动带上请求头 `Last-Event-ID`，让服务端补发断连期间漏掉的消息；而 WebSocket 本身不带重连机制，必须在应用层（如 STOMP/SockJS）手写重连和 ACK。”
