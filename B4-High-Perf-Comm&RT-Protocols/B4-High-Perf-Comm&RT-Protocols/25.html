WebSocket 101 协议升轨与安全签名握手机制

HTTP/1.1 Upgrade Request, `Sec-WebSocket-Key` SHA-1 Signature & Minimal Framing Overhead (RFC 6455)

1. HTTP 101 升轨与 Sec-WebSocket-Key 握手过程 101 Upgrade

WebSocket 借用 HTTP 的 80/443 端口完成初始建立。客户端通过发送带有 Upgrade: websocket 的 HTTP GET 请求，并在服务端确认应答 **HTTP/1.1 101 Switching Protocols** 后，底层 TCP 连接脱离 HTTP 状态机，正式升轨为全双工双向 WebSocket 管道。

① Sec-WebSocket-Accept 签名计算公式 RFC 6455 GUID

为防止中继代理（Proxy）误将 WebSocket 响应作为缓存应答，RFC 6455 规定服务端将客户端发来的 Sec-WebSocket-Key 拼接固定 Magic GUID，再经 **SHA-1** 散列和 **Base64** 编码：

Accept = Base64( SHA1( Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )
② 握手校验与反误连防护 (Handshake Validation) Anti-Proxy Mistake

该握手算法**并非用于数据加密**，而是证明两端均显式支持 WebSocket 协议，确保透明代理服务器不会将后续连续的二进制数据帧误识别为异常 HTTP 报文。

③ 客户端出站强制掩码 (Client-to-Server Masking) 4-Byte Mask Key

RFC 6455 强制规定：**客户端发往服务端的每一帧数据必须用 4 字节的随机 Mask Key 进行 XOR 掩码遮蔽**，防止代理缓存中毒攻击；而服务端发往客户端的数据帧**决不加掩码**。

握手本质：通过 101 状态码无缝借道 HTTP 80/443 端口穿透企业防火墙

核心架构启发 (WebSocket Handshake & Framing Insight)

WebSocket 的精妙之处在于**借道 HTTP 80/443 端口进行 101 升轨握手，握手成功后立刻切入极简二进制帧模式**。控制帧（Ping/Pong 心跳）与 2 字节的基础帧头保证了在高频实时通信下的极低延迟与 CPU 零开销。

Speaker Notes / 讲师讲稿
🎯 剖析 Sec-WebSocket-Key 的计算公式： “向学员做算法演示：`Sec-WebSocket-Key` 是客户端生成的 16 字节随机数 Base64 字符串。服务端拿到后，将其与 RFC 6455 规定的固定魔数 GUID (`258EAFA5-E914-47DA-95CA-C5AB0DC85B11`) 拼接，做 SHA-1 散列后再打成 Base64，写入 `Sec-WebSocket-Accept` 响应头。这一设计确保了该响应绝不会被普通 HTTP 缓存代理误缓存。”
💡 强调 WebSocket 帧格式与掩码掩盖： “请学员关注右侧的帧比特分布：WebSocket 消息帧头部最小仅 2 字节（对比 HTTP 的 800 字节）。还要注意 MASK 位：客户端发往服务端的数据必须用 4 字节掩码 key 进行异或掩盖，这是为了防范透明中间代理上的缓存中毒攻击（Proxy Cache Poisoning）。”
