gRPC 4 种核心服务调用模式 (1)：Unary 与 Server Streaming RPC

Service Call Patterns: Unary RPC (Request-Response) & Server Streaming RPC (Stream Response)

1. 一问一答 RPC (Unary RPC) Request-Response

最经典的 RPC 调用模式。客户端发送**单个请求**至服务端，并获取**单个响应**，使用体验与传统本地同步方法调用极其相似。

// 契约定义: 单个 Request 映射单个 Response
service SimpleService {
rpc SayHello (HelloRequest) returns (HelloReply);
}
HTTP/2 帧传输交互流 (Unary Frame Flow) Single Stream ID
Client HEADERS Frame + DATA Frame (End of Stream) → Server
Client ← HEADERS Frame + DATA Frame + HEADERS (EOS + Status) Server
**同步/异步双持**：支持 BlockingStub 同步挂起，亦支持 StreamObserver 异步回调。
**典型场景**：数据中心内网微服务常规 CRUD、鉴权校验与账户查询。
特点：单一 Request 带来最简单清晰的死锁与超时控制
2. 服务端流式 RPC (Server Streaming RPC) Stream Response

客户端发送**单个请求**，服务端返回一个**持续递送的消息流 (Stream)**。客户端从中按顺序持续读取，直到服务端关闭 Stream（发送 `onCompleted`）。

// 契约定义: 使用 stream 关键字标记 Response 类型
service SimpleService {
rpc StreamHello (HelloRequest) returns (stream HelloReply);
}
HTTP/2 帧传输交互流 (Server Stream Flow) Continuous Chunk Delivery
Client REQ (Single DATA Frame) → Server
Client ← RESP Chunk 1 | RESP Chunk 2 | ... | Chunk N Server
Client ← HEADERS Frame (Status: OK / End-of-Stream) Server
**内存友好**：支持大数据量分块增量传输，无需在服务端一次性拼装巨型数组防爆内存。
**典型场景**：实时日志流推送、股票/金融行情变动订阅、大数据导出报表。
下一个核心：客户端流式 (Client Streaming) 与双向流式 (Bidi Streaming) RPC (Slide 8)

核心架构启发 (Stream Semantics Insight)

在 Protobuf 接口契约中增加一个 stream 关键字，底层机制将完全改变：**底层 HTTP/2 链接不会在一次传输后关闭，而是持续保留 Stream 管道进行连续二进制块分发**。
