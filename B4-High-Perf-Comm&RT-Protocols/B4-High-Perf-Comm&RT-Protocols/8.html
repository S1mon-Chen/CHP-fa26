gRPC 4 种核心服务调用模式 (2)：Client Streaming 与 Bidirectional Streaming RPC

Service Call Patterns: Client Streaming RPC (Stream Request) & Bidirectional Streaming RPC (Full-Duplex)

3. 客户端流式 RPC (Client Streaming RPC) Stream Request

客户端建立连接后通过流向服务端发送**持续的消息序列**，发送完毕后发送 `onCompleted`。服务端在接收完全部消息后，返回**单个响应**。

// 契约定义: 使用 stream 关键字标记 Request 类型
service SimpleService {
rpc LotsOfGreetings (stream HelloRequest) returns (HelloReply);
}
HTTP/2 帧传输交互流 (Client Stream Flow) Batch Data Upload
Client REQ Chunk 1 | REQ Chunk 2 | ... | Chunk N → Server
Client HEADERS Frame (EOS - End-of-Stream) → Server
Client ← RESP (Single DATA Frame) + HEADERS (EOS + Status) Server
**高效上载**：避免客户端批量数据积压一次性大 Body 发送造成的网络抖动与内存峰值。
**典型场景**：IoT 传感器高频打点上报、大文件/分块日志异步上传、客户端事件采集。
特点：客户端自主控制上报速率与结束信号 (EOS)
4. 双向流式 RPC (Bidirectional Streaming RPC) Full-Duplex Stream

客户端与服务端均在**同一个 HTTP/2 Stream** 上通过读写流**独立且并发地**发送消息序列。两端读写完全解耦，可按任意顺序交互。

// 契约定义: 在 Request 与 Response 均标记 stream
service SimpleService {
rpc BidiHello (stream HelloRequest) returns (stream HelloReply);
}
HTTP/2 帧传输交互流 (Bidi Full-Duplex Flow) Async Concurrent Streams
Client REQ Msg 1 → Server
Client ← RESP Msg 1 (Immediate or Delayed) Server
Client REQ Msg 2 →  |  ← RESP Msg 2 (Interleaved) Server
**全双工协同**：实现极低延迟的全双工管道，两端可在无需挂起等待的情况下实时交叉投递。
**典型场景**：实时聊天/音视频会话、多玩家在线游戏状态同步、AI 实时交互式打字机管道。
下一个核心：gRPC Stub 存根机制与同步/异步 API (Slide 9)

核心架构启发 (Full-Duplex Stream Flexibility)

通过将请求或响应声明为 stream，gRPC 彻底超越了传统 REST 的一问一答约束。**底层 HTTP/2 协议天然支持同一 TCP 连接上的交错帧传输，为高性能高并发流式系统提供了坚实的底座**。
