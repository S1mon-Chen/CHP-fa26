API Gateway Pattern, Blocking Servlet vs. Non-blocking Netty Reactive Model & Performance Shift

1. 为什么需要 API 网关模式？(Core Responsibilities)

Unified Entry

在微服务集群中，若客户端（移动端/Web/小程序）直接连接几十个微服务，会导致地址分散、重复鉴权以及跨域乱象。**API 网关是系统的统一反向代理入口**：

① 统一路由转发 (Smart Routing) Path / Host Matching

根据请求的 Path、Header 或 Parameter，隐藏内部微服务物理拓扑，将流量精确重写分发至目标后端。

② 统一安全鉴权 (Centralized Auth & CORS) JWT & CORS Global

在边界统一拦截并解包 JWT Token，防止非法请求切入内部网络；全局统一配置 CORS 跨域请求头。

③ 流量限流与容错降级 (Rate Limiting & Resiliency) Redis Token Bucket

挂载 Redis 令牌桶算法实施全局/用户级限流，配合断路器在后端异常时快速返回 Fallback 托底响应。

本质：将横切面关口（鉴权/限流/日志/跨域）抽离到网关层，释放后端微服务业务专注度

2. 网关技术架构演进：Zuul 1.x 对比 Spring Cloud Gateway

Evolution Shift
Netflix Zuul 1.x (淘汰/停更) Blocking Servlet I/O

基于传统 Servlet 2.x 阻塞式 I/O 架构，采用 **Thread-per-Request** 模型。在高并发或后端 RPC 慢响应时，网关工作线程池会被迅速挂起耗尽，导致网关瘫痪。

Spring Cloud Gateway (现代标准) Netty + Project Reactor

基于 Spring 5、Spring Boot 2+、Netty 与 Project Reactor。采用**完全非阻塞响应式事件循环 (Reactive Non-blocking Event Loops)** 模型，少量线程即可支撑海量并发，吞吐量提升 300%+！

// 线程模型对比 (Thread Model Comparison)
Zuul 1.x: Request ──► [ Dedicated Thread ] ──► (Wait RPC) ──► Blocked!
SC Gateway: Request ──► [ Netty Event Loop ] ──► Async Mono/Flux ──► Non-blocking!

网关架构演进启发 (Gateway Evolution Insight)

从 Zuul 1.x 到 Spring Cloud Gateway 的跨越，代表了服务端架构从 **阻塞式线程池模式** 向 **基于 Netty 的非阻塞响应式事件流模式** 的物理进化。非阻塞网关能以极少的系统线程轻松应对数万 QPS 并发流量。
