Part 01 · 微服务演进与领域拆分

演进阶段 2：一服务一库 + 消息队列解耦 (Database-per-Service)

Physical Database Isolation, Polyglot Persistence & Async Event-Driven Communication

1. 阶段 2 物理拓扑 (一服务一库 + 事件消息解耦)

Database-per-Service

成熟微服务架构的核心基石：每个微服务独占其私有数据库，**严禁跨服务直接读写底层数据库**，微服务间仅通过 REST/gRPC 或异步 MQ 事件沟通：

// 阶段 2 物理拓扑：数据自治 + 异步事件流
[ 用户服务 ]
MySQL DB
[ 商品服务 ]
Redis / MongoDB
[ 订单服务 ]
MySQL DB
[ 促销服务 ]
Memcached
▲ 消息队列 MQ 事件总线 (Kafka / RocketMQ / RabbitMQ)
异步事件驱动（OrderCreatedEvent / UserRegisteredEvent），削峰填谷、极速解耦
成就：终结数据强耦合，实现完整的物理数据自治与独立部署保障

2. 一服务一库三大工程优势 (3 Core Benefits)

Data Autonomy
① 彻底物理解耦 (Complete Data Isolation) No Shared DB

锁空间、连接池完全相互隔离；用户服务修改 `user` 表字段只影响自身，不再会误伤后台管理或其他微服务。

② 异构多模持久化 (Polyglot Persistence) Fit-for-Purpose

各微服务自由按需选型最契合的底层存储：订单选 RDBMS 强事务，商品选 Redis 缓存/MongoDB 文档，推荐选图数据库。

③ 异步事件解耦 (Event-Driven Async) Non-blocking MQ

下单成功只需广播 `OrderCreatedEvent`，后续加积分、发短信、通知物流均由 MQ 异步广播触发，吞吐量极大提升。

演进阶段终局启发 (Database-per-Service Insight)

实现“一服务一库”是微服务走向真正自治的标志。虽然它引入了跨库分布式事务与数据一致性的新挑战（将在第 7 讲专篇解决），但它赋予了系统无限按需扩展与异构持久化的工程自由度。
