Part 05 · 云原生 Service Mesh 与全维可观测性

三维可观测性：Logs, Metrics & Traces (Three Pillars of Observability)

Discrete Event Logs, Aggregated Metrics Time-Series & Contextual Distributed Traces Correlation

1. Metrics (时序指标)

Prometheus

**物理定义**：在时间窗口内可聚合采样的离散数值（Counters, Gauges, Histograms）。

解答核心疑问

**“系统什么地方指标异常？”**
准实时回答 QPS 突增、P99 延迟陡增、CPU/内存水位、GC 停顿或断路器跳闸状态。

// 典型代表技术栈
• Prometheus + Grafana
• Micrometer / Actuator
特点：内存开销低，适合建立实时监控警报大盘

2. Traces (分布式链路追踪)

OpenTelemetry

**物理定义**：记录单次端到端请求跨越数十个微服务节点的完整调用有向无环图 (DAG)。

解答核心疑问

**“请求卡在哪个微服务节点？”**
靠 `traceId` 贯穿整个请求全生命周期，精准定位哪一个 RPC 调用耗时最长或抛出异常。

// 典型代表技术栈
• OpenTelemetry / W3C TraceContext
• Zipkin / Jaeger / SkyWalking
特点：基于 `traceId` / `spanId` 建立分布式关联关系

3. Logs (集中式日志)

EFK / ELK Stack

**物理定义**：包含时间戳的离散文本事件记录，记录系统在特定时刻发生的详细物理细节。

解答核心疑问

**“具体报错堆栈与参数是什么？”**
深入代码物理最底层，打印异常堆栈信息（`NullPointerException`）、SQL 传入参数与运行时上下文。

// 典型代表技术栈
• Elasticsearch + Logstash + Kibana
• Filebeat + Fluentd + Loki
特点：数据量极大，提供终极故障根因排查（Root Cause）

三位一体故障排查闭环 (Observability Tri-Pillars Synergy)

三维可观测性形成了完美的故障排查闭环：**Prometheus (Metrics)** 触发准实时告警通知 $\rightarrow$ **OpenTelemetry (Traces)** 依靠 `traceId` 快速定位异常发生的微服务节点与 Span $\rightarrow$ **EFK (Logs)** 在 Kibana 中精准过滤该 `traceId` 检索出底层代码报错物理堆栈。
