服务注册与发现物理原理 (Service Registration & Discovery)

Dynamic Pod IP Addressing, Periodic Heartbeat Leases, Local Registry Caching & Client-Side Routing

1. 动态寻址物理交互全景 (Interaction Sequence)

Discovery Sequence

在云原生弹性缩容环境中，容器 Pod 随切随换，静态硬编码 IP 彻底失效，必须引入分布式服务注册中心：

// 注册与发现全链路数据流 (Service Discovery Flow)
[ Provider Service A ] (192.168.1.6:8080) ① Register / Renew (30s)
向注册中心提交自身的 (serviceId, IP, Port, Metadata) 并发送周期心跳包续约
▲ 注册中心 (Service Registry: Eureka / Nacos / K8s DNS)
维护活跃服务地址字典表；逾期未发心跳（如 90s）剔除节点
[ Consumer Service B ] (Client-side LB) ② Pull / Poll Registry & Local Cache
定期拉取最新服务地址列表并本地缓存，通过负载均衡算法（如轮询）直连目标实例发起 RPC/HTTP 调用
成就：解耦服务提供者与消费者的物理 IP 依赖，实现无感弹性伸缩

2. 注册发现三大物理步骤解构 (3 Primary Steps)

Execution Steps
① 服务注册与心跳续约 (Register & Heartbeat) Interval = 30s

微服务启动时自动向注册中心发起 `POST /apps/{serviceId}` 提交其节点 IP、端口和元数据；之后按固定周期（默认 30s）发送 `PUT` 心跳续约。若注册中心连续多次未收到心跳（如 90s），判定节点不健康并予以下线。

② 服务发现与本地缓存 (Fetch & Local Caching) Local Registry Cache

服务消费者定期从注册中心增量拉取活跃实例字典表，并将其存放在本地内存缓存（Local Cache）中。即使注册中心发生单点故障宕机，已缓存的实例地址依然可以支持短时间内的 RPC 正常调用。

③ 客户端负载均衡与直连 (Client-side Routing) No Central Proxy

消费端的负载均衡器（如 Spring Cloud LoadBalancer）从本地缓存提取候选地址，依据预设算法（轮询、随机、响应时间权重）挑选目标实例，直接发起点对点 TCP/HTTP RPC 调用，避免中间代理单点瓶颈。

服务发现架构启发 (Service Registry Insight)

服务注册与发现是云原生微服务架构的**第一块基石**。它将“网络 IP”解耦为“逻辑服务名称（serviceId）”，让上层业务代码无需关心底层的物理节点漂移，消除了硬编码 IP 的历史沉窠。
