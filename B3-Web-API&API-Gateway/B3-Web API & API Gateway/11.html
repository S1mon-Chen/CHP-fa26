Part 02 · RESTful 架构风格与资源设计 (RESTful Architecture & Resource Design)

REST 架构风格诞生与 6 大核心约束原则

Roy Fielding (2000) Architectural Style vs. Protocol Specification & Core Constraints

1. 什么是 REST？ (What is REST?) Roy Fielding PhD Thesis (2000)

REST 是 **REpresentational State Transfer**（表述性状态转移）的缩写，由 HTTP 规范核心作者 **Roy Fielding 博士** 于 2000 年在其博士论文中正式提出。

不同于 SOAP，REST **不是一种强制的技术标准或协议**，而是一种指导分布式超媒体系统设计的**架构风格 (Architectural Style)**。

范式转变：RPC 过程调用 vs REST 资源视角
传统面向 RPC 范式 关注“服务方法调用” POST /getOrders.do POST /updateUser.action
现代面向 REST 范式 关注“资源表述与动作” GET /v1/orders PUT /v1/users/42
为什么 REST 能够迅速席卷现代 Web API？ Simplicity

它极度复用了已经无比成功的 Web 通用基础设施（HTTP 动词、HTTP Header、状态码与 URL 寻址），避免了 SOAP 复杂的序列化与工具链绑定。

核心理念：深度复用标准 Web 基础设施，而不是在 Web 之上重复造轮子
2. Roy Fielding 提出的 6 大核心架构约束 Fielding's 6 Constraints
① 客户-服务器 (Client-Server)

严格分离 UI 前端交互与后端数据存储，两者独立演进与水平扩展。

② 无状态 (Stateless)

服务端不保存客户端 Session 状态。每次请求必须包含处理所需的全部上下文。

③ 可缓存 (Cacheable)

响应必须隐式或显式标明是否可缓存，深度复用 HTTP Header 缓存提升性能。

④ 统一接口 (Uniform Interface)

核心基石：资源标识 (URI)、表述操作、自描述消息及超媒体链接 (HATEOAS)。

⑤ 分层系统 (Layered System)

客户端无需感知连接的是目标服务器还是中间网关/反向代理/CDN 缓存。

⑥ 按需代码 (Code on Demand) 可选 / Optional

服务端可临时下发可执行脚本（如 JS / Applet）扩展客户端功能。

REST 架构风格带来的核心收益

通过遵守这 6 大架构约束，软件系统能获得极佳的**可见性、可扩展性、易用性、组件独立演进能力以及长期的跨平台生命力**。

下一页精讲：REST 四要素 —— 资源 (Resource)、表述 (Representation)、URI 与状态转移

核心架构启示 (Architectural Insight)

理解 REST 的第一步是**放下“RPC 方法调用”的思维惯性**。REST 的本质是利用互联网天然的统一接口与超媒体链接，将服务端的功能抽象为“资源”，并驱动客户端在不同的资源表述状态之间平滑流转。
