Part 02 · RESTful 架构风格与资源设计 (RESTful Architecture & Resource Design)

RESTful URI 命名规范与资源寻址最佳实践

Noun Plurals, Kebab-Case, Resource Nesting, Query Parameters & API Versioning

1. RESTful URI 命名的 5 大黄金准则 URI Naming Rules
① 使用复数名词表示资源集合 (Plural Nouns) Plural Nouns

资源集合使用复数名词表达（如 /users、/orders）；定位特定单个实体时附加唯一 ID（如 /users/42）。

② 表达从属与关联资源 (Nested Resources) Sub-Resources

使用层级结构表示资源从属关系：GET /users/42/orders（用户 42 的所有订单）或 GET /orders/1001/items。建议嵌套层级不超过 2 至 3 层。

③ 小写字母与连字符 (Kebab-Case) kebab-case

URI 路径一律使用全小写字母，单词分割优先使用连字符 -（如 /order-items），严禁使用下划线 _ 或驼峰命名 orderItems。

④ 严格排除动词：RPC 错误示范 vs. REST 正确范式
RPC 动词混入（错误） POST /api/createUser GET /api/getOrders POST /api/deleteUser?id=42
REST 纯名词（正确） POST /v1/users GET /v1/orders DELETE /v1/users/42
规则总结：URL 定位资源名词，HTTP 动词执行动作，Query 参数过滤数据
2. 查询参数规范与 API 版本控制策略 Filtering & Versioning
查询参数 (Query Parameters) 过滤、排序与分页规范

URI 资源路径不应随着过滤条件而改变，过滤、排序与分页参数应当统一作为 Query String 提交：

GET /v1/orders?status=PAID&page=2&limit=20&sort=-created_at
status=PAID: 条件过滤
page/limit: 分页控制
sort=-created_at: 倒序排列
API 版本控制 3 大主流策略对比
① URI 路径版本化 (URI Path Versioning - 工业界首选) Most Popular
GET /v1/users/42 简单直观，对 API 网关路由、CDN 缓存及浏览器调试极度友好。
② 自定义 Request Header 版本化 Header Based
GET /users/42 [Header: X-API-Version: 2.0] 保持 URI 纯净，但无法直接在浏览器地址栏复制分享 URL。
③ 内容协商 Media Type 版本化 HATEOAS Alignment
Accept: application/vnd.company.v2+json 最符合 REST 纯粹理论规范，但客户端使用复杂度较高。

核心架构启发 (RESTful URI Naming Insight)

好的 URI 命名设计能达到**“自描述”与“符合人类直觉”**的效果。将 URI 严格限定为指向客观名词资源的地址，用 HTTP 动词修饰操作，Query 参数修饰约束条件，能够大幅降低前端开发者与第三方生态的集成门槛。
