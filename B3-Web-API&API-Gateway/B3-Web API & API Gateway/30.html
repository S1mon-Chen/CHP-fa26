Part 04 · 现代化 API 网关与治理决策 (API Gateway & Governance)

主流 API 网关架构对比：Spring Cloud Gateway vs. Apache APISIX / Kong

Architectural Trade-offs: Java Reactive Netty Engine vs. OpenResty Nginx C/Lua High-Performance Gateway

1. 两种典型网关架构路线深度解构 Architecture Paradigms
Spring Cloud Gateway (Java 响应式生态代表) Netty + Reactor

**机制**：基于 Spring 5、Spring Boot 2/3 和 Project Reactor，底层采用 Netty 非阻塞响应式事件循环 (Event Loop)。取代了旧版基于阻塞式 Servlet 的 Netflix Zuul 1.x。
**核心优势**：与 Java / Spring 生态 (Eureka, Nacos, Sentinel) 无缝集成，开发者可以直接使用 Java 编写复杂的自定义 Filter 逻辑。

Apache APISIX / Kong (云原生极致性能代表) Nginx + Lua + etcd

**机制**：基于 Nginx / OpenResty 高性能 C 语言引擎，配合 Lua 脚本实现极低延迟处理；配合 **etcd** 分布式 Key-Value 数据库实现路由与规则的毫秒级热加载。
**核心优势**：单核 QPS 达到数万级，内存开销极小；通过 Plugin Runner 支持 Go、Python、Wasm 多语言编写插件，天然适配 Kubernetes Ingress Controller。

选型要领：业务复杂度高的 Java 团队选 SCG；极致吞吐与多语言云原生选 APISIX
2. 多维技术选型矩阵 (Comparison Matrix) Gateway Matrix
特性维度 Spring Cloud Gateway Apache APISIX / Kong
底层引擎 Java, Netty, Project Reactor C / Nginx / OpenResty, Lua
吞吐与延迟 高 (毫秒级，受 GC 抖动影响) 极致 (微秒/亚毫秒级，C 语言内存)
生态集成 Spring Boot / Cloud 零门槛无缝融合 云原生 K8s Native, 多语言支持
动态配置 依赖 Nacos / Actuator 刷新配置 etcd 长轮询，热更新**无需重启**
二次开发扩展 Java 编写 Filter，降低 Java 团队门槛 Lua / Go / Python / Wasm 插件Runner
最佳适用场景 纯 Java / Spring 微服务架构企业 异构语言集群、超高并发流量入口
云原生“双层网关 (Two-Tier Gateway)”工业界演进范式

大型互联网架构普遍采用分层治理：外网流量入口采用 **Apache APISIX / Kong** 担当边缘南北向流量网关（负责 SSL 卸载、全局 WAF 与 DDoS 拦截）；进入内网后再由 **Spring Cloud Gateway** 担当业务东西向/部门级网关（负责细粒度业务鉴权与聚合）。

核心架构启发 (API Gateway Selection Insight)

网关选型没有绝对的优劣，只有**团队技术栈匹配度与性能诉求的权衡**。对于深度依赖 Spring 基础设施的 Java 团队，Spring Cloud Gateway 带来极低的研发维护成本；而面向多语言云原生集群与极致吞吐场景，Apache APISIX 则能释放更高的硬件效能。
