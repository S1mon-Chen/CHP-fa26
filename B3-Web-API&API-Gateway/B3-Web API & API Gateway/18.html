Part 02 · RESTful 架构风格与资源设计 (RESTful Architecture & Resource Design)

星巴克 RESTful 订单生命周期：支付处理与咖啡师 Atom Feed

Step 3: Payment Processing (PUT /payment/order/1234) & Step 4: Barista Order Feed (Atom Feed Polling & Pickup)

阶段 3：支付资源锁定 (Pay Order - PUT /payment/order/1234) 201 Created
客户端支付请求 (Digest 身份认证) PUT Request Payload
PUT /payment/order/1234 HTTP/1.1
Host: starbucks.example.com
Content-Type: application/xml
Authorization: Digest username="Jane Doe", realm="starbucks.example.org", nonce="..."
<payment xmlns="http://starbucks.example.org/payment">
<cardNumber>123456789</cardNumber>
<amount>4.00</amount>
</payment>
服务端响应 (201 Created - Payment Resource Built) Paid Confirmation
HTTP/1.1 201 Created
Location: https://starbucks.example.com/payment/order/1234
Content-Type: application/xml
<payment xmlns="http://starbucks.example.org/payment">
<status>PAID</status>
<amount>4.00</amount>
</payment>
Digest 安全认证 摘要认证防重放，保障交易 Payload 完整性
幂等性 (Idempotency) PUT 操作多次提交不会触发重复扣款状态
状态迁移：订单状态由 Placed 转换为 Paid，进入咖啡师制作队列
阶段 4：咖啡师 Atom Feed 轮询与取餐销毁 Barista Fulfillment
咖啡师终端 Feed 轮询 (Atom Feed + HTTP 缓存) Cache-Control

咖啡师客户端通过 GET 请求订阅订单 Feed 流，配合 HTTP 缓存标头节约带宽：

GET /orders/feed HTTP/1.1  ⇒  HTTP/1.1 200 OK
Expires: Thu, 12 Jun 2026 17:20:33 GMT
<feed xmlns="http://www.w3.org/2005/Atom">
<entry><id>http://starbucks.example.com/order/1234</id>
<content type="text/xml"><order><drink>latte</drink><cost>4.00</cost></order></content></entry>
</feed>
咖啡制作锁定与顾客最终取餐 (DELETE) Lifecycle Complete
1. 锁定接单 咖啡师提交 PUT /order/1234 标记状态为 <status>PREPARING</status>。
2. 取餐销毁 顾客拿到咖啡后，客户端发起 DELETE /order/1234，服务端回传 200 OK 销毁该订单资源。
REST 长事务全流程总结

POST 创建 $\rightarrow$ PUT 修改/冲突校验 $\rightarrow$ PUT 支付 $\rightarrow$ Atom Feed 异步接单 $\rightarrow$ DELETE 结案。

Part 02 小结：面向资源的设计将长事务业务完美解耦为自描述状态机

核心架构启发 (Complete RESTful State Machine Insight)

星巴克案例展示了 REST 的终极价值：**不需要复杂庞大的分布式事务 (2PC) 协议，仅仅通过 HTTP 原生动词与超媒体状态机**，就能优雅且松耦合地管理涵盖顾客、收银员、咖啡师等多个独立角色的复杂交易生命周期。
