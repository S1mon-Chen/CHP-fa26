Part 02 · RESTful 架构风格与资源设计 (RESTful Architecture & Resource Design)

HTTP 响应状态码分类与 REST 错误处理机制

Standardized Status Codes (2xx / 3xx / 4xx / 5xx) & RFC 7807 Problem Details

1. 标准 HTTP 响应状态码语义分类 RFC 7231 Standard
2xx 成功 (Success) Client Action Succeeded
200 OK: 请求成功，返回资源表述。
201 Created: 资源创建成功，Location Header 指向新 URI。
204 No Content: 执行成功但响应体无返回内容 (如 DELETE)。
3xx 重定向与缓存 (Redirection) Cache / Shift
304 Not Modified: 资源未变更，告知客户端/CDN 读取本地缓存。
4xx 客户端错误 (Client Error) Caller Responsibility
400 Bad Request: 参数校验失败或 Payload 格式错误。
401 Unauthorized: 未提供身份凭证；403 Forbidden: 缺乏权限。
404 Not Found: 资源不存在；409 Conflict: 状态冲突 (如并发更新)。
5xx 服务端错误 (Server Error) Callee Fault
500 Internal Server Error: 服务端未捕获的严重内部异常。
核心原则：充分利用 HTTP 协议原生的状态码传达准确语义
2. 反范式警告 vs RFC 7807 规范化错误定义 Problem Details Standard
伪 REST Anti-Pattern：盲目返回 HTTP 200
HTTP/1.1 200 OK
{"code": 500, "msg": "User Not Found"}

这种破坏 HTTP 语义的做法会导致浏览器、API 网关、CDN 缓存及自动监控系统无法感知真实的请求成败，极大地破坏了 REST 统一接口契约。

RFC 7807 标准错误格式 (Problem Details) application/problem+json
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
{
"type": "https://example.com/errors/user-not-found",
"title": "User Resource Not Found",
"status": 404,
"detail": "User with ID 42 does not exist.",
"instance": "/v1/users/42"
}
下一个核心：RESTful URI 命名最佳实践 (Plural Nouns, Kebab-Case & Versioning)

核心架构启发 (HTTP Status Codes Insight)

RESTful 架构契约的基础在于**准确地使用 HTTP 响应头状态码分类**。将业务处理错误与 HTTP 协议层状态解耦或强行隐藏在 `200 OK` 之后，将使得网关层的自动降级、限流与可观测性告警完全失灵。

🎯 引导学生明确状态码语义的重要性： “向学员强调：RESTful API 必须充分利用 HTTP 标准状态码。200 表成功、201 表已创建新资源、204 表无返回体，400 表参数校验失败、401/403 表未登录与未授权、404 表资源不存在、409 表资源状态冲突。严禁盲目返回 200 OK 并在 JSON 内部藏错误码！”
💡 引入 RFC 7807 Problem Details 规范： “请学员关注右侧的 RFC 7807 规范：它通过 `application/problem+json` 格式统一了 RESTful 错误的 Payload 结构（`type`, `title`, `status`, `detail`, `instance`），这也是现代 Spring Boot 与 ASP.NET Core 的标准错误响应格。”
