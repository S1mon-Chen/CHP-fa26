1. REST 内容协商核心概念与标头契约 Content Negotiation
`Accept` 与 `Content-Type` 标头成对演配 Header Contract

客户端在请求头声明 Accept: application/json 指明期望的表述格式；服务端处理完成后通过 Content-Type: application/json 标头明确告知返回体编码类型。

Spring `HttpMessageConverter` 管道机制 Pipeline

Spring Web 会遍历注册的转换器链（如 MappingJackson2HttpMessageConverter），比对客户端请求的 Media Type，自动选择合适的编解码器。

零代码侵入支持 XML (Jackson XML Integration) Multiformat

只需引入 jackson-dataformat-xml 依赖，同一 URI 端点（如 /greeting）即可在不改动 Controller 任何代码的情况下无缝回传 XML 表述。

REST 准则：同一个 URI 代表唯一资源，内容协商决定其具体的表现形式
2. 内容协商运行时处理图解与 Spring 配置 Jackson Converter Pipeline

// 可选：在 Spring WebMvcConfigurer 中自定义内容协商策略
@Configuration
public class WebConfig implements WebMvcConfigurer {
@Override
public void configureContentNegotiation(ContentNegotiationConfigurer configurer) {
configurer.defaultContentType(MediaType.APPLICATION_JSON)
.mediaType("json", MediaType.APPLICATION_JSON)
.mediaType("xml", MediaType.APPLICATION_XML);
}
}

核心架构启发 (Content Negotiation Insight)

内容协商体现了 REST 架构**资源与表述解耦 (Decoupling Resource & Representation)** 的真谛。通过在 Header 中传递 `Accept`，服务端同一个控制器方法能够同时支持移动端 JSON 消费与传统企业级 XML 系统对接，大幅提升 API 的通用性。
