Web API 应用场景决策与架构选型决策树

When to Use vs. When NOT to Use: Trade-off Matrix & Architectural Choice Tree

1. 适用场景 vs. 避坑反模式场景 Applicability Matrix
什么时候【强烈推荐】采用 Web API (RESTful)?
① 跨企业/跨机构 B2B 系统能力对接 B2B Integration

银行支付通道、物流履约查询、第三方 SMS/邮件服务。跨防火墙通信与高度通用性是第一需求。

② 多端异构客户端统一支持 (iOS/Android/Web) Heterogeneous Clients

同一个后端服务需要同时为 iOS 客户端、Android App、React SPA 单页应用及 IoT 硬件提供数据表述。

③ 开放平台与公共 API 生态 (Public Open APIs) Open API Ecosystem

类似 GitHub、Stripe、微信开放平台。通过 HTTP + JSON + OpenAPI 契约降到最低的三方开发者集成门槛。

什么时候【不建议】采用 Web API (RESTful)?
① 局域网内部超高频微服务 IPC (高吞吐低延时) Prefer gRPC/Dubbo

数据中心内部每秒数十万次互调。文本 JSON 序列化和 HTTP/1.1 头部开销过大，应首选基于 HTTP/2 + Protobuf 的 **gRPC**。

② 单机进程内调用与客户端本地组件 (Desktop Tools) In-Memory Call

进程内部模块调用（如桌面 IDE 或本地办公软件），无需引入网络层 Web API 的网络寻址与序列化损耗。

选型法则：通用性优先选 Web API (REST)；极致性能优先选二进制 RPC
2. Web API 通信架构选型决策树 Architecture Decision Tree
你的服务端通信场景类型与网络拓扑？
分支 A：外网 / 开放平台 / 移动端 / SPA 要求：极致通用性、低集成门槛、防火墙穿透
选型：RESTful Web API (JSON/HTTP)
分支 B：数据中心内部局域网微服务 (IPC) 要求：极致吞吐量、低 CPU 序列化损耗、强类型
选型：Binary RPC (gRPC / Protobuf)
分支 C：传统金融银行/医疗 B2B 异构系统 (合规需求) 要求：强严格 XML 契约、WS-Security 消息级加密验签
选型：SOAP / WSDL Web Service
现代云原生“对外 REST，对内 gRPC”混合选型范式

互联网大厂与微服务架构的工业标准：外部 HTTP 请求通过 **API 网关 (API Gateway)** 统一接入为 RESTful API；网关内部完成协议转换与 SSL 卸载后，以 **gRPC** 在内部局域网微服务之间极速转发。

下一个核心：从单体路由演进到现代化微服务 API 网关 (Part 04 开启)

核心架构启发 (Architectural Scenario Insight)

架构设计没有绝对的优劣，只有适不适合。**对外面向多端与开发者，选用 RESTful API 获得极致的通用性；对内面向微服务高频通信，选用 gRPC 获得极致的性能**。理解这套决策树是构建现代化企业级后端系统的必修课。
