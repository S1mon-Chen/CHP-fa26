HTTP 动词语义映射与 CRUD 原子操作

Unified Interface: HTTP Verbs Mapping, Safety & Idempotency Formal Definitions

1. 统一接口规范：HTTP 动词与 CRUD 映射矩阵 RFC 7231 / RFC 5789
HTTP 动词 CRUD 映射 操作语义说明 安全性 幂等性
GET Read 获取指定资源的当前表述，不修改服务端状态
POST Create 创建新资源，或提交非幂等的业务处理请求
PUT Update 整体替换/更新资源（若不存在则创建新资源）
PATCH Partial Update 局部增量修改资源的部分字段（非全量覆盖） 条件
DELETE Delete 销毁/删除指定 URI 对应的资源实体
PUT 全量更新 vs. PATCH 局部更新细粒度对比

PUT /users/42 要求 Payload 包含用户的全部字段（未提交字段会被清空）；而 PATCH /users/42 仅包含需要修改的属性（例如仅更新邮箱 `{"email": "new@sjtu.edu.cn"}`）。

严格约束：用 HTTP 动词修饰动作，严禁在 URI 路径中硬编码动词
2. 安全性 (Safe) 与 幂等性 (Idempotent) Formal Definitions
安全性 (Safe Method) No State Change
$$\text{Safe Method} \implies \text{无副作用（不修改服务端状态）}$$

客户端发起安全操作（如 `GET` / `HEAD`），绝不能破坏或修改服务器数据库中的任何资源状态，安全请求可以被浏览器或 CDN 随意缓存与预加载。

幂等性 (Idempotent Method) Identical Effect
$$\text{Idempotent} \implies f(f(x)) = f(x)$$

无论执行 1 次还是连续执行 $N$ 次（如因网络抖动重试），**对服务端产生的资源最终状态影响完全相同**。`PUT` 与 `DELETE` 具有幂等性，而 `POST`（多次提交创建多条新记录）不具备幂等性。

网络重试策略

具有幂等性的接口（PUT/DELETE）可以在网络超时后安全发起无损自动重试。

POST 幂等保障

非幂等 POST 需结合防重 Token（Idempotency Key）避免重复扣款。

下一个核心：HTTP 响应状态码分类 (2xx / 3xx / 4xx / 5xx) 规范

核心架构启发 (HTTP Methods Insight)

RESTful 架构优雅地将**特定动词与其对应的安全性、幂等性契约强绑定**。正确理解并遵循动词语义，能够指导前端与微服务网关在面对网络波动时，设计出最高效且安全的自动重试与缓存策略。
