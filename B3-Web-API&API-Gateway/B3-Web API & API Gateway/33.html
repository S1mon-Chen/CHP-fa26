Web API 通信架构选型决策树

Architecture Decision Tree: External RESTful API vs. Internal Microservice gRPC vs. Legacy SOAP

1. 架构选型逻辑决策流 (Decision Tree Diagram) Architectural Choice Flow
核心决策问题 (Core Question)

通信发生的【网络边界】是什么？调用端是什么类型的客户端？

边界 A: 公网接入 / 多端
  • iOS / Android / SPA
  • 第三方 Open API 平台
  • 要求防火墙零障碍穿透
推荐架构选型 RESTful API JSON + HTTP/1.1 + OpenAPI
边界 B: 数据中心内网
  • 微服务间高频 IPC 互调
  • 每秒数十万次并发 RPC
  • 要求极低 CPU 序列化开销
推荐架构选型 Binary RPC (gRPC) Protobuf + HTTP/2 Multiplex
边界 C: 金融/遗留系统
  • 银行/医疗传统通道对接
  • 强 XML Schema 校验
  • WS-Security 消息级加密
推荐架构选型 SOAP Web Service XML + WSDL + Envelope
选型要领：公网侧重【通用性与解耦】，数据中心内网侧重【极致吞吐与低延时】
2. 选型特征矩阵与云原生双层混合范式 Hybrid Pattern
RESTful API (JSON/HTTP) Universal Access

优势：极致通用性，浏览器与移动端零门槛消费，生态极其丰富；短板：JSON 文本序列化开销稍高。

Binary gRPC (Protobuf) High Performance

优势：Protobuf 二进制体积极小，HTTP/2 多路复用，CPU 序列化损耗降低 60%+；短板：浏览器原生无法直接调用。

云原生“对外 REST，对内 gRPC”工业标准模式
1. Edge Public Gateway APISIX / SCG

暴露 RESTful JSON 接口给 Web/Mobile，在网关层完成 SSL 卸载、JWT 鉴权与 CORS 校验。

2. Gateway Protocol Transcoding gRPC Transcoding

网关自动将外部 HTTP/JSON 请求转码为内网 Protobuf，通过 HTTP/2 在微服务集群内部极速转发。

下一个核心：微服务设计与 Web API 演进总结 —— 从架构选型到云原生部署 (Slide 34)

核心架构启发 (Architecture Selection Decision Insight)

完美的架构从来不是单一协议的“一刀切”。通过**对外 REST 保证最大化解耦与通用性，对内 gRPC 保证极致吞吐与性能，中间借助 API 网关完成无缝转码**，是现代化企业级分布式系统的黄金选型范式。
