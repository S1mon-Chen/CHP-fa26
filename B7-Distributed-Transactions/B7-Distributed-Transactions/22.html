TCC 模式原理：Try、Confirm 与 Cancel 三阶段 (TCC Pattern Mechanics)

Application-Level Two-Phase Commit, Resource Reservation, Frozen Balance Isolation & High Throughput

TCC 应用层两阶段资源预留管线 (Try $\rightarrow$ Confirm / Cancel Execution Flow) Resource Reservation guarantees Confirm execution success
阶段 1：Try (预留资源) Reservation
业务检查：检查账户余额、库存量等前置业务合法性。
资源预留：不直接扣减余额，而是加上 frozen_balance 冻结资金。
阶段 2A：Confirm (提交确认) All Try Success
全成功响应：所有分支服务的 Try 均成功后触发。
使用预留：真正的物理扣减，扣除 frozen_balance 并划转。由于 Try 已做预留，Confirm 默认必定成功！
阶段 2B：Cancel (取消解冻) Any Try Fails
任一异常触发：有任一分支服务 Try 失败或超时触发。
释放资源：扣减 frozen_balance 解冻资源，将状态恢复为初始状态。

1. TCC 资源预留数据表结构设计 (Resource Reservation Schema)

Try Isolation
// 资金账户表结构增加冻结金额字段 frozen_balance
CREATE TABLE account (
user_id VARCHAR(64) PRIMARY KEY,
balance DECIMAL(18,2), -- 可用余额
frozen_balance DECIMAL(18,2) DEFAULT 0.00 -- 冻结金额 (预留资源)
);
Try 阶段物理 SQL 演推 ($100 元)

UPDATE account SET balance = balance - 100, frozen_balance = frozen_balance + 100 WHERE user_id = 'Alice' AND balance >= 100;

本质：将数据锁定提升至应用层中间状态，本地 DB 事务随 Try 结束立即提交

2. 相比 2PC 强一致协议的物理性能优势

TCC vs 2PC
优势 1：无物理数据库排他长锁

2PC 的 RM 在 Prepare 后必须挂起持锁等待。TCC 的 Try 在本地更新完 frozen_balance 后立刻提交本地 DB 事务，归还连接池，极大释放了高并发数据库吞吐！

优势 2：跨数据源/第三方接口支持

TCC 是纯应用层协议，不依赖底层数据库的 XA 驱动。任何能够暴露 HTTP/RPC Try-Confirm-Cancel 接口的外部服务均可接入。

开启下一个核心：Slide 23 · TCC 异常治理：防空回滚、防悬挂与防重幂等性

核心架构启发 (TCC Reservation Insight)

TCC 模式的成功取决于“预留资源 (Reservation)”的设计。Try 阶段将并发冲突转化为业务状态冻结，保证了 Confirm 阶段可以无阻塞并发提交。然而，TCC 也要求开发者必须妥善处理网络丢包导致的**空回滚与悬挂问题**。
