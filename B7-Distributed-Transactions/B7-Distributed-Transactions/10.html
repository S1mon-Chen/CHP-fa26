系统事务 1：读取数据

用户点击编辑按钮。开短事务加载客户 129 信息（带 version），释放 DB 连接。

用户思考阶段 (Think-Time)

用户在页面修改名称。绝不能保持物理 DB 连接或加 DB 排他锁（否则会打爆连接池）。

系统事务 2：校验与提交

用户提交表单。开短事务比对版本，成功则更新 version + 1，失败则回滚。

1. 乐观离线锁 (Optimistic Offline Lock)

Optimistic Versioning
核心原理与物理机制

假定多会话并发冲突概率低。在数据表中维护 version 版本列。在提交阶段通过 SQL 检查版本号是否发生变动：

// 带有 version 校验的更新 SQL
UPDATE customer
SET name = 'NewName', version = version + 1
WHERE id = 129 AND version = 1;
// 若影响行数 (Rows Affected) == 0，说明被其他 Session 抢先修改
// 抛出 OptimisticLockException，业务显式回滚处理！
优点：不持有物理 DB 锁，吞吐量极高；JPA 标准提供 `@Version` 原生支持

2. 悲观离线锁与粗粒度锁 (Pessimistic & Coarse-Grained)

Pessimistic & Coarse
悲观离线锁 (Pessimistic Offline Lock)

假定冲突高发。在业务长事务开始时（用户加载编辑页），通过独立 **Lock Manager**（如 Redis 或数据库 lock_table）申请数据行的锁定令牌，阻止其他会话开启编辑。

粗粒度锁 (Coarse-Grained Lock)

当修改涉及一组关联对象（如 Customer 及其包含的多条 Address）时，不给每条 Address 单独维护锁，而是**让组内所有成员共享对根对象 (Customer) 的同一个版本/锁令牌**。

Part 01 总结 (Spring 本地事务与离线锁心法)

单机本地事务中，Spring @Transactional 借助 **AOP 代理切面** 与 **`ThreadLocal` 绑定连接** 托管了声明式事务；而在跨越 HTTP 用户思考时间的长事务中，**乐观离线锁 (Version)** 与 **悲观离线锁 (Lock Manager)** 则补齐了长会话下的离线并发控制。
