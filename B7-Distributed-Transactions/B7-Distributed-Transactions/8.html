生产环境八大 `@Transactional` 事务失效陷阱 (Eight Common Pitfalls)

AOP Proxy Bypassing, Class Self-Invocation, Non-Public Modifiers, Swallowed Exceptions & Multi-Thread Boundaries

Spring `@Transactional` 事务失效八大物理场景分类 (8 Transaction Failure Patterns) Core Rule: AOP Aspect Interception & ThreadLocal Connection Boundaries
1. 同类自调用 AOP Bypass

方法内部使用 this.method() 调用同类带注解方法，绕过代理切面。

2. 非 public 修饰 Private Method

注解加在 private / protected 方法上，Spring 默认拦截器直接忽略。

3. Bean 未被托管 Not Spring Bean

类缺少 @Service / @Component，直接通过 new 创建无法被代理。

4. final 类/方法 CGLIB Barrier

CGLIB 通过生成子类重写方法代理，final 阻止了子类重写。

5. 内部吞掉异常 Try-Catch Trap

内层 try-catch 捕获异常未向上抛出，AOP 代理无法感知到错误。

6. Checked 异常未设 Default Policy

抛出受检异常未配 rollbackFor = Exception.class，默认提交。

7. 跨线程异步调用 ThreadLocal Lost

新子线程无法复用主线程绑定的 ThreadLocal 物理 DB 连接。

8. 存储引擎不支持 MyISAM Engine

MySQL 使用了不支持事务的 MyISAM 引擎而非 InnoDB。

1. 高频罪魁祸首：同类内部自调用 (Self-Invocation)

Self-Invocation Trap
// ❌ 踩坑示范：直接调用 this.updateStock()，绕过了 Spring AOP 代理切面！
@Service
public class OrderServiceImpl implements OrderService {
public void createOrder() {
this.updateStock(); // 直接目标调用，@Transactional 完全失效！
}
@Transactional
public void updateStock() {
stockDao.deduct();
}
}
本质：Spring AOP 代理对象只有被外部 Bean 调用时才能触发拦截器管线

2. 同类自调用失效三大物理解法 (Solutions)

Fix Solutions
方案 1：解耦拆分到独立 Service（强烈推荐）

将 updateStock() 拆分重构到独立的 StockService 中，在 OrderService 里注入并调用。

// 方案 2：使用 AopContext.currentProxy() 强行获取当前 AOP 代理对象
public void createOrderCorrect() {
((OrderService) AopContext.currentProxy()).updateStock();
} // 需在配置类标注 @EnableAspectJAutoProxy(exposeProxy = true)
方案 3：通过 `@Lazy` 自身循环注入代理对象

在类内部使用 @Autowired @Lazy private OrderService self; 注入自身代理对象，并使用 self.updateStock()。
