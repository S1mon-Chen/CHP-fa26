Seata TCC 模式：应用层预留与手动控制 (Seata TCC Mode)

`@LocalTCC`, `@TwoPhaseBusinessAction`, `BusinessActionContext` & Non-RDBMS/Cross-Service Control

Seata TCC 注解框架与两阶段方法映射原理 (Seata TCC Lifecycle Pipeline) Explicit App-Level 2PC: No DB Proxy Needed
阶段 1：Try 方法 (`prepare`) Prepare
• 标注 @TwoPhaseBusinessAction
• 显式检查并预留业务资源（如冻结资金/库存）
• 向 TC 注册分支，将参数打包存入 Context
阶段 2A：Commit 方法 (`confirm`) Commit
• 由 TC 异步下发调用 commitMethod
• 消费 Try 预留的资源，真正完成物理业务扣减
• 依赖 `BusinessActionContext` 取回主键与参数
阶段 2B：Rollback 方法 (`cancel`) Rollback
• 由 TC 异步下发调用 rollbackMethod
• 逆向释放 Try 阶段预留冻结的资源
• 需接入 `tcc_fence_log` 防防空回滚与悬挂

1. Seata TCC 接口与注解范式 (`PaymentTccAction`)

Java Interface
// 1. TCC 接口定义：必须使用 @LocalTCC 注解
@LocalTCC
public interface PaymentTccAction {
@TwoPhaseBusinessAction(name = "paymentTccAction", commitMethod = "confirm", rollbackMethod = "cancel")
boolean prepare(BusinessActionContext ctx,
@BusinessActionContextParameter(paramName = "userId") String userId,
@BusinessActionContextParameter(paramName = "amount") BigDecimal amount);
boolean confirm(BusinessActionContext ctx);
boolean cancel(BusinessActionContext ctx);
}
本质：把两阶段提交的物理裁决全权交由应用层编写 Java 逻辑

2. 相比 AT 模式，何时必须选型 Seata TCC 模式？

When to use TCC
1. 非关系型存储或 NoSQL 场景 (Redis / MongoDB)

Seata AT 依赖代理数据源解析 SQL 和 `undo_log` 表。如果资源存放在 Redis、MongoDB 或 ES 中，**只能使用 TCC 模式由应用层手动冻结解冻**。

2. 追求极致性能，避免 TC 全局锁瓶颈 (No Global Lock)

AT 模式在一阶段需要向 TC 申请全局锁 `table_name:pk`。TCC 的预留发生在应用层，**完全不依赖 TC 全局锁**，吞吐量极高。

3. 跨第三方 API 服务的应用层包装

调用的下游是外部机构暴露的 HTTP/RPC 接口，无法直接连数据库，TCC 可以将外部 API 包装为 Try/Confirm/Cancel。

开启下一个核心：Slide 35 · Seata Saga 模式：基于 JSON 状态机的可视化长事务编排

核心架构启发 (Seata TCC Mechanics Insight)

Seata TCC 模式将分布式事务的控制权重新交还给程序员。通过 @LocalTCC 与 @TwoPhaseBusinessAction 注解，Seata TC 只充当调度协调者，将参数隐式透传至 Confirm/Cancel 方法，兼具高度灵活性与无与伦比的超高并发吞吐。
