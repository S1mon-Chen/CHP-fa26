Part 04 · 微服务最终一致性模式：TCC、Saga 与消息事务

本地消息表模式 (Local Message Table Pattern)

eBay Pattern: Binding Business Logic & Outbound Messages via Single-Database Local ACID Transactions

本地消息表原子写与后台异步投递管线 (Local Message Table Pipeline) Zero Message Loss Guarantee via Local DB ACID
步骤 1：本地 ACID 事务 Atomicity
• UPDATE order SET status = 'PAID';
• INSERT INTO local_message (...);
✓ 本地 DB 事务提交，保证业务与消息日志同成败！
步骤 2：定时 Job 轮询 Async Polling
• 独立后台 Task / 定时任务轮询数据库
• 定期扫描 status = 0 (UN_SENT) 消息
• 将就绪消息推送投递至 MQ / 下游 RPC
步骤 3：下游消费与 Ack Consumption
• 下游服务 B 消费消息，执行本地数据更新
• 下游处理成功后返回确认 Ack
• 要求下游必须具备防重幂等处理能力
步骤 4：状态更新 / 清理 Completed
• 收到 Ack 后，更新消息 status = 1 (SENT)
• 或定期归档/物理删除已发送成功的历史记录
✓ 全链路达成 BASE 最终一致性！

1. 本地消息表数据库 DDL 结构设计与索引优化

Schema DDL
// 经典本地消息表结构 (local_message_table)
CREATE TABLE local_message_table (
id VARCHAR(64) PRIMARY KEY, -- 消息全局 ID
topic VARCHAR(64) NOT NULL, -- MQ Topic 或目标服务
payload TEXT NOT NULL, -- JSON 格式消息体
status INT NOT NULL DEFAULT 0, -- 0:UN_SENT, 1:SENT, 2:FAIL
retry_count INT DEFAULT 0, -- 重试次数
update_time DATETIME NOT NULL,
KEY idx_status_time (status, update_time) -- 索引优化 Job 扫描
);
核心优势 (Key Advantage)

巧妙借用了单机数据库成熟的 **ACID 事务与 WAL 机制**，彻底消除了“先写 DB 再发 MQ，网络中途断开”引发的消息丢失硬伤。

本质：将分布式网络不可靠消息问题转化为单机数据库本地 ACID 事务写

2. 模式缺陷与生产实践改进 (Engineering Trade-offs)

Trade-offs & Fixes
缺陷 1：高并发数据库写压力与耦合 (DB Coupling)

消息表与业务表共用同一个数据库，大量的消息 INSERT 与定时 Job 频繁 SELECT 扫描，会给核心业务 DB 带来额外磁盘 I/O 负担。

缺陷 2：定时 Job 延迟与重复投递 (Polling Latency & Duplicates)

一致性取决于 Job 轮询周期（通常存在秒级延迟）。若网络超时重试，可能导致同一消息被多次投递，**消费端必须做好幂等性防护**。

改进方案：CDC Binlog 监听 (Canal / Debezium)

生产环境中，可使用 Canal / Debezium 替换定时 Job，通过**解析数据库 Binlog** 增量实时抓取消息写入 MQ，兼顾毫秒级低延迟与零 DB 扫描开销。

核心架构启发 (Local Message Table Insight)

本地消息表模式是**用“单机数据库 ACID 事务”解决“分布式网络不靠谱”问题的典范**。尽管存在 Job 轮询开销，但其极低的技术门槛和 100% 不丢消息的硬核保证，使其在中小微服务架构中得到了极其广泛的应用。
