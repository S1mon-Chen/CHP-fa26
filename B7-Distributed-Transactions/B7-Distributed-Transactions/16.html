Part 03 · 传统强一致性分布式事务：XA 与 2PC/3PC

跨库更新与 XA 规范架构 (Multiple Database Updates & XA Architecture)

Cross-Server RPC Invalidation, X/Open DTP Model: AP (Application), TM (Transaction Manager) & RM (Resource Manager)

X/Open DTP (Distributed Transaction Processing) 经典模型拓扑 (DTP Model Topology) Standardized Model for Multi-Resource Global Transactions
AP (Application Program) 应用程序

定义业务事务边界。调用 TX 接口开启/提交全局事务，并触发各 RM 上的具体业务数据改动。

TM (Transaction Manager) 事务管理器

全局事务协调器。分配全局 XID，协调驱动所有参与的 RM 完成两阶段提交 (2PC) 或回滚。

RM (Resource Manager) 资源管理器

管理具体物理共享资源（如 MySQL, Oracle 数据库）。实现 XA 驱动接口，接收 TM 的锁控制与提交指令。

1. 经典跨 Java EE 服务器 / 跨库更新问题

Cross-DB Dilemma
经典企业级场景推演 (Bean-A $\to$ Bean-B)

客户端调用服务器 1 上的 Bean-A，Bean-A 更新本地数据库 $X$；接着通过跨网络 RPC 调用服务器 2 上的 Bean-B，Bean-B 更新远程数据库 $Y$。

// 单机 Connection 本地事务失效困境：
BeanA.updateDB_X(); // 数据库 X 连接
BeanB.updateDB_Y(); // 跨 RPC，数据库 Y 连接
// 场景：若 BeanB 写 DB_Y 成功，而 BeanA 提交时网络断开，数据产生永久悬挂！
本质：独立的 Connection 无法感知彼此状态，需要全局 TM 进行统一裁决

2. X/Open XA 接口规范物理细节

XA Specification
XA 接口定义 (AX / XA SPI)

XA 规范定义了 TM 与 RM 之间的双向控制接口：
• xa_start(xid): 关联当前 SQL 与全局事务 ID。
• xa_end(xid): 解除分支事务关联。
• xa_prepare(xid): 询问 RM 是否准备就绪并写 Undo/Redo。
• xa_commit / xa_rollback(xid): 物理提交或回滚。

全局事务标识符 (XID Structure)

由格式标识符 (Format ID)、全局事务 ID (GTRID) 与分支 qualifier (BQUAL) 拼接而成，保证全局唯一标识。

开启下一个核心：Slide 17 · 两阶段提交协议 (2PC) 物理链路与两阶段锁机制

Part 03 核心开篇哲学 (XA Architecture Insight)

跨库更新的根本难题在于缺少一个能够跨 TCP 连接调度所有独立数据库的“超级裁判”。X/Open DTP 模型通过引入 TM 协调器与 XA 驱动规范，将多个本地事务统一提升绑定为带有全局 XID 的强一致事务。
