Module 4 · 工程避坑与生产调优

自动化编排常见翻车现场：路由失效、插件超时与 RAG 智障排查

在实验室里跑通了 Demo 不叫成功，上了生产环境才是真正的考验。大模型是概率驱动的，插件依赖外部网络，知识库依赖切片质量。作为科技管理者，必须掌握系统“翻车”时的望闻问切，通过 Trace 日志精准定位并修复问题。

三大经典翻车现场与排障指南

TROUBLESHOOTING

1 意图路由失败 (Router Fail)

现象： 用户明明问的是“退款”，Router 却把问题派给了“技术 Bot”，或者干脆兜底说“我不懂”。
病因： 转移条件（Condition）写得太重叠，大模型无法区分边界。
药方： 加入明确的互斥关键词（如：包含“退钱、发票”时，绝对转给财务），并必须设置 Fallback 兜底。

2 插件调用报错或超时 (Plugin Error)

现象： 系统卡顿很久，最后直接报错。查看 Trace 发现 API 返回 HTTP 400 或 500。
病因： 大模型提取参数产生了幻觉（把订单号提取成了带中文字符的格式），导致接口校验失败。
药方： 在 LLM 参数提取后，加一个 Code 节点进行强正则清洗，确保传给插件的参数绝对合法。

3 知识库检索“智障” (RAG Miss)

现象： 知识库里明明有答案，AI 却回答“没找到”。
病因： 使用了纯向量检索（Vector Search），对料号、专有名词（如 Error 05）极其不敏感。
药方： 必须切换为 混合检索 (Hybrid Search)，并适当调大召回数量 (Top K=5)。
