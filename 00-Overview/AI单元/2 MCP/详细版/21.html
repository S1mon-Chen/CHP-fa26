Module 5: 安全红线与单元收官

Guardrails · 边界防御

架构师心法：给猛兽戴上 “双重防呆锁”

不要考验大模型的道德，要用系统的物理边界去限制它。
优秀的产品经理在设计 AI 业务流时，一定会加上这两道防线。

第一道锁：业务逻辑锁

Prompt-Level Constraint (防君子)

这是“软防线”。在发给 AI 的 Prompt 中，强制使用 XML 标签划定安全红线，与大模型签订“只读契约”。

<安全红线> 1. 你的最高指导原则是【绝对只读】。 2. 在连接数据库时，仅允许生成和执行 SELECT 查询语句。 3. 严禁生成或执行任何带有 DELETE, DROP, UPDATE, INSERT 的修改型 SQL。 4. 如果用户的提问暗示要修改或删除数据， 请直接拒绝并提示“权限不足”。 </安全红线>

第二道锁：物理环境锁

Infrastructure-Level (防小人)
终极防御

这是“硬防线”。哪怕 AI “发癫”想要删库，我们也要在系统底层直接没收它的“刀”。在配置 MCP 时强行限制权限。

"我的业务数据库": { "command": "npx", "args": [ "-y", "mcp-sqlite-tools",
"--read-only" // 开启插件的只读模式
], // 备选方案：通过操作系统 // 直接把 .db 文件右键设置为“只读”权限。 }

Vibe Coding 核心心法：先求稳，再求快

当代码不再成为壁垒，“业务风控与架构设计”就是你和普通调包侠拉开差距的核心竞争力。永远预判 AI 的失控，并提前布下防线。

Speaker Notes / 讲师备课备注
🛡️ 传授架构师思维： “既然 AI 是头猛兽，那我们该如何约束它？优秀的产品经理绝不会去赌 AI 听不听话，而是要用【物理规则】去限制它。请大家看大屏幕上的这套‘双重防呆锁’！”
📝 第一道软锁： “左边是防君子的。在你让 AI 查数据之前，你的 Prompt 里必须带上 `<安全红线>` 这个模块，白纸黑字写清楚：不准改数据。大模型对这种带有惩罚性质的声明非常敏感。”
🔒 第二道硬锁（终极防御）： “右边是防小人的。如果你怕 AI 突然幻觉失控，我们就在装插头的时候，直接把它的写权限没收掉！在 `args` 里加上 `--read-only` 参数。哪怕 AI 生成了删库指令，底层也会直接报错拦截：对不起，您只有只读权限！甚至更简单的，你直接去文件夹里把那个文件右键设置成‘只读’即可。”
