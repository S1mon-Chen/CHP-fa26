Part 04 · 快照隔离与多版本并发控制 (MVCC)

MVCC 与 Next-Key Lock 组合拳消除幻读 (Eliminating Phantoms)

Dual Defense in InnoDB RR: Snapshot Read via MVCC ReadView vs. Current Read via Next-Key Lock

MySQL InnoDB RR 隔离级别下的“双模式”幻读物理防御矩阵 (Dual Phantom Defense) Target: Eliminating Phantom Rows Across All Query Types
模式 A：快照读 (Snapshot Read) —— MVCC 视图隔离 Lock-Free MVCC
• **SQL 语法**：普通的不加锁 SELECT ... FROM table;
• **防御物理**：基于第一次查询捕获的**静态 ReadView**。即使并发事务 $T_2$ 强行 `INSERT` 并提交，新行的 $TRX\_ID \ge max\_trx\_id$，沿 Undo 链遍历时自动被**物理过滤**！
• **效果**：零锁开销，完全不被并发 `INSERT` 干扰！
模式 B：当前读 (Current Read) —— Next-Key Lock 区间挂起 Gap Locking Defense
• **SQL 语法**：SELECT ... FOR UPDATE / UPDATE / DELETE
• **防御物理**：对检索范围自动施加 **Next-Key Lock (行锁 + 间隙锁)**，排他封锁索引开闭区间 $(X_i, X_{i+1}]$。当并发 $T_2$ 尝试插入间隙时，**直接被强行挂起等待**！
• **效果**：物理阻止新行诞生，源头扑灭幻读！

1. 两种读取模式下幻读防范的物理本质

Physical Insight

许多开发者混淆了快照读与当前读在防范幻读时的手段，其本质差异在于：

快照读 (MVCC ReadView) —— 允许插入，但屏蔽视图

并发事务 $T_2$ 可以成功执行 `INSERT` 并提交。只是在 $T_1$ 的 ReadView 视窗里，新记录的 $TRX\_ID$ 被判定为不可见，因此 $T_1$ 的快照读查询看不到新行。

当前读 (Next-Key Lock) —— 直接禁止并发插入

当 $T_1$ 执行 `FOR UPDATE` 时，间隙锁 (Gap Lock) 会锁定目标索引区间。并发事务 $T_2$ 若尝试在间隙中插入数据，会被阻塞并进入 `LOCK WAIT` 状态，直至 $T_1$ 提交。

法则：快照读用 Undo 版本掩模避开幻读，当前读用 Next-Key Lock 挂起并发写

2. 当前读锁间隙实战与特殊“伪幻读”破防场景

SQL Scenario
// 1. T1 执行当前读锁定区间 (10, +∞)
SELECT * FROM account WHERE age > 10 FOR UPDATE;
// 2. T2 尝试插入 age = 15 新行
INSERT INTO account(age) VALUES (15); // BLOCKED (等待 T1 释放间隙锁)
特殊“破防”场景：快照读中途升级为当前读

若 $T_1$ 先执行普通 `SELECT`（快照读未加锁），随后 $T_2$ 成功 `INSERT` 并提交；接着 $T_1$ 对该新行执行了 `UPDATE`（升级为当前读，将该行的 `DB_TRX_ID` 修改为 $T_1$ 自己），此后 $T_1$ 再次 `SELECT` 就会看到该行（因为能看见自己修改的数据）。建议：需要强一致性断言时，务必使用 `FOR UPDATE` 显式加锁！

Part 04 总结 (MVCC & Snapshot Isolation Insight)

MVCC 实现了“读不阻塞写，写不阻塞读”，是现代数据库高性能并发的基石。在 Repeatable Read (RR) 级别下，快照读靠 **MVCC ReadView 隐藏未期行**，当前读靠 **Next-Key Lock 锁死间隙**，两者完美协同消除了幻读。
