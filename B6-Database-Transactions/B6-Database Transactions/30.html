1. Buffer Pool 内存页与脏页 (Dirty Pages) 物理定义

Memory Concepts

为了解决物理磁盘随机 I/O 极慢的瓶颈，关系型数据库（如 MySQL InnoDB）在内存中开辟了巨大的 `Buffer Pool`：

Buffer Pool 缓存池

以 **16KB 数据页 (Page)** 为单位在 DRAM 中缓存磁盘数据。所有的读写 SQL 操作一律先在 Buffer Pool 中查找或修改。

脏页 (Dirty Page)

在 Buffer Pool 中被 `UPDATE / INSERT / DELETE` 修改了内容，但**尚未写入同步回磁盘**的数据页。

干净页 (Clean Page)

内存中的数据与磁盘物理文件上的内容完全一致的数据页（未被修改过或已被平滑刷盘）。

法则：写操作只需修改内存脏页即算成功，落盘延后异步解耦

2. 后台异步刷脏策略与四大触发时机 (Flushing Triggers)

4 Triggers
1. 正常关机 (Normal Shutdown)

数据库关闭时，触发全量脏页刷盘，将 Buffer Pool 中所有脏页彻底清空刷回磁盘。

2. Buffer Pool 淘汰旧页 (LRU Eviction)

内存不足淘汰最久未使用 (LRU) 数据页时，若该页为脏页，必须先将其强行刷盘后才能腾出内存。

3. Redo Log 环形日志满 (Checkpoint Pressure)

重做日志（Redo Log）空间达到安全阈值时，强制推进 Checkpoint，拉动脏页刷盘释放 Redo 空间。

4. 后台定时线程平滑刷盘 (`page_cleaner`)

后台独立线程按照 `innodb_io_capacity` 参数指定的速率，持续平滑将脏页刷盘，避免抖动。

Part 05 核心开篇哲学 (Buffer Pool & Async Flushing Insight)

Buffer Pool 实现了内存级极速写，但**异步刷脏使得磁盘数据在任意瞬间都落后于内存脏页**。这一物理时间差直接引出了一个致命风险：如果在脏页写回磁盘前突发断电宕机，数据该如何恢复？这就是接下来预写日志（WAL）与 Redo Log 要解决的核心问题。
