隔离性与并发执行的妥协 (Isolation & Concurrent Execution)

Serial Execution Illusion, Interleaved Transactions & Isolation Strictness vs. Throughput Balance

并发吞吐量与隔离级别严苛度权衡坐标轴 (Concurrency Performance vs. Isolation Strictness) Strictness $\uparrow \implies$ Throughput $\downarrow$
Read Uncommitted Lowest Isolation
无锁无视图，允许读未提交数据（脏读），吞吐量极高，数据极不安全。
Read Committed Every Query MVCC
语句级 MVCC 快照，消除了脏读，但允许不可重复读与幻读。
Repeatable Read Trx Level MVCC
事务级 MVCC 快照 + 间隙锁（Next-Key Lock），消除不可重复读与多数幻读。
Serializable Highest Isolation
读写全面加锁（2PL 读写锁 / 谓词锁），彻底排斥并发读写冲突，吞吐低。

1. 纯串行执行 (Pure Serial Execution)

100% Safe, Zero TPS

在纯串行模式下，事务按顺序排队执行，$T_1$ 完全提交后再启动 $T_2$。这种方式不存在任何并发读写冲突。

核心优势
  • • 逻辑绝对安全简单
  • • 彻底杜绝任何并发异常
  • • 一致性与隔离性天然成立
物理瓶颈
  • • 遇到磁盘/网络 I/O 时 CPU 空转
  • • 无法利用现代 CPU 多核算力
  • • TPS 吞吐量遭遇断崖式下跌
代价：安全但吞吐量极低，无法支撑互联网高并发场景

2. 并发交叉执行 (Concurrent Interleaving)

High TPS, Conflict Risk

现代数据库允许多个事务的操作按时间重叠交叉执行（Interleaved Schedule），在 $T_1$ 发生磁盘 I/O 时调度 $T_2$ 运算。

并发交叉引发的三大读写冲突 (Read/Write Conflicts) Anomalies Risk
  • • **读写冲突 ($RW$)**：$T_1$ 读完后 $T_2$ 修改，引发不可重复读。
  • • **写写冲突 ($WW$)**：$T_1$ 未提交时 $T_2$ 覆盖写入，引发脏写/更新丢失。
  • • **写读冲突 ($WR$)**：$T_2$ 读取了 $T_1$ 未提交的临时脏数据，引发脏读。
法则：隔离性的核心是依靠并发控制技术消除 $RW/WW/WR$ 异常

核心物理哲学 (Isolation Engineering Compromise)

隔离性绝不是死板的硬性铁板一块，而是**性能吞吐与数据一致性之间的物理妥协**。数据库引擎通过提供多个隔离级别，允许开发者根据业务承受能力，在“绝对串行化”与“极高并发吞吐”之间灵活寻找平衡点。
