原子性与状态回滚机制 (Atomicity & State Rollback)

All-or-Nothing Principle, Before-Image Logging via Undo Log & Reverse Abort Handshake

事务异常中断与 Undo Log 逆向回滚链路 (Transaction Abort & Undo Flow) Before-Image Logging $\rightarrow$ Memory Write $\rightarrow$ Reverse Undo Cleanup
1. 写入 Undo 镜像 Before-Image
修改数据页前，引擎先将旧值（$A=100$）写入 Undo Log 缓冲区。
2. 内存数据更新 Buffer Pool
在内存脏页中更新为新值（$A=0$），后续可根据 STEAL 策略择机刷盘。
3. 中途遭遇异常 Abort / Crash
触发 `ROLLBACK`、死锁撤销、约束违反或进程突然断电崩溃。
4. 逆向 Undo 撤销 Reverse Apply
逆序读取该事务的 Undo Log，重新写回旧值 $A=100$，彻底擦除中间痕迹。

1. 原子性的工程定义与异常捕获诱因

Atomicity Definition

原子性（Atomicity）要求事务中的所有数据库修改操作**要么全部成功生效，要么全部被拒绝并完全撤销**。系统绝对不允许留存处于“只执行了部分 SQL 语句”的物理中间脏状态。

引发事务失败回滚的物理诱因 Failure Vectors
  • **应用层主动终止**：显式执行 ROLLBACK 或触发业务异常（如余额不足）。
  • **数据库引擎中断**：违反唯一性约束、外键约束或被并发死锁检测器选为 Victim 被迫牺牲。
  • **系统级突发崩溃**：数据库进程崩溃、OS Kernel Panic 或服务器突发断电。
法则：无论何时发生异常，重启或回滚后数据必须与事务执行前无异

2. Undo Log (回滚日志) 的物理存储逻辑

Undo Mechanics
Before-Image 记录法则 Undo Record Structure

Undo Log 记录的是用于**撤销修改的补偿数据**。例如： • 执行 INSERT 时，Undo 记录对应行的主键，回滚时执行 DELETE。
• 执行 UPDATE 时，Undo 记录修改前的旧值（Before-Image），回滚时写回旧值。

// 典型 Undo Log 记录物理字段
struct UndoRecord {
uint64_t trx_id; // 所属事务 ID
uint64_t roll_ptr; // 指向同事务上一条 Undo 记录的指针
uint32_t page_id; // 物理数据页编号
byte[] before_img;// 修改前的数据旧镜像 (Before-Image)
};
法则：Undo Log 链表指针决定了回滚必须严格逆序逆向撤销

核心物理哲学 (Atomicity & Rollback Insight)

原子性并不是神迹，而是依靠数据库在修改内存数据前**强行先写 Undo Log 旧镜像**来实现的。只要带有 Before-Image 的 Undo Log 在手，系统随时有能力逆向回放擦除任何半完成的修改。
