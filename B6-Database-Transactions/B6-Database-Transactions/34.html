Undo 日志物理结构与事务逆向回滚 (Undo Log Structure & Transaction Rollback)

Undo Segment, Rollback Segment (RSEG), Before-Images & Reverse Abort Execution

InnoDB Undo Log 物理存储段层级与单向回滚链表 (Undo Log Segment Architecture) Rollback Segment (RSEG) Slot $\to$ Undo Slot $\to$ Undo Page $\to$ Undo Record
1. 回滚段 (RSEG) 128 RSEGs

表空间中管理 Undo 的顶层结构，每个 RSEG 包含 1024 个 Undo Slot。

2. Undo 页段 Insert / Update

按事务类型划分为 `Insert Undo`（提交即删）与 `Update Undo`（保留供 MVCC）。

3. Undo 记录物理项 Before-Image

记录物理修改前旧值 (`Before-Image`)，包含 `roll_ptr` 指向更早的 Undo 节点。

4. 逆向应用撤销 Reverse Apply

事务 Abort 时逆向遍历指针链，依次覆写回旧值，并生成 CLR 重做日志。

1. Undo Log 物理分类与字段解构

Physical Structure

InnoDB Undo 日志划分为两类形态完全不同的链表：

Insert Undo Log（插入回滚日志）

只在事务回滚时需要。因为新插入的行在事务提交前对其他事务不可见，**事务一提交该 Undo 日志便可直接物理删除**。

Update Undo Log（更新/删除回滚日志）

同时服务于回滚与 MVCC 快照读。事务提交后**不能立即删除**，加入 Purge 链表，等待无任何 ReadView 依赖时由后台 `purge_thread` 垃圾回收。

// TRX_UNDO_UPD_EXIST_REC 关键字段
struct UndoUpdateRecord {
uint64_t undo_no; // 事务内递增的 Undo 编号
uint64_t table_id; // 目标表 ID
uint64_t roll_ptr; // 指向同行上一条 Undo 记录的指针
byte[] before_image;// 被修改列的原始旧值镜像
};
法则：Insert Undo 提交即删，Update Undo 留给 Purge 线程回收

2. 事务逆向回滚执行管线与 CLR 保护

Rollback Pipeline

当事务触发 `ROLLBACK` 或崩溃重启需要清除未提交事务（Abort）时，执行以下步骤：

步骤 1：定位头节点指针

从事务控制块（TRX Header）获取当前事务最后写入的 `LastUndoLSN` 或聚簇索引页的 `DB_ROLL_PTR`。

步骤 2：逆向链表遍历与写回

沿着 Undo 链由新到旧逐条读取，将 `Before-Image` 旧值覆盖写入 Buffer Pool 数据脏页。

步骤 3：写入 CLR 补偿日志（防二次崩溃）

回滚物理页本身也是一次修改，**必须向 Redo Log 写入一条 CLR (Compensation Log Record)**，确保回滚过程中途若再次断电，重启后无需重复回滚已撤销项。

开启下一个核心：Slide 35 · Redo Log 物理结构与事务正向重放 (Replaying History)

核心物理哲学 (Undo Log Rollback Insight)

Undo Log 是数据库实现**“后悔药”**的物理载体。它不仅用 Before-Image 护航原子性撤销，更用 `roll_ptr` 构建了 MVCC 历史长河。为了防止回滚中途断电导致无限死循环，回滚动作本身还会向 Redo Log 写入 CLR 日志——这就是工程设计的极致严密性。
