MVCC 核心思想：读写解耦 (MVCC Core Philosophy: Non-Blocking Reads)

Multi-Version Concurrency Control, Lock-Free Snapshot Reads & Concurrent Read-Write Decoupling

MVCC 物理黄金法则：并发“读不阻塞写，写不阻塞读” (Non-Blocking Read-Write Decoupling) Traditional 2PL Locks vs. MVCC Snapshot Isolation
传统 2PL 封锁模式 (Strict 2PL Locking) Read-Write Mutual Blocking
• **读读**：加 $S$ 锁，共享兼容
• **读写 / 写读**：$S$ 锁与 $X$ 锁互斥，读写操作互相强行挂起等待！
• **后果**：写事务阻塞高频读查询，系统整体并发吞吐量剧烈下跌。
MVCC 多版本并发模式 (Snapshot Read) Lock-Free Snapshot Read
• **写操作**：更新当前页生成排他写锁，并在 Undo Log 生成历史版本链。
• **读操作**：完全不加锁！根据 ReadView 直接拉取合法的历史快照 (Undo Image)。
• **结果**：读写完全解耦，极大地提升了商业数据库的高并发 TPS！

1. MVCC 诞生的核心痛点与物理哲学

Multi-Version Principle

多版本并发控制（MVCC）是现代化关系型数据库（MySQL InnoDB、PostgreSQL、Oracle）解决**读写冲突**最核心的物理杀手锏：

旧数据的物理保留 (Multi-Version Records)

当写事务对某行数据执行 `UPDATE` 或 `DELETE` 时，引擎不会直接在原物理位置毁灭旧值，而是将旧镜像（Before-Image）追加保存在 Undo Log 中。

历史快照与事务视角的匹配 (Consistent Snapshot)

读事务根据自身开启时的状态，在 Undo 链上寻找属于自己“可见”的特定历史快照。即使写事务正在强行加锁修改最新行，读事务依然能无锁顺畅读取旧快照。

法则：MVCC 依靠多版本 Undo 链，用空间换取了并发读写的零锁等待

2. 快照读 (Snapshot Read) 与 当前读 (Current Read)

Two Read Modes

在 MySQL InnoDB 引擎中，SQL 查询根据语义被划分为两类完全不同的读取模式：

快照读 (Snapshot Read / Consistent Nonlocking Read)

普通的不带锁 `SELECT` 语句。读取由 MVCC ReadView 确定的历史快照版本，**完全不加任何锁**，极高并发。

当前读 (Current Read / Locking Read)

读取记录的**最新已提交物理版本**，并对读取到的记录加锁：
• `SELECT ... FOR UPDATE` (加 $X$ 锁)
• `SELECT ... LOCK IN SHARE MODE` (加 $S$ 锁)
• `UPDATE / DELETE / INSERT` (先执行当前读加 $X$ 锁，再执行写修改)

开启下一个核心：Slide 26 · InnoDB 隐式系统列 (DB_TRX_ID, DB_ROLL_PTR) 与 Undo 版本链

核心物理哲学 (MVCC Non-Blocking Insight)

MVCC 的本质是**把写操作产生的旧数据转化为只读的版本快照**。这使得占比高达 80% 以上的普通 `SELECT` 查询能够彻底摆脱排他写锁的束缚，真正实现了互联网高并发下的“读不阻塞写，写不阻塞读”。
