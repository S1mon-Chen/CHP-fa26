1. 内存淘汰维度：STEAL vs. NO-STEAL

Memory Dimension

决定 **未提交事务修改的脏页** 是否允许被 Buffer Pool 提前刷入磁盘：

STEAL 策略 (允许“窃取”) —— 必须配合 Undo Log

允许内存紧张时将未提交事务的脏页置换刷盘。若事务随后 Abort 发生崩溃，**物理磁盘上已存有脏数据**，必须依靠 **Undo Log** 逆向撤销。

NO-STEAL 策略 (禁止“窃取”)

未提交事务的脏页绝对禁止写盘。这意味着崩溃时磁盘永远无脏数据（无需 Undo），但**长事务或大批量写会将 Buffer Pool 挤爆**。

法则：STEAL 带来了极高 Buffer Pool 内存利用率，但必须用 Undo 保障原子性

2. 提交持久维度：FORCE vs. NO-FORCE

Commit Dimension

决定 **事务提交响应瞬间** 是否必须把该事务修改的所有物理数据脏页写回磁盘：

FORCE 策略 (提交“强刷脏页”)

提交前必须将所有脏页彻底刷回数据文件。无需 Redo Log 即可持久，但**每次提交产生大量离散随机写磁盘 I/O**，TPS 剧烈下跌。

NO-FORCE 策略 (提交“不强制刷脏页”) —— 必须配合 Redo Log

提交时数据脏页继续留在 Buffer Pool。**只需将极小的 Redo Log 顺序写盘 `fsync`**。即便断电，重启后重放 Redo Log 即可还原。

核心物理哲学 (STEAL/NO-FORCE Matrix Insight)

现代商业关系型数据库（MySQL InnoDB、Oracle、PostgreSQL）全数统一选型 **STEAL / NO-FORCE 组合**：通过 **STEAL 释放内存**、通过 **NO-FORCE 提升提交速度**，同时引入 **Undo Log 保证原子性**、**Redo Log 保证持久性**。

Speaker Notes / 讲师讲稿
🎯 引导学员透视 STEAL/FORCE 矩阵： “向学员做解构说明：数据库 Buffer Pool 的刷盘策略由两个维度决定：一是 STEAL（未提交的数据页是否允许刷新到磁盘数据文件），二是 FORCE（事务提交时是否强制把脏数据页同步写磁盘）。”
💡 剖析工业界为何全数选择 STEAL / NO-FORCE： “请学员特别关注右下角绿框：选择 STEAL 意味着 Buffer Pool 可以在内存吃紧时把未提交脏页换出写盘（高内存利用率），但必须使用 Undo Log 处理 Abort 回滚；选择 NO-FORCE 意味着提交时只写 Redo Log 顺序文件（极高提交吞吐），但断电后需要 Redo Log 重放恢复。这就是为什么 Undo 和 Redo 在商业数据库中缺一不可。”
