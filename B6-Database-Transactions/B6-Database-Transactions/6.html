持久性与非易失存储保障 (Durability & Non-Volatile Storage)

Volatile Memory vs. Non-Volatile Storage Gap, Force vs. No-Force Page Flush & WAL Redo Persistence

事务提交与持久性落盘链路 (Commit Persistence & WAL Pipeline) Memory Write $\rightarrow$ Redo Log Flush (`fsync`) $\rightarrow$ Async Dirty Page Flush
1. 内存脏页修改 Buffer Pool
更新 Buffer Pool 内存页（高吞吐），数据处于易失（Volatile）状态。
2. 顺序刷入 Redo Log Sequential I/O
将本次改动的重做日志（Redo Log）顺序写入日志缓冲区并准备调用 `fsync`。
3. 强制刷盘 (`fsync`) Commit Point
将 Redo Log 强行写回物理磁盘。一旦 `fsync` 返回成功，向客户端响应 `COMMIT OK`。
4. 延迟异步刷脏页 No-Force Policy
离散的数据脏页延迟写回物理数据文件，途中断电可依靠 Redo Log 重放恢复。

1. 内存与磁盘的物理鸿沟 (Memory vs. Disk Gap)

Physical Paradox

数据库引擎面临着严重的物理矛盾：**内存速度快但易失，磁盘非易失但随机写极其昂贵**。

内存 (Buffer Pool) Volatile
  • • 纳秒级（ns）访问速度
  • • 支撑极高并发读写
  • • 突发断电/崩溃即彻底丢失
非易失磁盘/SSD Non-Volatile
  • • 永久保存，断电不丢失
  • • 毫秒/微秒级访问速度
  • • 离散数据页随机 I/O 极慢
核心矛盾：如何用最低的物理 I/O 成本换取最高的持久性保障？

2. 提交刷盘策略权衡：Force vs. No-Force

Policy Trade-off
FORCE 策略 (提交时强制刷脏页) High Latency

事务提交时，系统强行将该事务修改的所有内存脏页写回磁盘。无需 Redo 日志即可保障持久性，但**会导致大量的磁盘离散随机 I/O，吞吐量断崖式下跌**。

NO-FORCE 策略 + WAL (工业标准解法) Sequential Log Flush

事务提交时**不强制写回离散数据脏页**，仅将修改记录写入 **Redo Log 重做日志并调用 `fsync` 刷盘**。将离散随机 I/O 转化为高效的顺序追加写（Sequential Write）。

法则：NO-FORCE + WAL 顺序写是现代化数据库系统的绝对主流

核心物理哲学 (Durability & WAL Insight)

持久性的核心工程智慧在于：**绝不直接向磁盘写离散的数据页，而是先向物理磁盘顺序追加写 Redo Log**。利用预写日志（WAL）以微秒级顺序 `fsync` 开销保证持久性，同时将高昂的数据页刷盘延迟卸载（Offload）到后台。
