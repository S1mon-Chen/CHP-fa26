Part 03 · 隔离级别与数据库封锁协议

并发异常 1：脏读与脏写 (Dirty Read & Dirty Write)

Dirty Write ($WW$ Conflict), Dirty Read ($WR$ Conflict) Timelines, Rollback Cascades & Physical Safeguards

并发读写冲突异常图解：脏写 ($WW$ 覆盖未提交) vs. 脏读 ($WR$ 读未提交) Hazard: Uncommitted Intermediate State Leakage
异常 A：脏写 (Dirty Write / $WW$ 冲突) Strictly Forbidden
// $T_1$ 修改数据项 $A$ 后未提交，$T_2$ 强行覆盖修改 $A$
Sequence: $w_1(A=200) \to w_2(A=300) \to \mathbf{a_1 \text{ (Abort!)}}$
* 灾难性后果：$T_1$ 发生回滚 ($a_1$)，将 $A$ 恢复为旧值 $100$，直接冲毁了已提交或并发的 $T_2$ 的修改 ($300$)！数据库发生物理破损。
• **铁律**：所有 SQL 隔离级别（包含 Read Uncommitted）必须**绝对禁止脏写**。
异常 B：脏读 (Dirty Read / $WR$ 冲突) RU Level Risk
// $T_1$ 修改数据项 $A$ 但未提交，$T_2$ 读取了 $A$ 的中间值
Sequence: $w_1(A=200) \to \mathbf{r_2(A \Rightarrow 200)} \to \mathbf{a_1 \text{ (Abort!)}}$
* 灾难性后果：$T_2$ 读到了 $200$ 并以此为依据计算账单；随后 $T_1$ 被回滚，$T_2$ 读到的 $200$ 成为物理上**从未存在过**的脏数据。
• **解法**：在 RC 及以上级别，通过 **MVCC 快照读** 或 **排他写锁** 消除脏读。

1. 脏写 (Dirty Write) 物理防线机制

Exclusive Lock Mandate

脏写是最严重的并发灾难，因为它会导致数据库的状态一致性与 Undo 回滚机制全面崩溃。数据库通过以下物理手段禁止脏写：

写操作强行加 X 锁 (Exclusive Lock)

任何事务在修改数据项 $X$ 之前，必须先获取 $X$ 的**排他锁 (X 锁)**。

X 锁保持至事务提交 (Strict 2PL)

$T_1$ 持有的 X 锁必须保持到 $T_1$ 彻底 `COMMIT` 或 `ABORT` 后才释放，强行阻断 $T_2$ 在未提交数据上再次覆盖写入。

规则：没有任何隔离级别允许脏写发生，排他锁是维护写一致性的底线

2. 脏读 (Dirty Read) 消除与读写解耦解法

MVCC & S-Locks

要消除脏读（防止读取到未提交事务的修改），主流数据库引擎采用了两种完全不同的物理实现路径：

解法 A：MVCC 多版本快照读 (主流引擎如 InnoDB / Postgres)

写事务修改数据时生成 Undo 历史版本。读事务不加锁，直接根据 **ReadView** 读取事务启动时已提交的旧版本数据（Before-Image），实现“读不阻塞写，写不阻塞读”。

解法 B：读加 S 锁，写加 X 锁 (传统 2PL 封锁引擎)

读操作需要获取 **共享锁 (S 锁)**。由于写事务持有 X 锁，读事务会被强行阻塞，直到写事务提交释放 X 锁后才允许读取。

开启下一个核心：Slide 18 · 并发读写异常 2：不可重复读 (Non-Repeatable Read) 与更新丢失

核心物理哲学 (Dirty Read & Write Insight)

脏写冲毁数据库存储基石，因此被所有数据库严格杜绝；脏读暴露中间临时数据，现代 RDBMS 通过 **MVCC 快照读** 优雅消除脏读，既保障了 Read Committed 隔离安全性，又避免了读写相互加锁等待。
