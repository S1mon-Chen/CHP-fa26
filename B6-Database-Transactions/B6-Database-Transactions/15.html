Part 02 · 事务调度与可串行化理论

可恢复调度与无级联回滚 (Recoverable & Cascadeless Schedules)

Commit Order Constraint ($c_i < c_j$), Cascading Aborts Elimination & Schedule Safety Hierarchy

事务调度安全层次包含图 (Schedule Safety Containment Spectrum) Hierarchy: Serial $\subset$ Strict $\subset$ Cascadeless $\subset$ Recoverable $\subset$ All
1. 纯串行 (Serial) 100% Isolated
• **特点**：无交叉执行。
• **安全级别**：最高。
• **并发度**：吞吐量为零。
2. 严格 (Strict 2PL) RDBMS Standard
• **特点**：未提交写的修改不可被读取也不可被覆盖。
• **安全级别**：杜绝脏写与脏读。
3. 无级联 (Cascadeless) No Chain Abort
• **特点**：仅允许读取已提交数据。
• **优点**：彻底消除级联回滚风暴。
4. 可恢复 (Recoverable) Commit Order
• **特点**：依赖事务延后提交 ($c_i < c_j$)。
• **最低底线**：防止提交数据泄漏。

1. 可恢复调度 (Recoverable Schedule)

Commit Order Rule
可恢复调度的形式化定义 $c_i < c_j$ Order

若调度 $S$ 中事务 $T_j$ 读取了由事务 $T_i$ 写入的数据项 $X$，则 **$T_i$ 的提交操作 $c_i$ 必须先于 $T_j$ 的提交操作 $c_j$ 发生**。

不可恢复陷阱示例 (Unrecoverable Hazard) Forbidden
$S_{\text{bad}}: w_1(A) \to r_2(A) \to \mathbf{c_2} \to a_1$
* 灾难原因：$T_2$ 读了 $T_1$ 的脏数据后先提交 ($c_2$)。根据持久性，$T_2$ 提交结果不可撤销；随后 $T_1$ 发生回滚 ($a_1$)，但已提交的 $T_2$ 无法撤销，脏数据永久泄漏！
法则：读脏事务提交的顺序约束是数据恢复的绝对底线

2. 无级联回滚调度 (Cascadeless Schedule)

Avoid Cascading Aborts
无级联调度的形式化定义 Read Committed Data Only

调度 $S$ 中，事务 $T_j$ **仅被允许读取已被提交事务写入的数据**（即 $T_j$ 读取 $X$ 之前，$T_i$ 必须已经完成 $c_i$）。

消除级联回滚风暴 (Cascading Aborts) Chain Abort Risk

在允许读取未提交数据的可恢复调度中，若 $T_1$ 发生回滚 ($a_1$)，会导致依赖 $T_1$ 的 $T_2, T_3, \dots, T_k$ 全部被迫产生连锁级联回滚，引发系统 CPU 与 I/O 资源风暴。**无级联调度通过只读已提交数据，彻底扑灭级联风暴**。

Part 02 总结 (Recoverable & Cascadeless Engineering Insight)

可恢复性与无级联性是数据库系统实现**安全可靠故障回滚 (Abort/Rollback)** 的理论基石。现代化 RDBMS 引擎（如 MySQL InnoDB）通过实施 **严格两阶段锁 (Strict 2PL)**，天然保证了所有调度既是冲突可串行化的，又是无级联、可恢复的。
