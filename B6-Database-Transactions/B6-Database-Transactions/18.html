并发异常 2：不可重复读与更新丢失 (Non-Repeatable Read & Lost Update)

Non-Repeatable Read ($RW$ Conflict), First/Second Class Lost Updates & Defensive Solutions

并发读写冲突图解：不可重复读 ($RW$ 读后写) vs. 第二类更新丢失 (提交覆盖) Hazard: In-Transaction State Drift & Overwrite
异常 A：不可重复读 (Non-Repeatable Read / $RW$ 冲突) RC Level Risk
// $T_1$ 首次读取数据 $A=100$；$T_2$ 随后修改 $A=200$ 并提交；$T_1$ 再次读取 $A$
Sequence: $r_1(A \Rightarrow 100) \to w_2(A=200) \to \mathbf{c_2} \to \mathbf{r_1(A \Rightarrow 200)}$
* 灾难性后果：$T_1$ 在同一个事务内部两次读取同一行数据，得到了不一致的结果（$100 \neq 200$），导致账单报表计算崩溃。
• **解法**：开启 **Repeatable Read (RR)** 级别，依靠事务级 **MVCC ReadView** 或 S 锁消除。
异常 B：更新丢失 (Lost Update / 提交覆盖) Silent Overwrite
// $T_1$ 与 $T_2$ 同时读到 $A=100$；$T_1$ 加 50 提交 $150$；$T_2$ 基于旧值加 100 提交 $200$
Sequence: $r_1(A=100), r_2(A=100) \to w_1(A=150) \to c_1 \to \mathbf{w_2(A=200) \to c_2}$
* 灾难性后果：$T_2$ 的提交直接覆盖了已经完成的 $T_1$ 的加款操作！$T_1$ 增加的 $50$ 元被静默蒸发。
• **解法**：使用 **排他写锁 ($X$-Lock)**、**乐观锁版本号 (`version`)** 或 **原子 SQL 语句**。

1. 不可重复读 (Non-Repeatable Read) 物理防御

ReadView & S-Locks

不可重复读源于 **读写冲突 ($RW$)**。现代数据库提供以下物理手段消除不可重复读：

解法 A：事务级 MVCC 快照读 (InnoDB / Postgres RR)

仅在事务首次执行 `SELECT` 时生成一个 **ReadView**，并贯穿整个事务复用。后续任何 `SELECT` 均读取同一份历史快照，其他事务后续对该行的 `UPDATE/DELETE` 统统不可见。

解法 B：共享锁保持至事务结束 (Strict 2PL)

读操作对数据项 $X$ 加 **共享锁 (S 锁)**，且该 S 锁一直保持到事务 `COMMIT` 才释放。任何想要修改 $X$ 的写事务（需要 X 锁）都会被强行阻塞。

规则：Repeatable Read (RR) 级别保证同一事务内多次读取结果绝对一致

2. 更新丢失 (Lost Update) 三重防御模式

Defensive Design

第二类更新丢失是高并发扣款与库存扣减场景的头号杀手。工程上采用三层防御手段：

1. 当前读悲观排他锁 (`SELECT ... FOR UPDATE`)

读取时强制获取 **排他锁 (X 锁)**，阻塞其他事务读取与修改，直至当前事务处理完毕。

2. 数据库层面原子 UPDATE 替换

避免应用层“先 Read 再在内存中 Compute 最后 Write”。改用原子 SQL：UPDATE account SET balance = balance + 50 WHERE id = 1。

3. 业务层乐观锁 (`version` 字段)

更新时带上读取时的版本号：UPDATE account SET balance=150, version=version+1 WHERE id=1 AND version=1。受影响行数为 0 则重试。

开启下一个核心：Slide 19 · 并发读写异常 3：幻读 (Phantom Read) 概念与间隙锁防御

核心物理哲学 (Non-Repeatable Read & Lost Update Insight)

不可重复读是由于在同一个事务内两次读取之间插入了其他事务的 `UPDATE`；而更新丢失则是并发“先读后写”覆盖了彼此的修改。在生产环境中，**原子 UPDATE** 与 **乐观锁版本号 (`version`)** 是解决高并发扣款更新丢失的最轻量级武器。
