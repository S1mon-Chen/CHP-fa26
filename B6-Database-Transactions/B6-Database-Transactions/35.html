1. Redo Log 物理结构与 MTR (Mini-Transaction) 原子性

MTR Atomicity

Redo Log 是 InnoDB 保证**持久性 (Durability)** 的核心载体。对底层数据页的任何物理修改均由 **Mini-Transaction (MTR)** 保证原子性：

MTR (Mini-Transaction) 原则

对数据页进行底层修改（如 B-Tree 节点分裂或 Slot 更新）时，包含的所有 Redo 记录必须作为一个 MTR 原子组连续写入 Log Buffer，末尾以 MLOG_MULTI_REC_END 标记，防止半写日志干扰重放。

LSN (Log Sequence Number) 递增刻度

单调递增的 64 位无符号整数，代表写入 Redo 日志的总字节量。数据页头部的 FIL_PAGE_LSN 记录了该页最后一次修改对应的 LSN。

// Redo Log Physiological Record 结构
struct RedoLogRecord {
uint8_t type; // MLOG_1BYTE, MLOG_2BYTES, MLOG_REC_UPDATE_IN_PLACE
uint32_t space_id; // 表空间 ID
uint32_t page_no; // 数据页号 (16KB Page)
uint16_t offset; // 页内物理 Offset
byte[] redo_payload;// 页内更新逻辑数据
};
法则：MTR 保障物理页修改的原子组提交，PageLSN 提供幂等重放基准

2. 刷盘参数 `innodb_flush_log_at_trx_commit` 权衡

Flush Policies

`innodb_flush_log_at_trx_commit` 决定了事务提交时，Redo Log 何时强行刷入物理磁盘：

0：每秒异步写盘与 fsync（最高性能，最高风险）

提交时不写盘，仅每秒由后台线程将 Log Buffer 写入 OS Cache 并调用 `fsync`。MySQL 进程崩溃或断电**可能丢失最近 1 秒的所有事务**。

1：每次提交强制写盘与 fsync（默认，金融级强持久性）

**每次 `COMMIT` 必须同步调用 `fsync` 刷入非易失磁盘**。严格符合 ACID 持久性，崩溃零数据丢失，但增加极小顺序写延迟。

2：每次提交写 OS Cache，每秒 fsync（折中折中）

提交时仅写入操作系统 Page Cache（不 `fsync`），每秒由后台线程调用 `fsync`。**MySQL 进程崩溃不丢数据**，仅 OS 宕机断电会丢 1 秒数据。

核心物理哲学 (Redo Replay & Durability Insight)

Redo Log 是数据库实现**“历史重放 (Replaying History)”**的物理凭证。通过将磁盘数据页离散写转化为极速的日志顺序写，配合比对 **$\text{Log LSN} > \text{PageLSN}$**，数据库能够在重启瞬间精准修复内存脏页丢失，完美锁死持久性底线。
