Part 03 · 隔离级别与数据库封锁协议

封锁粒度与表锁、行锁 (Lock Granularity: Table vs. Record Locks)

Locking Hierarchy, Table vs. Page vs. Row Granularity & Index Record Locking Constraints

封锁粒度光谱：并发吞吐量 vs. 锁管理开销权衡 (Granularity Spectrum) Coarse Granularity $\longleftrightarrow$ Fine Granularity
表级锁 (Table Lock) Coarsest
• **并发度**：极低（直接锁定整个表数据）
• **锁开销**：极小（无需维护逐行锁状态）
• **死锁风险**：极低（一次性锁定整个表）
页级锁 (Page Lock) Medium
• **并发度**：中等（锁定 16KB 物理数据页）
• **锁开销**：中等（BDB / B-Tree 页面锁定）
• **死锁风险**：中等（相邻并发页冲突）
行级锁 / 索引锁 (Record Lock) Finest
• **并发度**：最高（仅锁定索引行记录）
• **锁开销**：较高（需维护大量的锁结构）
• **死锁风险**：存在（交叉锁竞争导致循环等待）

1. InnoDB 行锁本质：对索引记录 (Index Record) 加锁

Index-Based Locking

InnoDB 的行锁在物理实现上**并不是直接加在物理行数据上，而是加在聚簇索引或二级索引项 (Index Record) 上**。

二级索引加锁链 (Secondary to Primary Index)

当通过二级索引更新数据时，InnoDB 会先对**二级索引记录**加锁，随后回表找到对应的**主键聚簇索引记录**并再次加锁。

无索引情况下的退化黑洞 (Index Failure Hazard)

重要警告：如果 SQL 的 `WHERE` 条件没有命中索引（导致全表扫描），InnoDB 只能把表里所有的索引记录及间隙全部锁住，相当于退化为表锁！

法则：无索引不行锁，优化查询索引是提升锁并发度的前提

2. 显式当前读 (Current Read) 加锁 SQL 语法

Current Read SQL

普通 `SELECT` 是快照读（不加锁）。如果需要在查询时强行加行级 S 锁或 X 锁，必须使用**当前读语法**：

// 1. 显式加共享锁 (S 锁 / 读锁)
SELECT * FROM account WHERE id = 1 LOCK IN SHARE MODE;
// MySQL 8.0+ 推荐新语法: FOR SHARE
// 2. 显式加排他锁 (X 锁 / 写锁)
SELECT * FROM account WHERE id = 1 FOR UPDATE;
// 阻塞其他事务的 LOCK IN SHARE MODE 和 FOR UPDATE
开启下一个核心：Slide 22 · 间隙锁 (Gap Lock) 与临键锁 (Next-Key Lock) 机制

核心物理哲学 (Lock Granularity Insight)

行锁虽然带来了极高的并发吞吐量，但前提是**查询必须精准走索引**。一旦缺少索引导致全表扫描，InnoDB 行锁将瞬间退化并锁住整张表的所有记录与间隙，造成严重的并发性能灾难。
