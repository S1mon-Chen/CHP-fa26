Part 02 · Elasticsearch 分布式搜索引擎架构

分布式写入流程与一致性 (Distributed Write Flow & Consistency)

3-Phase Write Pipeline (Coordinating $\to$ Primary $\to$ Replicas), `wait_for_active_shards` Quorum & Failure Recovery

1. 分布式写请求执行三步曲 (3-Phase Distributed Write)

Write Pipeline
// 客户端发起 POST /orders/_doc/1001 写入流
1. 路由阶段 (Routing Phase) Client $\to$ Coordinating Node

客户端请求随机接入节点（即 **Coordinating Node**）。根据公式 $\text{MurmurHash3}(\text{"1001"}) \pmod 3 = 0$，计算出目标位于 **Primary Shard 0**，将请求转发至 Node 1。

2. 主分片写入 (Primary Execution) Node 1 (Primary Shard 0)

Node 1 校验 Mapping 类型，校验通过后将文档写入本地 Index Buffer 和 **Translog 日志**，生成递增序列号 (`_seq_no`)。

3. 副本并行同步 (Parallel Replica Replication) Primary $\to$ Replicas

Primary Shard 0 **并行分发**写请求至 Replica 所在节点 (Node 3)。所有副本节点写入本地完成后，向 Primary 返回 ACK，Primary 再向 Coordinating 节点返回 ACK 告知 Client 写入成功。

关键：写请求必须先在 Primary 成功执行后，才能并行分发给各个 Replicas

2. 写入一致性控制与异常恢复 (Consistency & Recovery)

Consistency Rules
活跃分片门槛 (`wait_for_active_shards`) Default = 1

控制在开始处理写请求前必须处于活跃状态的分片副本数。
• 默认值 `1`：只要 Primary 活跃即允许写入；
• 设为 `all` 或强一致阈值 $N$：必须等待所有 Replica 活跃才允许写入，提升高可用防护。

副本同步失败处理流程 (Replica Failover) Auto Unhealthy Mark

若 Primary 分发写请求至 Replica 节点时某个 Replica 抛出异常或超时未响应：
1. Primary 向 Master 节点上报故障事件；
2. Master 自动在集群状态中将该问题 Replica 移除并标记为不健康；
3. 其它正常写请求不受影响继续完成响应。

// 序列号与乐观锁控制 (_seq_no & _primary_term)
Primary 节点为每个写操作分配严格递增的 _seq_no 与 _primary_term，即使副本因网络无序收包，也能按序列号严格按顺序重放日志，消除写冲突！
开启下一个核心：Slide 18 · 近实时 (NRT) 搜索物理机制：Buffer、Translog、Refresh 与 Flush

核心架构启发 (Distributed Write Flow Insight)

Elasticsearch 分布式写入采用了**主从并行副本同步架构 (Primary-Centric Replication)**。写请求严格先落地 Primary Shard 并生成 `_seq_no` 顺序号，而后向所有 Replicas 并行分发，既保证了数据顺序重放一致性，又极大减少了写响应的整体阻塞延迟。
