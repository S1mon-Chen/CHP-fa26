Part 01 · 全文检索原理与 Apache Lucene 物理内核

顺序扫描局限与倒排索引 (Sequential Scanning vs. Inverted Index)

Full Table Scan Bottlenecks ($O(N \times M)$), Forward Index vs. Inverted Index & Posting Lists

1. 传统 RDBMS 顺序扫描 (Sequential Scan) 痛点

O(N × M) Flaw

在海量文本检索场景下，使用关系型数据库 SQL LIKE '%keyword%' 必须对磁盘数据进行逐行逐字节的顺序扫描：

顺序扫描时间复杂度 (Time Complexity)
$$\text{Time Complexity}: O(N \times M)$$

其中 $N$ 为记录总文档条数，$M$ 为每篇文档平均字符长度。

① 传统 B+Tree 索引完全失效 Index Unusable

前置通配符 %keyword 破坏了 B+Tree 索引的最左匹配原则，强制退化为全表物理磁盘扫描。

② 无法计算词频相关性评分 (Relevance) No Scoring

仅能判断“包含”或“不包含”（Boolean 匹配），无法统计词频 (TF) 与逆文档频率 (IDF) 以进行相关性排序。

③ 海量数据下随机 I/O 延时飙升 High Latency

当文本规模达到 GB/TB 级时，单次检索产生的磁盘 I/O 导致 API 响应时间拉长至数十秒，引发连接池爆满。

致命局限：无法扩展至海量文档，且缺乏文本相关性匹配能力

2. 倒排索引物理思想 (Inverted Index Philosophy)

Inverted Mapping

倒排索引的核心哲学是将传统的 **“文档 $\to$ 包含的词项 (Forward Index)”** 颠倒映射为 **“词项 (Term) $\to$ 包含该词项的文档列表 (Inverted Index / Posting List)”**：

// 1. 正向索引 (Forward Index: Document -> Terms)
Doc 1 ──► "Apache Lucene is a high performance IR library"
Doc 2 ──► "Lucene provides full-text indexing and searching"
// 2. 倒排索引 (Inverted Index: Term -> Postings List)
Term "Apache" ──► [ Doc 1 ]
Term "Lucene" ──► [ Doc 1, Doc 2 ]
Term "IR" ──► [ Doc 1 ]
Term "searching" ──► [ Doc 2 ]
倒排索引的三大物理优势 Microsecond Lookup
  • • **微秒级定位**：检索时只需根据 Token 在 Term 字典中二分查找或 FST 寻址，无需读取全文物理文本。
  • • **天然支持集合运算**：支持多个关键词 Postings List 的交集（AND）、并集（OR）与差集（NOT）快速合并。
  • • **高效统计相关性**：Postings List 中可附加存储每个文档内部的词频 (TF) 与字符位置 (Position)。
开启下一个核心：Slide 4 · Lucene 核心数据模型 (Document, Field, Term 物理抽象)

核心架构启发 (Inverted Index Philosophy Insight)

倒排索引是现代搜索引擎（Lucene、Elasticsearch、Solr）的理论灵魂。通过将“文档包含词”翻转为“词指向文档”，建立了词典到文档 ID 列表的直接物理索引，将海量文本搜索的时间复杂度从 $O(N \times M)$ 骤降至 $O(\log \text{Terms})$。
