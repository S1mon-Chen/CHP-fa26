1. 主分片 (Primary Shard) 与副本分片 (Replica Shard)

Shards & Replicas
Primary Shard (主分片) Fixed Count

将 Index 数据水平切分为 $N$ 份，突破单节点存储与写入吞吐上限。**创建索引后 Primary Shard 数量绝对不可修改！**（若修改会导致原有 Hash 路由归错物理 Shard）。

Replica Shard (副本分片) Dynamic Scale

Primary Shard 的物理镜像副本。提供故障自动转移 (Failover) 高可用保障；同时分担并发**读请求**。副本数量可随时动态修改（例如将 Replica 设为 2）。

// 索引 "orders" (3 Primaries P0-P2, 1 Replica R0-R2 $\to$ 6 物理 Shards)
Node 1: [ P0 (Primary 0) ] [ R1 (Replica 1) ]
Node 2: [ P1 (Primary 1) ] [ R2 (Replica 2) ]
Node 3: [ P2 (Primary 2) ] [ R0 (Replica 0) ]
黄金准则：Primary 与对应 Replica 绝对禁止分配在同一个物理 Node 上

2. 文档路由计算公式 (Document Routing)

MurmurHash3
ES 文档分片路由核心公式 (Routing Formula)
$$\text{Shard ID} = \text{MurmurHash3}(\text{routing\_value}) \pmod{\text{primary\_shards\_count}}$$

默认 `routing_value` 为文档 `_id`。计算结果范围在 $0 \sim (\text{primary\_shards\_count} - 1)$。

自定义 Routing 锁定数据倾斜与微秒级定向检索 `routing=user_id`

若默认使用 `_id`，查询某用户数据必须在**所有 Shards** 上执行广播散发（Scatter-Gather）。通过指定 routing=user_id，将相同用户的全部文档绑定在同一个 Shard，查询时精准直达，效率提升数十倍！

POST /orders/_doc/1001?routing=user_888
GET /orders/_search?routing=user_888 // 仅检索目标 1 个 Shard
// 深度透视：为什么创建索引后 Primary Shard 数量不可修改？
公式中分母为 primary_shards_count。若修改了 Primary 数量，同 `_id` 文档重新计算出的 `Shard ID` 将与已存位置不一致，导致原有文档**永远无法被查到**！

核心架构启发 (Sharding & Routing Insight)

分片与副本是 Elasticsearch 实现海量数据扩展与高可用的基石。理解 **$\text{MurmurHash3}(\text{routing}) \pmod N$** 公式能帮助我们在大规模多租户或电商系统中善用 **Custom Routing**，将广播搜索转化为单 Shard 精准定位，显著降低 CPU 消耗。
