冷热分离架构拓扑与生产无损滚动更新 (Hot-Warm-Cold & Rolling Restart)

Node Role Tiering (`data_hot`, `data_warm`, `data_cold`), Searchable Snapshots & Zero-Downtime Maintenance

1. 冷热分离物理节点角色拓扑 (Tiered Storage Topology)

Node Tiering
Hot Nodes (热节点) NVMe SSD + High CPU

• **角色设置**：node.roles: [ data_hot, data_content ]
• **物理职责**：高频 Bulk 写入与实时检索。配备极速 NVMe SSD 与极高 CPU 算力。

Warm Nodes (温节点) Standard SSD / HDD

• **角色设置**：node.roles: [ data_warm ]
• **物理职责**：处理近 30–90 天只读历史数据。进行 ForceMerge 1 段合并压缩，降低内存开销。

Cold & Frozen Nodes (冷/冻节点) S3 / MinIO Object Storage

• **角色设置**：node.roles: [ data_cold, data_frozen ]
• **物理职责**：挂载云端廉价对象存储 (S3/MinIO) 配合 **Searchable Snapshots**，成倍削减存储开销。

效果：存储成本直降 70%+，将黄金硬件算力 100% 倾斜给写热点

2. 生产环境无损滚动重启四步法 (Rolling Restart)

Zero-Downtime
严禁在生产环境直接 kill -9 重启节点！ Avoid Rebalance

直接停节点会导致 Master 误判定节点挂掉，瞬间在全网触发巨量分片（Shards）跨节点网络迁移复制，引发磁盘 I/O 和网络带宽风暴！

// 步骤 1: 暂时关闭节点分片自动平衡分发 (Disable Allocation)
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.enable": "primaries" } }
// 步骤 2: 执行物理 Synced Flush，清空内存待落盘数据
POST /_flush/synced
// 步骤 3: 停止目标单个节点服务 $\to$ 执行配置/版本升级 $\to$ 重启该节点
# 待重启节点成功加入集群并且状态恢复后，再继续处理下一个节点
// 步骤 4: 重新恢复集群全局分片自动平衡分配
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.enable": "all" } }

核心运维架构启发 (Tiering & Rolling Maintenance Insight)

大型 Elasticsearch 集群治理的核心原则是**“按数据生命周期精细化控制”**：借由冷热分离架构让数据根据年龄流动到最经济的存储介质上，借由严格的无损滚动重启（Rolling Restart）规范避免误关闭节点引发的跨网络 Shard 搬迁风暴，实现 7x24 小时零停机维护。
