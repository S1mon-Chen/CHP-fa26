Part 02 · Elasticsearch 分布式搜索引擎架构

Query 上下文 vs. Filter 上下文 (Query Context vs. Filter Context)

Dual Execution Paths, `_score` BM25 Calculation vs. Fast BitSet Caching & Performance Rules

1. Query 上下文 (Query Context)

Calculates `_score`
核心问题：How well does this doc match? Relevance Score

评估文档与查询条件的**相关性程度**！必须执行复杂的 **Okapi BM25 公式** 计算每个匹配文档的相关性得分 _score。

缓存机制：无法进行 BitSet 缓存 No Caching

由于不同用户查询词、词频与文档分布动态变化，算出的得分不能复用，**结果无法沉淀缓存**，每次查询均需消耗 CPU 进行浮点计算。

// 典型 Query Context 语法 (must / should)
{ "match": { "title": "wireless headphones" } }
// 适用场景：全文搜索，要求按相关度降序排列 (Relevance Ranking)
代价：需消耗 CPU 算得分，且无缓存；仅在做全文语义/模糊匹配时使用

2. Filter 上下文 (Filter Context)

BitSet Caching
核心问题：Does this doc match? (Yes / No) Zero Scoring

判断文档是否“符合”或“排除”条件！**完全跳过 BM25 得分计算**（返回的 _score 恒定为 0），节省巨大 CPU 资源。

缓存机制：自动激活 Fast BitSet 缓存 Roaring Bitmaps

频繁使用的 Filter 条件会自动在节点内存中构建 **BitSet (Roaring Bitmaps)** 压缩位图。后续相同过滤条件直接做极速位图与或运算，耗时达到**微秒级**！

// 典型 Filter Context 语法 (filter / must_not)
{ "term": { "status.keyword": "active" } }
{ "range": { "price": { "gte": 50, "lte": 300 } } }
// 适用场景：状态、分类、标签、时间/数值范围等结构化精准过滤
优势：不打分、省 CPU、激活 Node-Level BitSet 缓存；高并发场景下的防护罩

生产环境 Query DSL 黄金法则 (Filter First Rule)

在编写复杂 Query DSL 时，**凡是不需要计算相关性得分的条件（状态码、用户 ID、价格区间、时间范围、上架标志），强制写入 `bool.filter` 或 `bool.must_not` 中**！这样不仅省去了浮点打分计算，还能完美享受内存 BitSet 缓存带来的微秒级极速响应。

Speaker Notes / 讲师讲稿
🎯 引导学员区分 Query Context 与 Filter Context 的底层区别： “向学员做解构说明：很多工程师写 ES DSL 时把所有条件都塞在 `must` 里，这是非常低效的写法。
• **Query Context (`must`/`should`)**：回答‘这篇文档匹配得多好’，必须为每个文档算 BM25 浮点得分，且**无法被 BitSet 缓存**；
• **Filter Context (`filter`/`must_not`)**：回答‘这篇文档符不符合’（非黑即白），得分恒为 0，并且 ES 会在节点内存自动构建 **Roaring Bitmaps 位图缓存**！后来的相同过滤条件直接做位运算，极速返回。”
