Part 03 · 向量检索与 AI 时代 Vector DB

ES 8+ / Lucene 9+ 原生向量检索 (Native Vector Search)

`dense_vector` Mapping, HNSW Index Parameters (`m`, `ef_construction`) & Top-level `knn` Query DSL

1. `dense_vector` 映射与 HNSW 索引参数定义 (Mapping)

PUT /image_embeddings

在 ES 8.x 中，dense_vector 类型原生集成了 Lucene 9 的 HNSW 图索引：

// HNSW 向量索引 Mapping 定义
{
"mappings": {
"properties": {
"image_id": { "type": "keyword" },
"image_vector": {
"type": "dense_vector",
"dims": 1536,
"index": true,
"similarity": "cosine", // cosine | dot_product | l2_norm
"index_options": {
"type": "hnsw",
"m": 16, // 节点出边连接数
"ef_construction": 100 // 建图搜索候选池深度
}
}
}
}
}
提示：从脚本评分 (Script Score) 演进为原生 HNSW 图索引，检索效率提升 100 倍

2. 顶层 `knn` 向量搜索请求 (Native KNN Query DSL)

POST /_search

ES 8.x 引入了顶层 knn 参数，允许直接触发底层 Lucene 9 HNSW 图检索：

// 顶层 KNN 向量近似近邻检索 DSL
{
"knn": {
"field": "image_vector",
"query_vector": [0.12, -0.45, 0.88, /* ... 1536 dims */],
"k": 10, // 返回的目标近邻数
"num_candidates": 100 // 相当于 HNSW 的 efSearch (候选池深度)
},
"_source": ["image_id", "title"]
}
`num_candidates` 候选池权衡 Candidate Pool

• num_candidates 必须大于或等于 k。
• 调大 `num_candidates`（如 200–500）能提高向量召回率 (Recall)，但会增加 CPU 向量点积计算耗时。

开启下一个核心：Slide 29 · 专用向量数据库选型矩阵 (Milvus vs Qdrant vs ES 8)

核心物理架构启发 (Native ES Vector Search Insight)

Elasticsearch 8.x 的向量检索彻底摒弃了旧版本低效的线性脚本评分 (`script_score`)，直接将 **Lucene 9 的 HNSW 图文件** 编入底层的 Segment 中。利用顶层的 **`knn` DSL**，企业无需引入独立的向量数据库，即可在同一个 ES 集群内完成标量数据与千万级高维向量的微秒级统一检索。

Speaker Notes / 讲师讲稿
🎯 引导学员理解 ES 8.x 原生向量索引的突破： “向学员做解构说明：在 ES 7.x 早期，向量只能作为普通的密集数组存着，查询时要用 `script_score` 对全库做线性遍历，慢如龟速。
而在 ES 8.x / Lucene 9+ 中，通过引入 `dense_vector` 并把 `index_options.type` 设为 `hnsw`，建索引时就会自动在 Lucene Segment 里生成 HNSW 图文件，直接将向量检索提速了上百倍！”
💡 剖析 `num_candidates` 与 `k` 的关系： “请学员注意右侧代码中的 `"k": 10` 和 `"num_candidates": 100`：`k` 是你希望返回的近邻数量；而 `num_candidates` 代表在 HNSW 图底层的候选池搜索深度（相当于上一页介绍的 $efSearch$）。候选池设得越大，召回率 Recall 越高，但计算耗时也会有所增加。下一个 Slide 29 将对比**专用向量数据库 (Milvus / Qdrant) 与 ES 8** 的选型。”
