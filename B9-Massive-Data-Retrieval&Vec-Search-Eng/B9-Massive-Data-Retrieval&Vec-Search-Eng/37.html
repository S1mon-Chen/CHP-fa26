1. Snapshot & Restore 物理快照备份与灾难恢复

Snapshot & Restore

依赖 Repository 存储插件（如 S3、MinIO 或 NFS 共享挂载），对集群全量或指定索引构建增量物理快照 (Point-in-Time Snapshot)：

// 步骤 1: 注册 S3/MinIO 对象存储快照仓库
PUT /_snapshot/my_s3_repository
{ "type": "s3", "settings": { "bucket": "es-backups" } }
// 步骤 2: 创建按日增量物理快照 (Snapshot)
PUT /_snapshot/my_s3_repository/snapshot_20260821
{
"indices": "orders_2026*",
"ignore_unavailable": true,
"include_global_state": false
}
// 步骤 3: 灾难恢复 (Disaster Recovery Restore)
POST /_snapshot/my_s3_repository/snapshot_20260821/_restore
增量快照存储优势 (Incremental Delta)

ES 快照是底层 Lucene Segment 级别的物理硬链接引用。连续创建快照时，仅备份新增的 Segment 文件，极大节省存储空间与网络带宽。

提示：快照是唯一支持跨版本集群数据迁移的物理安全保障

2. 集群健康三色标识与 Kibana/Prometheus 监控指标

Health & Metrics
集群健康三色标识 (Cluster Health Status) GET /_cluster/health
GREEN 所有 Primary 与 Replica 分片均已成功分配
YELLOW Primary 均分配，部分 Replica 待分配 (无丢数据风险)
RED 至少 1 个 Primary 未分配！(数据丢失严重危险)
① JVM Heap GC 与内存垃圾回收 (G1GC STW) Heap <= 32GB

单节点 JVM 堆上限不得突破 **32GB**（防止 Compressed OOPs 压缩指针失效）。监控 Old Gen GC 频率，预防长达数秒的 Stop-The-World (STW) 卡顿。

② 线程池拒绝队列 (`rejected_execution_exception`) Write & Search Pools

重点监控 `write` 与 `search` 线程池的挂起队列。当积压队列满时将触发拒绝，客户端需引入指数退避重试 (Exponential Backoff)。

核心运维架构启发 (Cluster HA & Operations Insight)

海量 Elasticsearch 集群治理的核心铁律是**“把事故扼杀在黄灯与绿灯之间”**：一方面依靠定时 S3 物理增量快照建立灾备底线，另一方面借助 Prometheus/Kibana 监控 JVM 堆 GC 停顿与线程池拒绝队列，确保集群状态永不滑向代表 Primary 损坏的 **RED** 危险警戒线。
