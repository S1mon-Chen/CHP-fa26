多 Agent 蜂群拓扑结构：Supervisor、Hierarchical 与 Peer-to-Peer 网络

掌控蜂群决策指挥权与通信路径：解构 Supervisor 中心主管模式、Hierarchical 多级树状拓扑 与 Peer-to-Peer 对等网络 Handoff 的适用边界与控制力权衡

1. Supervisor 中心主管模式

Central Router Orchestration

Supervisor
# Supervisor Agent 充当中央路由调度器
Supervisor ──► Coder Agent
Supervisor ──► Tester Agent
Supervisor ──► Reviewer Agent
# 每次 Worker 执行完后，控制权必返回 Supervisor
  • 极高控制力与状态收敛：所有子 Agent 计算完后必须向 Supervisor 汇总，由主管决定下一步分发或结束。
  • 防范通信死锁： Worker 之间不可私自通信，彻底杜绝 A 与 B 无限循环交互的乱象。
定位：工作流明确、结果需严密把控的企业级单级业务网关

2. Hierarchical 多级树状拓扑

Multi-tier Manager-Worker Tree

Hierarchical
# 顶级主管调度子主管，子主管调度专业 Worker
Top Supervisor
├── Frontend Lead ──► [UI Agent, React Agent]
└── Backend Lead ──► [DB Agent, API Agent]
# 适合大型软件重构与分层领域推演
  • 分层上下文隔离：前端 Lead 仅感知 UI 状态，后端 Lead 仅感知 DB 状态，实现 Context 极大瘦身。
  • 支撑百级节点膨胀：通过多层主管归约，可承载超大型软件重构项目的蜂群协同。
定位：大型跨领域软件重构、复杂的企业级敏捷研发流水线

3. Peer-to-Peer 对等网络拓扑

Decentralized Direct Handoffs

P2P Network
# 无中心主管，Agent 之间基于 Handoff 函数直接转移
Agent A (Triage) ──► transfer_to_agent_B()
Agent B (Billing) ──► transfer_to_agent_C()
# 极简动态，但需警惕 A 与 B 之间产生无声死锁震荡
  • 极致灵活与低开销：免去 Supervisor 重复调度与 Prompt 评估过程，交接响应极其敏捷。
  • 适合客服分诊：如 OpenAI Swarm 示范的前台客服把用户工单直接转给账单客服。
定位：轻量客服分诊、极简工作流交接与轻量级 POC 验证

Multi-Agent Swarm Topology Architectural Decision Matrix / 多 Agent 蜂群拓扑架构选型矩阵

Swarm Decision Matrix
拓扑模式 / Topology Supervisor (中心主管) Hierarchical (多级树状) Peer-to-Peer (对等网络)
控制力与可预测性 / Control 极高 (主管统一持锁与裁决) 高 (分层主管隔离管控) 中/低 (由 Agent 自主交互交接)
状态开销 / State Overhead 中等 (全局与 Worker 状态汇总) 优 (各层级子图隔离极度瘦身) 高 (容易累积长多轮对话上下文)
死锁与震荡风险 / Deadlock 极低 (无 Worker 间隐式死锁) 低 (层级向上熔断拦截) 较高 (需挂载强制 Max Handoffs)

Architectural Core Thesis / 架构师视角

根据控制力诉求与状态收敛难度选择蜂群拓扑！大型软件重构与严肃工程首选 Supervisor 与 Hierarchical 拓扑；对于极简的在线客服分诊，才可以采用 Peer-to-Peer 对等网络，但必须同时挂载硬性最大交接次数熔断器。

Speaker Notes / 讲师讲稿
🎯 讲授 3 种多 Agent 蜂群拓扑： “向学员深入剖析：当我们把全能单 Agent 拆分为 Coder、Tester、Reviewer 之后，这些子 Agent 之间应该以什么结构组网？这就引出了三大拓扑：Supervisor（中心主管模式）、Hierarchical（多级树状模式）以及 Peer-to-Peer（对等网络模式）。”
💡 强调 Supervisor 与 Peer-to-Peer 的权衡： “提示学员看对比表：在对等网络（Peer-to-Peer）中，Agent A 可以直接调 `transfer_to_agent_B()` 交接给 B，这种方式极度敏捷；但如果 A 和 B 互相说‘我认为你的代码有问题’，没有中心主管协调，就会陷入无休止的死循环。因此在严肃工程落地中，我们更推荐带有中央裁决能力的 Supervisor 或 Hierarchical 架构。”
